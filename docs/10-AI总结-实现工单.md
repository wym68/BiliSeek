# BiliSeek 实现工单 · AI 总结（音视频 → Markdown）

> 状态：**待开工**（本文只是设计工单，未落任何代码）。
> 目标：用户自配 AI 服务，对一条视频（的某一 P）生成结构化 Markdown 总结；时间戳可点跳播。能力做成独立模块 `:core:ai`，后续其他入口（本地文件、合集批量、问答）直接复用。
> 前置：`AuthGate` / `WbiSigner` / `RequestThrottle` / `RiskCooldown`（Phase B 已落地）、`DownloadManager` 取流与 `DownloadService` 前台服务写法、`PlayerConnection.play(startPositionOverride)` / `seekTo()`。
> 关联：《架构设计篇》（模块边界、Service 承载长任务）、`CLAUDE.md`（Policy 纯函数、公开 API 克制、不持久化远端数据）、`AGENTS.md`（自动化不得联网）。
> **诚实红线**：
> 1. 自动化测试**既不打 B 站，也不打任何 AI 服务**（后者花钱、且 Key 不进 CI）。全部走 `MockWebServer` + 本地 fixture。
> 2. 第三方服务的行为（MiniMax 思考内容格式等）与离线识别的真机性能（耗时、发热、准确率）在拿到真机数据前一律标「未验证」，不写成通过。

## 0. 背景与已定决策

需求来自讨论（2026-09-29）。参考了 BiliNote（MIT，字幕优先 + ASR 兜底 + map-reduce + 断点续做）、BibiGPT-v1（GPL-3.0，时间戳提示词、字幕压缩）、bilibili-subtitle（MIT，按 UP 主章节分段）。三者许可证均与本项目 GPLv3 兼容，但都非 Kotlin，**只借思路、不搬代码**。

第二轮调研（识别 + 总结类项目）补充参考：phone-whisper（**GPL-3.0**，Android + sherpa-onnx，已上架；R8 规则、解码器收尾、下载进度节流可直接借鉴并注明出处）、android-offline-transcribe（Apache-2.0，Galaxy S10 真机测速：SenseVoice RTF 0.06、whisper.cpp tiny RTF 3.52）、AudioNotes（MIT，分层合并、句末切分）、ownscribe（MIT，孤立 `</think>` 清理）、VideoCaptioner（GPL-3.0，用标题/简介/标签作参考信息纠正同音错字）。

第三轮：BiliPai（GPL-3.0，本项目主要代码来源）的 AI 总结**不调用大模型**，直接读 B 站官方接口 `x/web-interface/view/conclusion/get`。本工单采纳其接口与状态判断（`AiSummaryFetchPolicy`），作为**零成本的第一选择**（§AI-4b）；但**不采纳**它的「打开详情页自动请求 + 排队时最多轮询 6 次 + HTTP 412 自动重试」，与本项目风控约束冲突。

| 维度 | 决策 |
|------|------|
| 模块 | 新建 `:core:ai`，**不依赖** `:core:network` / `:core:player`，不含任何 B 站概念；B 站接线在 `:app` |
| 提供商 | **可扩展的 Provider 架构**（§3）。v1 实现 OpenAI 兼容协议；预设：MiniMax 国内、MiniMax 国际、自定义（OpenAI 兼容）。模型名用户自填、无默认。Kimi Code 会员 Key 条款禁止编程工具以外使用，**不做预设** |
| 转写 | **本地离线识别**：新模块 `:core:asr`，sherpa-onnx（Apache-2.0）+ SenseVoice-Small int8 + Silero VAD；音频不出手机，只有识别出的文字发给大模型。云端转写（Whisper 兼容 / MiniMax `speech_to_text`）作为后续扩展，协议层预留（§3） |
| 识别模型 | 不打进 APK；App 内按需下载（多来源 + SHA-256 校验）或手动导入；APK 只保留 arm64-v8a（debug 另加 x86_64 供模拟器） |
| 运行条件 | 随时可运行；视频超过 30 分钟时先提示预估耗时与耗电；识别线程低优先级，不影响播放 |
| 官方总结 | 用户点「AI 总结」时**查一次** B 站官方 AI 总结（`view/conclusion/get`）：有 → 弹窗里作为默认选项「使用 B 站 AI 总结（免费）」，选中后直接转成本项目 md，不调用大模型；没有 / 排队中 / 未登录 → 走下面的自有流程。只在用户点击时请求、不轮询、未登录不请求、风控错误不重试 |
| 内容来源 | B 站字幕优先（人工中文 > AI 中文 > 任意中文 > 首条）+ 同接口的 UP 主章节 `view_points`；无字幕走本地识别；有字幕但未登录拿不到 → 提示登录或选择改用本地识别 |
| 长文本 | 章节优先分块 → 按体积分块 → 超长单段二分；每块总结 → 合并（只合并去重、不编造、保留时间戳）；每块落 checkpoint 可续做 |
| 推理模型 | 剥离 `<think>…</think>` 与 `reasoning_content`，md 只留正文 |
| 入口 | 播放页 `VideoActionBar` 新增「总结」；所有 `ActionListSheet` 三点菜单 + 动态长按菜单加「AI 总结」 |
| 启动 | 已有总结 → 直接开阅读页（可「重新生成」）；生成中 → 开阅读页看进度；没有 → 风格选择弹窗（有官方总结时默认选「使用 B 站 AI 总结」，否则默认上次风格；标明走字幕 / 本地识别） |
| 多 P | 播放页 = 当前 P；列表入口 → 复用挑 P 页（多选，每个选中的 P 各排一个任务）；每 P 一份 |
| 风格 | 预设「精简 / 详细笔记 / 时间戳大纲」+ 自定义提示词 |
| 执行 | 前台服务（`dataSync`）+ 通知进度；任务串行排队 |
| 展示 | 引入成熟 Markdown 渲染库；流式实时显示；时间戳点击跳播 |
| 存储 | App 私有目录存 md + 原文（字幕 / 识别文本），Room 存索引；分享 / 另存导出（SAF） |
| 流量 | 本地识别需先下载音频（已下载的视频完全离线），计量网络下先确认并显示预估流量；识别模型下载（约 230MB）计量网络下同样确认；字幕路径不拦 |
| 凭据 | API Key 用 Android Keystore（AES-GCM）加密后存 DataStore，**不进日志、不进 `AppSettings`** |

## 1. 范围

**做**：AI-0 ~ AI-8 与 AI-4b（§4）。

**不做（本期）**：Anthropic / Gemini 原生协议适配器（架构预留，§3.4）；云端转写（Whisper 兼容 / MiniMax `speech_to_text`，协议层预留；MiniMax Token Plan Starter 经查不含语音识别额度，按量约 $0.38/小时）；识别模型的 armv7 支持；NPU/QNN 加速；截图插入；基于总结的 AI 问答；合集批量总结；总结历史页（数据现成，随时可补）；官方总结的自动轮询与「打开页面即请求」；官方 `model_result.subtitle` 作为原文来源（待真机确认内容后再议）。

**任务依赖**：

```
AI-0 模块骨架 ─┬─ AI-1 Provider 与 OpenAI 兼容 Chat ── AI-2 总结流水线 ─┐
               └─ AI-3 设置与凭据 ────────────────────────────────────┤
AI-4 B 站字幕来源 + AI-4b 官方总结（:core:network + :app，可与 AI-1/2 并行）─┤
                                              AI-5 存储 + 任务 + 服务 ─┴─ AI-6 UI ─┐
```

建议顺序 **AI-0 → AI-1 → AI-2 → AI-3 → AI-4 → AI-4b → AI-5 → AI-6 → AI-7 → AI-8**。AI-0~AI-6 完成即「有字幕视频可用」的完整版本；AI-7/AI-8 补齐无字幕视频。AI-7 风险最高（原生库、性能），可提前做一个真机 spike 测 RTF。

## 3. Provider 架构（可扩展）

**核心思路**：把「一家 AI 服务」拆成 **协议（怎么说话）** × **预设（在哪、叫什么、有何怪癖）** 两层。

- 加一家**已支持协议**的服务（例如 Kimi 开放平台、DeepSeek、通义、SiliconFlow）= **只加一条预设数据**，零代码逻辑。
- 加一种**新协议**（Anthropic Messages、Gemini；以后的云端转写：Whisper 兼容、MiniMax `speech_to_text`）= 实现一个 `ChatClient` / `TranscriptionClient` 适配器 + 在 `ProviderFactory` 注册一行 + 加预设。上层 `Summarizer`、UI、存储全部不动。

### 3.1 协议与能力

```kotlin
package com.biliseek.core.ai.provider

/** 线协议。新增协议 = 新增枚举值 + 适配器 + ProviderFactory 一行。 */
enum class ChatProtocol { OPENAI_COMPAT /*, ANTHROPIC, GEMINI — 预留 */ }
// 以后做云端转写时再加（本期不建，仅示意扩展方向）：
// enum class TranscriptionProtocol { OPENAI_WHISPER_COMPAT, MINIMAX_STT }

/** 推理模型的「思考内容」长在哪。决定 ReasoningStripPolicy 怎么剥。 */
enum class ReasoningFormat { NONE, THINK_TAG_IN_CONTENT, SEPARATE_FIELD, AUTO }

/** 一家服务在某协议下的已知怪癖。全部有保守默认值，预设只覆盖差异。 */
data class ChatCapabilities(
    val streaming: Boolean = true,
    val reasoningFormat: ReasoningFormat = ReasoningFormat.AUTO,
    /** 部分推理模型拒收 temperature；为 false 时请求里不带。 */
    val acceptsTemperature: Boolean = true,
    /** 单次请求正文字节上限（保守估计，用于 ChunkPolicy）。 */
    val maxRequestBytes: Int = 96 * 1024,
    /** 额外固定请求参数（如某家需要的开关），原样并入 body。 */
    val extraBody: Map<String, kotlinx.serialization.json.JsonElement> = emptyMap(),
)

// 以后做云端转写时再加（本期不建）：
// data class TranscriptionCapabilities(val verboseJson: Boolean, val maxAudioSeconds: Int, val maxAudioBytes: Long)
```

### 3.2 预设目录

```kotlin
/** 一个可选的服务预设。只是「帮你填好」，所有字段在设置页都可覆盖。 */
data class ProviderPreset(
    val id: String,                 // 稳定 id，落库用；改名不改 id
    val displayName: String,
    val baseUrl: String,            // 自定义预设为空，由用户填
    val chatProtocol: ChatProtocol? = null,
    val chatCapabilities: ChatCapabilities = ChatCapabilities(),
    // 云端转写时再加 transcriptionProtocol / transcriptionCapabilities
    val docsUrl: String = "",       // 设置页「去哪拿 Key」
    val errorCodeMap: Map<Int, VendorErrorKind> = emptyMap(), // 厂商错误码 → 分类（§3.7.1），MiniMax 预设填写
)

/** 厂商错误码能映射到的类别；AiErrorPolicy 据此构造具体 AiError。 */
enum class VendorErrorKind { QUOTA, MODEL_NOT_IN_PLAN, CONTENT_FILTERED, RATE_LIMITED, INVALID_KEY }

object ProviderCatalog {
    val chat: List<ProviderPreset>          // minimax_cn, minimax_global, custom_openai
    fun byId(id: String): ProviderPreset?
}
```

v1 预设（**baseUrl 与能力值实现时逐一以官方文档核对，未核对的标 TODO**）：

| id | 用途 | baseUrl | 备注 |
|----|------|---------|------|
| `minimax_cn` | Chat | `https://api.minimaxi.com/v1` | 国内版 Key 只能打国内域名 |
| `minimax_global` | Chat | `https://api.minimax.io/v1` | 国际版 Key 只能打国际域名 |
| `custom_openai` | Chat | 用户填 | 任意 OpenAI 兼容服务（Kimi 开放平台、DeepSeek、通义、Ollama…） |

MiniMax 的 `reasoningFormat` 先按 `AUTO`（两种都剥）；是否用请求参数让它把思考拆到独立字段，**真机核对后**再写进 `extraBody`。

### 3.3 用户配置（落库形态）

```kotlin
/** 用户对某一用途（本期只有「总结」）的最终配置 = 预设 id + 覆盖项。 */
data class AiEndpointConfig(
    val presetId: String,
    val baseUrl: String,            // 预设值或用户覆盖
```

### 3.6 网络隔离（硬约束）

`:core:ai` 使用**自己的 `OkHttpClient`**，由 `:app` 构造时从空白 builder 起步：**无 CookieJar、无 B 站拦截器、无 B 站 UA/Referer**。绝不能把 B 站 Cookie（SESSDATA）带给第三方 AI 主机。日志拦截器（若开）必须对 `Authorization` 头打码。此约束写成一条测试：`AiHttpClientTest` 断言发往 MockWebServer 的请求不含 `Cookie` 头。

### 3.7 失败处理（贯穿 AI-1 / AI-2 / AI-3 / AI-5 / AI-6）

**总原则：已经花掉的成本不丢。** 字幕或本地识别的原文（`transcript.json`）、已完成的分块总结与合并轮次（checkpoint）在任何失败下都保留；重试只补剩下的部分；任何时候都有一个不依赖大模型的出口（原文笔记）。

#### 3.7.1 错误分类（`AiErrorPolicy`，纯函数）

**先判响应体、再判 HTTP 码**：MiniMax 可能返回 HTTP 200 但 `base_resp.status_code != 0`（官方 CLI `requestJson` 即如此处理），只看 HTTP 码会把失败当成功。响应体不是 JSON（如被公共 Wi-Fi 登录页截获）→ `BadResponse`。

| `AiError` | 典型信号 | 自动处理 | 用户出路 |
|-----------|----------|----------|----------|
| `Offline` | 系统无可用网络（`ConnectivityManager`） | 不算失败：任务转「等待网络」，网络恢复后自动继续 | 自动 |
| `Network` | DNS / 连接失败 / 超时 / 连接中断 / SSL | 指数退避重试 3 次（2s、6s、18s，带抖动） | 稍后重试 |
| `Server(code)` | 5xx、529（过载） | 同上 3 次 | 稍后重试 / 改用备用模型 |
| `RateLimited(retryAfterMs)` | 429 且非额度类 | 按 `Retry-After`（缺省 20s）等待，最多 3 次 | 稍后重试 |
| `QuotaExceeded` | 402、`insufficient_balance_error`、body 含 quota/insufficient/余额/用尽；MiniMax `1028`、`1030` | **不重试、不自动排期** | 稍后重试（额度恢复后手动点）/ 改用备用模型 / 用 B 站官方总结 / 生成原文笔记 |
| `Config(kind)` | `kind = INVALID_KEY`（401/403）、`WRONG_ENDPOINT`（404、非 JSON 的 2xx）、`MODEL_NOT_FOUND`（400/404 + model 相关）、`MODEL_NOT_IN_PLAN`（MiniMax `2061`）、`REGION_MISMATCH`（MiniMax 预设下 401 时的提示分支） | 不重试 | 去设置页，**按 kind 给出具体说明**（如「国内版 Key 只能用国内域名」）；改完后继续 |
| `ContentFiltered` | MiniMax `1002`、`1026`、`1027`、`1039`，或 body 含 sensitive | 不重试 | 改用备用模型 / 生成原文笔记 |
| `ContextTooLong` | 400 + context/length/token 相关 | 缩小分块重试（AI-2，最多 2 次） | 同 `Server` |
| `Truncated` | `finish_reason == "length"` | 分块总结：该块对半拆开重做；最终合并：追加一次「请从中断处继续」请求并拼接 | — |
| `BadResponse` | 空正文、只有思考内容、JSON 结构不对 | 重试 1 次 | 稍后重试 |
| `StreamInterrupted` | 流式输出进行中断开 | 按 `Network` 重试该步骤（只重跑这一步） | 已生成的部分保留显示并标「未完成」，不落成 `DONE` |
| `Cancelled` | 用户取消 | — | 保留断点，下次继续 |

MiniMax 专有错误码集中写在 MiniMax 预设的一个映射表里（`ProviderPreset.errorCodeMap`），不散落在通用逻辑中；其他厂商以后按需补表。以上 MiniMax 码值来自其官方 CLI 源码，**真机核对前标「未验证」**。

`temperature` 不被接受（400 + temperature）→ 去掉该参数重试 1 次，并在本次任务内记住（借鉴 BiliNote）。

#### 3.7.2 超时

| 阶段 | 超时 | 说明 |
|------|------|------|
| 连接 | 15s | — |
| 首个 token | 120s | 推理模型会先思考很久；思考内容增量（`reasoning_content` 或 `<think>` 内）也算「有输出」，会重置计时 |
| 流式两个增量之间 | 60s | 超过视为 `StreamInterrupted` |
| 非流式整体 | 180s | 分块总结与压缩合并用非流式 |

#### 3.7.3 预检（开跑前先确认配置能用）

- 任务开始前，若当前配置（`presetId + baseUrl + model + key 指纹`）**从未验证通过**，或**上次失败是 `Config`**，先发一次与「测试连接」相同的极短请求；失败即以 `Config` 结束，**不开始**下载音频 / 本地识别。
- 验证通过的配置记下 `lastVerifiedAt`（存 `AiSettingsStore`，按配置指纹区分），之后不再每次预检。key 指纹 = SHA-256 前 8 位，不存明文。
- 目的：避免跑完几分钟的本地识别后才发现 Key 填错。字幕路径同样预检（成本只有一次极短请求）。

#### 3.7.4 进度保留与续做

- **任务状态**（`ai_summary.status`）：`QUEUED` → `PREPARING`（取字幕 / 下载音频）→ `TRANSCRIBING` → `SUMMARIZING` → `DONE`；旁路状态 `WAITING_NETWORK`、`FAILED`。另有两列：`failureKind`（`AiError` 类别名）与 `hasTranscript`（原文是否已落盘）。
- **`FAILED` 且 `hasTranscript = true`** 即「原文已就绪、总结失败」：阅读页可看原文，顶部显示失败原因与出路按钮；「重试」从 checkpoint 继续，**不再取字幕 / 不再识别**。
- **换模型后沿用已完成的分块总结**：checkpoint 签名**不含模型**（= hash(原文 + 风格 + 分块参数)），每个分块结果记录生成它的 `presetId/model`；最终合并由当前模型完成。md 头部「模型」一栏列出实际用到的全部模型（如 `MiniMax-M2.7（分块 1–3）、DeepSeek-V3（分块 4–6、合并）`）。换风格仍会使签名失效。
- 进程被杀：下次启动时 `PREPARING / TRANSCRIBING / SUMMARIZING / WAITING_NETWORK` 的行按断点重新入队（识别有 `asr_partial.jsonl`，总结有 `checkpoint.json`）。

#### 3.7.5 备用模型（失败后询问再切换）

- 设置页「总结模型」下可选配一套「备用模型」（同样的预设 / Base URL / Key / 模型名 / 测试连接）。
- **只在以下失败时提供切换**：`QuotaExceeded`、`ContentFiltered`、`Server` / `Network` 自动重试耗尽。`Config` 错误**不提供**切换（应先修配置，避免掩盖问题）。
- **切换必须用户确认**（可能产生另一家的费用）：失败通知与阅读页都给出「改用备用模型继续」按钮；确认后以备用配置从断点继续（沿用已完成分块，见 3.7.4）。不做静默自动切换。
- 备用模型同样走 3.7.3 预检。

#### 3.7.6 原文笔记（不调用大模型的出口）

- `SummaryStyle.TranscriptNote`：`Summarizer` 遇到此风格**不发任何网络请求**，由 `TranscriptNotePolicy`（纯函数）直接把 `Transcript` 转成 md：头部同其他总结（来源 + 「原文笔记，未经 AI 整理」），有章节按章节分节，否则每 5 分钟一节；每节 `## [mm:ss] 标题或时间段`，正文为该段原文（句子级 `[mm:ss]` 可选保留）。时间戳可点跳播。
- 两个入口：① 风格弹窗里作为一个普通选项（未配置大模型时也可选）；② 任何失败后作为出路按钮「生成原文笔记」。
- 生成后 `status = DONE`、`style = TRANSCRIPT_NOTE`；之后仍可「重新生成」为 AI 总结（原文已在，不再取字幕 / 识别）。

#### 3.7.7 通知与提示文案

- 通知按失败类别给出一句原因 + 至多两个动作按钮，例如：
  - 额度已用尽 · [改用备用模型]（已配置时）/ [生成原文笔记]
  - API Key 无效 · [去设置]
  - 网络不可用 · 等待网络后自动继续（进行中通知，非失败）
  - 服务暂时不可用 · [重试] [改用备用模型]
- 阅读页失败横幅展示同样的原因与全部可用出路（重试 / 备用模型 / 官方总结（可用时）/ 原文笔记 / 去设置）。出路列表由 `FailureActionPolicy`（纯函数：`(AiError, hasTranscript, hasBackup, officialAvailable) → List<Action>`）计算。
- 日志只记录 `AiError` 类别、HTTP 码、厂商错误码与截断到 200 字符的消息；**绝不记录 Key、请求正文与原文**。

### AI-1 — Provider 与 OpenAI 兼容 Chat

`OpenAiChatClient`：`POST {baseUrl}/chat/completions`，`Authorization: Bearer`，body `{model, messages, stream, temperature?}` + `extraBody`。

- **`SseParser`**（纯函数）：按行解析 `data:`，忽略注释行/心跳，`[DONE]` 结束；兼容 `\r\n`、跨 chunk 断行、单事件多 `data:` 行。不引入 `okhttp-sse`，自写 ~50 行以便单测。
- **`ReasoningStripPolicy`**（纯函数）：
  - `THINK_TAG_IN_CONTENT`：去掉 `<think>…</think>`；**流式场景**要处理标签跨增量切开（`<thi` + `nk>`）与未闭合（仍在思考中 → 暂不输出）。
  - **孤立的 `</think>`**（借鉴 ownscribe `clean_response`）：部分服务端会吃掉开头的 `<think>`，正文里只剩一个 `</think>`。此时删掉 `</think>` 及其之前的全部内容。流式场景下，在见到第一个 `</think>` 或确认已开始输出正文之前，先缓冲一小段（如前 256 字符）再判断。
  - `SEPARATE_FIELD`：只取 `delta.content`，丢弃 `delta.reasoning_content`。
  - `AUTO`：两者都做。
- **`AiErrorPolicy`**（纯函数）：`(httpCode, body, finishReason, exception, preset) → AiError` + `shouldRetry(error, attempt)` + `backoffMs(attempt)`。完整分类与重试规则见 **§3.7.1**；超时见 **§3.7.2**。实现要点：先解析响应体（含 HTTP 200 + `base_resp.status_code != 0`），再看 HTTP 码；厂商码走预设的 `errorCodeMap`。

### AI-2 — 总结流水线（`Summarizer`）

流程：`Transcript` → 压缩 → 分块 → 逐块总结（每块落 checkpoint）→（多块时）**分层合并**（最后一轮流式）→ 规整 md。单块时直接流式出正文。

- **`TranscriptCompactPolicy`**：把逐句字幕合并成约 20~30 秒一行的 `[mm:ss] 文本`（借鉴 BibiGPT，减 token 且保留跳转精度）；超过 1 小时的视频用 `[h:mm:ss]`。去掉空行和纯符号行（「♪」「[音乐]」等）。
- **`ChunkPolicy`**：输入压缩后的行 + `chapters` + `maxRequestBytes`（扣除提示词开销）。有章节 → 按章节切，超长章节再按体积切；无章节 → 按体积贪心装箱；按体积切时**只在窗口后半段找句末标点**（`。！？；.!?;`）断开，避免切出大量过短的块；找不到句末（识别结果可能没有标点）时按上限硬切兜底（借鉴 AudioNotes）。单行超限 → 二分切（借鉴 BiliNote `request_chunker`）。输出 `List<Chunk(startMs, endMs, chapterTitle?, text)>`。遇到 `AiError.ContextTooLong` 时以 `maxRequestBytes / 2` 重新分块（最多 2 次）。
- **`PromptPolicy`**：`基础提示词 + 风格片段 + 格式约束 (+ 自定义)`。基础部分包含：中文输出、专有名词保留原文、「字幕可能有错别字请改正」、去广告/寒暄、**不要用代码块包裹输出**、**编号标题用 `## 1. xxx` 不用 `1. **xxx**`**、时间戳一律 `[mm:ss]`。`Timing.CHUNK` 时改为「时间戳仅标到段落级」。提示词附「参考信息」段：视频标题、简介（截断到约 500 字）、标签——用于纠正识别/字幕里的同音错字和专有名词（借鉴 VideoCaptioner 的 reference 做法），并注明「参考信息不是视频内容，不要据此补充视频里没说的内容」。模板分三套：**分块总结**（要求「完整保留所有事实、观点、数字、日期、专有名词和结论，不省略、不补充」，借鉴 AudioNotes 的 partial 提示词）、**压缩合并**（分层合并的中间轮：去重压缩但保留上述要素）、**最终合并**（只合并去重、不发明新内容、保留全部时间戳，按所选风格组织）。
- **`MarkdownPolicy`**：剥 ```` ```markdown ```` 外壳；时间戳格式归一（`12.4 -`、`(03:12)`、`【03:12】` → `[03:12]`）；丢弃超出视频时长的时间戳；拼 md 头部（标题、元信息、生成时间、模型、来源）。
- **分层合并（`MergePlanPolicy`，纯函数，借鉴 AudioNotes）**：分片摘要全部拼起来仍可能超过单次请求上限（长视频块数多时）。规则：若全部分片摘要 + 合并提示词 ≤ `maxRequestBytes` → 一次最终合并（流式）；否则按体积把分片摘要分组，每组做一次「压缩合并」（非流式），得到新一层摘要，重复直到能一次最终合并。每轮压缩结果也写 checkpoint。设最大轮数（如 4），超出报 `AiError.ContextTooLong`。
- **Checkpoint**：`checkpointDir/checkpoint.json` = `{signature, partials[{text, presetId, model}], mergeRounds[][]}`；`signature` = hash(原文内容 + 风格 + 分块参数)，**不含模型**（换模型沿用已完成分块，§3.7.4），签名不符即作废。全部完成后删除。
- **`Truncated` 处理**：分块总结遇 `finish_reason=length` → 该块对半拆开重做；最终合并遇到 → 追加一次「从中断处继续」请求并拼接，仍截断则以已得内容完成并在 md 末尾标注「输出可能不完整」。
- **`TranscriptNotePolicy`**（纯函数）：`SummaryStyle.TranscriptNote` 的实现（§3.7.6），`Summarizer` 对此风格直接返回，不发请求。
- 并发：分块总结**串行**（订阅额度有并发限制，且便于续做）。
- `VideoContext` 的来源：播放页已经会请求 `x/web-interface/view`（`VideoInteractionController`），但现有 DTO `VideoViewInfo` 没有解析简介。AI-4 顺带给它加 `desc`（简介）与 `tname`（分区名）两个可空字段，`VideoContext.tags` 先用分区名；真正的视频标签需要另一个接口，**本期不为它多发请求**。拿不到就不传，提示词里省略参考信息段。
- 验证：各 Policy 单测（压缩边界、章节切分、句末切分与硬切兜底、二分、提示词片段组合（含参考信息有/无）、md 归一的各种畸形输入）；`MergePlanPolicyTest`（一次可合并 / 需 2 轮 / 超过最大轮数）；`SummarizerTest`（MockWebServer 模拟 3 块 + 合并；分层合并 2 轮；中途失败后重跑只请求剩余块与剩余轮次；换模型后沿用已完成分块；ContextTooLong 触发缩块；Truncated 拆块与续写）；`TranscriptNotePolicyTest`（有章节 / 无章节 5 分钟分段、超 1 小时时间戳、**断言不发任何请求**）。

### AI-4b — B 站官方 AI 总结（零成本第一选择）

- **接口**（`BiliApi`）：

  ```kotlin
  @GET("x/web-interface/view/conclusion/get")
  ```

- **DTO**（`ConclusionDto.kt`，字段全部可空/有默认）：`ConclusionData{ code /*0 有, 1 无, -1 不支持*/, stid, model_result }`、`ModelResult{ result_type /*0 无, 1 仅摘要, 2 摘要+大纲*/, summary, outline: List<Outline>, subtitle: List<…> }`、`Outline{ title, timestamp /*秒*/, part_outline: List<PartOutline{ timestamp, content }> }`。`subtitle` 字段先解析但**本期不使用**（内容形态待真机确认）。

- **`OfficialSummaryPolicy`**（`:app`，纯函数；状态表照 BiliPai `diagnoseAiSummaryResponse`）：

  | 条件 | 结果 |
  |------|------|
  | 未登录（本地判断，**不发请求**） | `Skipped(NotLoggedIn)` |
  | 外层 `-101` | `Skipped(NotLoggedIn)` |
  | 外层其他非 0（含风控码） | `Unavailable(ApiError)`，不重试 |
  | `data.code == 0` 且 `summary` 或 `outline` 非空 | `Available(result)` |
  | `data.code == 0` 但内容为空 | `Unavailable(Empty)` |
  | `data.code == 1` 且 `stid == "0"` | `Unavailable(Queued)`（B 站还在生成；**不轮询**，弹窗提示「B 站总结生成中，可稍后再试或直接自己生成」） |
  | `data.code == 1` 且 `stid` 为空 | `Unavailable(NoSpeech)` |
  | `data.code == -1` | `Unavailable(Unsupported)` |
  | 网络异常 | `Unavailable(Network)`，不自动重试（用户可在弹窗点「重新查询」，仍是一次用户操作一次请求） |
- **何时请求**：只在「没有本地总结记录 → 打开风格弹窗」这一刻查询一次（与 `SummarySourcePolicy` 的字幕查询并行）。结果在内存里按 `(bvid, cid)` 缓存到进程结束，同一视频重复打开弹窗不重复请求。**不在打开播放页 / 详情时预取**。
- **`OfficialSummaryMarkdownPolicy`**（纯函数，思路同 BiliPai `AiSummaryNoteDraftPolicy`）：转成与自有流程一致的 md——同样的头部（标题、元信息、生成时间），来源标注「B 站官方 AI 总结」，模型字段留空；`summary` → 「## 一句话总结」；每个 `outline` → `## [mm:ss] 标题`，其下 `part_outline` → `- [mm:ss] 内容`。时间戳格式与 `MarkdownPolicy` 一致，阅读页的跳播逻辑无需区分来源。
- **保存**：用户在弹窗里选中「使用 B 站 AI 总结」即视为用户主动保存，写入 `summary.md` 与 `ai_summary` 表（`sourceKind = OFFICIAL`），不写 `transcript.json`。
- **与大模型配置的关系**：未配置大模型（无 Key / 无模型名）时，**官方总结仍然可用**——弹窗里自有生成的选项置灰并附「去设置」，官方选项照常可选。
- **阅读页「重新生成」**：来源为 `OFFICIAL` 时，弹窗默认选「用大模型自己生成」，官方选项仍保留（B 站的总结可能更新）。

### AI-7 — `:core:asr` 离线识别引擎 + 模型管理

**选型**：[sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)（Apache-2.0，Kotlin API，`OfflineRecognizer` + `Vad`）+ **SenseVoice-Small int8**（`sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2025-09-09`，中/英/日/韩/粤，自带标点与 ITN）+ **Silero VAD**（`silero_vad.onnx`，约 0.6MB）。第三方评测中文 CER：SenseVoice 7.8%，Whisper-large-v3 20.0%；CPU 约 17× 实时（服务器 CPU，手机需实测）。

**模块边界**：`:core:asr` 只认「本地音频文件 → 带时间戳的句子」，**不依赖** `:core:ai` / `:core:network` / `:core:player`，也不知道 B 站。唯一的网络行为是模型下载（`AsrModelManager`，自带独立 `OkHttpClient`，不带任何 Cookie）。

#### 公开 API

```kotlin
package com.biliseek.core.asr

data class AsrSegment(val startMs: Long, val endMs: Long, val text: String, val lang: String?)

sealed interface AsrProgress {
    /** 已处理到音频的哪个位置；UI 显示「12:30 / 58:00」。 */
    data class Running(val processedMs: Long, val totalMs: Long, val newSegments: List<AsrSegment>) : AsrProgress
    data class Done(val segments: List<AsrSegment>, val rtf: Float) : AsrProgress   // rtf 回填给预估
    data class Failed(val error: AsrError) : AsrProgress
}

sealed interface AsrError {
    data object ModelNotReady : AsrError
    data class DecodeFailed(val message: String) : AsrError      // 音频格式不支持 / 文件损坏
    data class EngineFailed(val message: String) : AsrError      // 原生层异常
    data object OutOfMemory : AsrError
}

class OfflineTranscriber(context: Context, models: AsrModelManager) {
    /** 串行执行；[checkpoint] 文件已有内容时从断点继续。取消协程即停止并释放原生资源。 */
    fun transcribe(audio: File, checkpoint: File?, numThreads: Int = defaultThreads()): Flow<AsrProgress>
}

data class AsrModelSpec(
    val id: String,                     // 例：sensevoice_small_int8_2025_09_09
    val displayName: String,
    val files: List<ModelFile>,         // model.int8.onnx、tokens.txt、silero_vad.onnx
    val sources: List<ModelSource>,     // 同一组文件的多个下载来源
    val license: String, val licenseUrl: String,
)
data class ModelFile(val name: String, val bytes: Long, val sha256: String)
data class ModelSource(val id: String, val displayName: String, val baseUrl: String) // 文件 URL = baseUrl + name

sealed interface ModelState {
    data object NotInstalled : ModelState
    data class Downloading(val doneBytes: Long, val totalBytes: Long) : ModelState  // 只在整数百分比变化时发射
    data object Verifying : ModelState
    data object Ready : ModelState
    data class Broken(val reason: String) : ModelState   // 校验失败 / 文件缺失
}

class AsrModelManager(context: Context) {
    val state: StateFlow<ModelState>
    suspend fun download(spec: AsrModelSpec, source: ModelSource)   // 断点续传（Range），逐文件 SHA-256
    suspend fun import(spec: AsrModelSpec, uris: List<Uri>)         // SAF 选文件，复制后同样校验
    suspend fun delete(spec: AsrModelSpec)
    fun modelDir(spec: AsrModelSpec): File?                        // Ready 时非空
}

object AsrModelCatalog { val default: AsrModelSpec; val all: List<AsrModelSpec> }
```

以上即 `:core:asr` 的全部公开类型，其余 `internal`。

#### 模型管理

- **不进 APK**。存放 `filesDir/asr_models/{specId}/`；下载先写 `.part`，全部文件校验通过才原子改名、状态置 `Ready`。
- **下载来源**（`ModelSource`，逐文件下载，**不下 tar.bz2**，免去解压依赖）：HuggingFace 原站（`csukuangfj/sherpa-onnx-sense-voice-zh-en-ja-ko-yue-int8-2025-09-09` 仓库 `resolve/main/`）、HuggingFace 国内镜像、（可选）ModelScope。具体 URL 与每个文件的字节数、SHA-256 **实现时从官方文件核对后写死**进 `AsrModelCatalog`；任何来源下载的文件都必须过同一组 SHA-256。
- **手动导入**：设置页「导入模型文件」→ SAF 多选 `model.int8.onnx`、`tokens.txt`（`silero_vad.onnx` 体积小，可随 APK 附带在 assets，免下载）→ 复制 + 校验。（是否额外支持直接导入官方 `.tar.bz2`：需引入 commons-compress，实现时再定。）
- **进度节流**（phone-whisper v0.9.9 的教训：进度推送过密把主线程消息队列塞满导致 ANR）：`Downloading` 状态只在整数百分比变化时发射；识别进度 `AsrProgress.Running` 同理，至多每 500ms 或每完成一个片段发射一次。
- 计量网络下下载模型先确认（约 230MB）；下载走 `SummaryService` 同款前台通知或独立通知，页面退出不中断。
- `silero_vad.onnx` 约 0.6MB，建议放 `:core:asr` 的 assets，首次使用时拷到模型目录。

#### 识别流水线

```
音频文件(m4a/AAC)
  → PcmDecoder：MediaExtractor + MediaCodec，边解码边吐 ShortArray（不整段读入内存；1 小时 16k float 约 230MB）
                必须一直取输出直到**输出端**出现 EOS 才 stop（见下）
  → ResamplePolicy：下混单声道 + 重采样到 16 kHz（线性插值即可，纯函数）
  → Silero VAD（窗口 512 样本）：得到语音片段 [start, end]
  → VadSegmentPolicy：合并间隔 < 300ms 的片段、切开 > 20s 的片段、丢弃 < 250ms 的片段（参数可调，单测覆盖）
  → SenseVoice OfflineRecognizer：逐片段识别（每片段一个 OfflineStream）
  → AsrTextPolicy：去 `<|zh|><|NEUTRAL|><|Speech|>` 类标签、规整空白与重复标点
  → AsrSegment(startMs, endMs, text)  ——  片段起止即句子级时间戳
  → AsrCheckpoint：每识别完一个片段就追加写 asr_partial.jsonl（片段即断点，processedMs = 最后片段 endMs）
```

- **断点续做**：重启后读 `asr_partial.jsonl`，取最后一个**已完成片段的 `endMs`** 作为续做起点，`PcmDecoder` seek 到该处（`MediaExtractor.seekTo` 落在之前的同步帧，解码后丢弃时间戳早于起点的样本），VAD 状态从零开始。VAD 片段本身就是完整的句子，起点之后到下一句之间只有静音或未处理的音频，所以**不需要回退重叠、也不需要去重**（对比 VideoCaptioner 按固定 8 分钟切块、重叠 10 秒再模糊对齐的做法，这里复杂度低得多）。写入 jsonl 时最后一行可能写了一半（进程被杀），读取时丢弃无法解析的末行。
- **解码收尾（phone-whisper v1.0.3 的教训）**：输入端送出 EOS 后，解码器里还积压着最后几帧；如果此时就 `stop()`，**最后几个字会丢**。循环条件必须是「输出缓冲带 `BUFFER_FLAG_END_OF_STREAM`」，而不是「输入已送完」。收尾时 VAD 也要 `flush()`，把最后一个未闭合的语音片段交给识别。
- **资源与优先级**：识别跑在单独的后台线程（`THREAD_PRIORITY_BACKGROUND`），`numThreads` 默认 `min(4, 大核数)`；前台服务保证识别不被系统杀掉。识别不占主线程，但会和播放争 CPU，真机验收要确认播放无卡顿；必要时识别期间把 `numThreads` 降到 2。
- **内存**：模型常驻约 250~300MB（int8，待实测）。识别结束立即 `release()` 原生对象；`onTrimMemory` 高等级时若空闲也释放。
- **取消**：协程取消 → 停止喂数据 → 释放 recognizer/vad → 保留 checkpoint（下次可续）。

#### 验证

- 纯函数单测：`ResamplePolicyTest`（44.1k/48k 立体声 → 16k 单声道长度与幅值）、`VadSegmentPolicyTest`（合并/切长/丢短/边界）、`AsrTextPolicyTest`（各类标签、空结果、中英混排）、`AsrCheckpointTest`（续做起点 = 最后片段 endMs、末行残缺被丢弃、空文件从 0 开始）。

### AI-8 — 本地识别接入总结流程

- **`LocalAsrSource`**（`:app`，实现 `TranscriptSource`）：
  1. 音频来源：「已下载」里有该 `(bvid, cid)` 且含音频 → 直接用本地文件（**完全离线，不请求 B 站**）；否则用 `DownloadManager` 同一取流解析器（`resolveSource`）拿 `audioUrl`，以**最低音质档**下载到 `ai_summary/{bvid}_{cid}/audio.m4a`（走 B 站媒体请求头的 client，不是 AI client），识别完成即删。
  2. 调 `OfflineTranscriber.transcribe(...)`，把 `AsrProgress.Running` 映射成 `SummaryManager` 的进度（通知与阅读页显示「本地识别 12:30 / 58:00」）。
  3. `AsrSegment` → `TranscriptSegment`；`Transcript.timing = SEGMENT`，`chapters` 仍来自 B 站 `view_points`（若 AI-4 已取到；取不到不影响）。
- **`LocalAsrPolicy`**（纯函数）：`(durationMs, lastMeasuredRtf?) → NoPrompt / ConfirmLong(estimatedMinutes)`。时长 > 30 分钟提示；无实测 RTF 时按**默认 0.1** 估算（android-offline-transcribe 在 Galaxy S10 上实测 SenseVoice 为 0.06，取保守值），每次完成后用 `AsrProgress.Done.rtf` 更新（取最近几次的滑动平均，存 `AiSettingsStore`）。预估耗时另加解码与 VAD 开销（按 RTF 的 20% 估，实测后修正）。
- **设置页「离线识别模型」卡片**：状态（未安装 / 下载中 xx% / 校验中 / 已就绪 xxxMB / 损坏）、来源选择、下载 / 暂停 / 删除、「导入模型文件」、许可证与来源说明。
- 验证：`LocalAsrPolicyTest`；`LocalAsrSource` 用假 `OfflineTranscriber` 测：本地音频不触发下载、下载失败可见、取消后保留 checkpoint、进度映射正确。**真机**：见 §5.2。

## 6. 风险与未决

1. **订阅条款**：Kimi Code 会员 Key 明文限制编程工具使用，不做预设；MiniMax Token Plan 未见此类限制，但以用户所购套餐的最新条款为准。设置页「去哪拿 Key」链接指向各家官方文档。
2. **云端转写（后续）**：经查 MiniMax Token Plan Starter 为纯文本套餐，不含语音识别；`speech_to_text`（`asr-1.0`）按量约 $0.38/小时，单次 ≤50MB / 500 秒，非 Whisper 兼容（`language` 走请求头）。需要时作为第一个「新协议」扩展案例。
3. **思考内容形态漂移**：推理模型的输出格式各家不一且会变；集中在 `ReasoningStripPolicy` + 预设的 `reasoningFormat`，默认 `AUTO` 兜底。
4. **官方总结接口**：`view/conclusion/get` 为未公开接口，字段与状态码含义来自 BiliPai 的实践（`stid == "0"` 表示排队等），可能变化；全部字段可空，解析失败按 `Unavailable` 处理，自有流程兜底。覆盖率有限（B 站只对部分视频生成），且需要登录。
5. **字幕接口变化**：`x/player/wbi/v2` 的 `subtitle` 字段在未登录时常返回空 url；AI 字幕可能延迟生成。DTO 全可空，失败走 `SummarySourcePolicy` 的明确分支，不静默。
6. **额度与并发**：订阅通常有 RPM / 并发限制；分块串行 + `RateLimited` 退避。超长视频（>3 小时）块数多、耗时长，UI 需显示预估块数。
7. **Markdown 渲染库兼容性**：版本与 Compose BOM、R8 的兼容需实测；有自写降级方案兜底。
8. **Keystore 可用性**：少数 ROM 的 Keystore 有 bug；解密失败一律按「未配置」处理并提示重填，不崩。
9. **离线识别性能**：耗时、发热、耗电因机型差异大，只能真机实测。参考数据：Galaxy S10（2019）上 SenseVoice RTF 0.06（30 秒音频，不含长音频的解码与 VAD 开销），1 小时约 4 分钟量级；更老或更低端的机器会更慢。缓解：长视频提醒 + 实测 RTF 回填预估 + 线程数自适应 + 断点续做。
10. **原生库体积与维护**：sherpa-onnx 无 Maven Central 发布，需手动升级入库的 AAR / .so；只保留 arm64 控制体积。R8 须保留 `com.k2fsa.sherpa.onnx.**`，否则 release 包运行时崩。
11. **模型下载可达性**：GitHub / HuggingFace 在国内可能慢或不可达；提供多个来源 + 手动导入兜底。镜像地址实现时核对，SHA-256 固定在 `AsrModelCatalog`，任何来源都必须校验通过。
12. **模型许可证**：sherpa-onnx 为 Apache-2.0（与 GPLv3 兼容）；SenseVoice 模型的许可证条款实现时核对原文，并在「关于」页注明来源与许可证。模型不随 APK 分发，由用户自行下载。
13. **SenseVoice 输出细节**：输出带语言 / 情感 / 事件标签（`<|zh|><|NEUTRAL|><|Speech|>` 等），需 `AsrTextPolicy` 清理；单段输入过长会变慢且可能降质，VAD 须限制最长片段。
14. **厂商错误码不透明**：各家额度 / 审核 / 配置错误的表达方式不同，且可能随版本变化；分类优先依据 HTTP 码与结构化字段，厂商码表集中在预设里，未知码按 HTTP 码兜底分类，错误信息原样截断展示给用户，保证至少「看得懂发生了什么」。
