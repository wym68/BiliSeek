## 0. 使用说明

### 0.1 判定规则

| 标记 | 含义 |
| --- | --- |
| ★ | **必过项**。不通过则该里程碑不算完成，不得进入下一个 |
| ☆ | 观察项。不通过可记录为已知问题，继续推进 |

**里程碑完成条件** = 本里程碑全部 ★ 通过 **且** §8 回归集全部通过。

### 0.2 验收项的写法约定

每条都是「**操作 → 可观察的结果**」，不是功能描述。

- ❌ 「实现了一键切看」——无法判定
- ✅ 「点『看』按钮 → 3 秒内出画面，且**声音不中断、进度不跳**」——可判定

**后半句才是真正的判据。** 出画面很容易，「声音不断、进度不跳」才能证明无缝切轨做对了。

### 0.3 记录方式

每次验收复制本文对应章节到 `docs/验收记录/M{n}-{日期}.md`，逐条勾选并附关键日志片段。失败项记录现象与诊断结论，不要只写「不通过」。

## 1. 验收环境准备

### 1.1 设备要求

| | 用途 | 要求 |
| --- | --- | --- |
| **主力机** | 日常验收 | Android 12+，性能中上 |
| **低端老机** | 分级降级验证 | Android 8.0–11，2–4 GB RAM |

**低端机不是可选项。** 要移植的 `BlurBudgetPolicy` / `MotionTier` 就是为低端设备做的降级策略，没有低端机无法验证它们是否生效；`c2.android.flac.decoder` 的输入缓冲问题也只在特定（多为老旧/低端）设备上暴露，新旗舰上永远撞不到。

**模拟器不能替代真机**：音频焦点、锁屏控制、蓝牙耳机切换、PiP、前台服务行为在模拟器上都不真实。

### 1.2 必装观测工具

**① `EventLogger`（Media3 自带，最重要）**

```kotlin
// 仅 debug 变体
if (BuildConfig.DEBUG) {
    player.addAnalyticsListener(androidx.media3.exoplayer.util.EventLogger())
}
```

它会打印轨道选择、格式切换、缓冲事件、位置不连续。**这是验证切轨是否真正生效的唯一可靠手段**——肉眼看到画面消失不能证明视频轨关了（可能只是 surface 没了，解码还在跑，那样省电省流量的目标并未达成）。

**② Chucker（应用内网络查看器，仅 debug 变体）**

直接在手机上翻请求与响应。验证风控三件套时比抓包方便得多，能立刻定位 `-352` / `-412` 出现在哪个请求上。

**③ debug 专用入口**

有些路径自然复现要等很久（Cookie 过期）或很难构造（凭据失效）。**在 debug 变体加一个隐藏调试面板**，提供：

- 强制触发 Cookie 刷新
- 手动损坏本地 SESSDATA
- 清空风控凭据（buvid / ticket / wbi）
- 强制切换网络策略判定结果

这几个开关会在 M1–M2 反复用到，早做早省事。

### 1.3 常用命令速查

```bash
# ── 前台服务状态（确认类型与存活）
adb shell dumpsys activity services | grep -A 8 PlaybackService

# ── MediaSession 注册状态（锁屏/通知栏控制的前提）
adb shell dumpsys media_session

# ── 播放器日志（EventLogger 输出）
adb logcat -s EventLogger:V PlaybackService:V

# ── 查应用 uid（流量统计要用）
adb shell dumpsys package com.biliseek | grep userId

# ── 流量统计（验证听模式是否真的不下视频）
adb shell dumpsys netstats detail | grep -A 12 "uid=<你的uid>"

# ── PiP 状态
adb shell dumpsys activity activities | grep -i -E "pip|picture"

# ── 唤醒锁（排查后台被杀/耗电）
adb shell dumpsys power | grep -i -A 5 wake

# ── 模拟进程被杀（验证续播与状态恢复）
adb shell am kill com.biliseek
```

## 2. M0 —— 打通最高风险链路

> **目标**：空工程 → 起 Service → MediaController 连接 → attach surface → 切一次视频轨。  
> **不接 B 站**，用公开 DASH 测试流，避免风控噪音干扰架构验证。

**测试流建议**：Media3 官方 demo 内置的 DASH 样例，或任意含独立音视频轨的公开 MPD。**必须是音视频分离的 DASH**，否则验不了切轨。

### A. Service 与连接

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **A-1** Service 起来且类型正确 | 启动 App 并开始播放 → `dumpsys activity services` 中能看到 `PlaybackService`，且 `foreground=true`、类型含 `mediaPlayback` |
| ★ | **A-2** MediaController 连接成功 | App 内点播放/暂停 → 播放状态随之改变；`dumpsys media_session` 中能看到活跃 session |
| ☆ | **A-3** fallback 通知生效 | 在主通知构建完成前触发前台服务启动 → 不崩溃，出现占位通知 |

**A-1 详细验收**：

```bash
adb shell dumpsys activity services | grep -A 8 PlaybackService
```
输出里要能看到 `isForeground=true`，且前台服务类型包含 `mediaPlayback`。若类型缺失，Android 14+ 会在某些场景直接抛异常。

### B. Surface 与切轨（M0 的全部意义）

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **B-1** 画面能渲染到指定区域 | `setVideoSurfaceView()` 后 → 画面出现在页面内指定区域，不是全屏 |
| ★ | **B-2** **视频轨真的被禁用** | 调用 `setTrackTypeDisabled(VIDEO, true)` → **EventLogger 日志显示视频轨状态变为未选中**，而不只是画面消失 |
| ★ | **B-3** **切轨无缝** | 启用视频轨 → 画面恢复，**音频不中断、进度连续** |
| ★ | **B-4** 关轨后不再下载视频数据 | 音频模式播放 5 分钟 vs 视频模式播放 5 分钟 → 流量差异显著 |

**B-2 详细验收**：

过滤 `adb logcat -s EventLogger:V`，在切轨前后各截一段。关轨后的 `Tracks` 输出中，video 组的 `selected` 应为 `false`（或该组整体不再被选中）。

> **为什么必须看日志**：`clearVideoSurface()` 也会让画面消失，但视频轨可能仍在选中状态、仍在下载和解码。那样耗电和流量一点没省，而这正是 BiliSeek「省流量」承诺的核心。**画面消失 ≠ 轨道禁用。**

**B-3 详细验收**（本项最严格，是无缝的硬判据）：

监听并记录两个信号：

1. **切换过程中不应出现 `STATE_BUFFERING`**。EventLogger 里若打出 buffering，说明播放器重新拉流了，不是无缝。
2. **不应出现 `onPositionDiscontinuity(reason = SEEK)`**。出现即说明做了 seek，不是无缝。

辅助判据：切换前后各记一次 `currentPosition`，差值应小于 1 秒且单调递增。

听感判据：戴耳机切换，**不应听到任何断点、爆音或重复片段**。

**B-4 详细验收**：

```bash
adb shell dumpsys package com.biliseek | grep userId    # 取 uid
adb shell dumpsys netstats detail | grep -A 12 "uid=<uid>"
```
分别在两种模式下播放同样时长，记录 rx 字节增量。视频模式应显著高于音频模式（量级差异，不是几个百分点）。

### C. 后台与锁屏

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **C-1** 后台音频继续 | 播放中按 Home 退到桌面 → 声音继续，通知栏出现媒体控制 |
| ★ | **C-2** 锁屏控制可用 | 锁屏 → 锁屏界面出现媒体控制，可暂停/继续 |
| ☆ | **C-3** 耳机控制 | 蓝牙耳机按暂停/下一首 → 响应正确 |
| ☆ | **C-4** 拔耳机自动暂停 | 播放中拔出有线耳机 / 断开蓝牙 → 自动暂停（`setHandleAudioBecomingNoisy(true)`） |

---

> ⚠️ **M0 的 B-2 与 B-3 是整个项目最不可逆的假设。**  
> 若不通过，说明「Service 持有 player + MediaController 转发」这条路走不通，需退回 BiliPai 的单例方案——越晚发现改动越大。**M0 必须第一个做。**

## 3. M1 —— 出声

> **目标**：接入 B 站。风控 gate 跑通 → 硬编码一个 BV → 取流 → MPD 组装 → 播出音频。  
> 此阶段**无 UI 可言**，一个按钮触发即可。

### A. 风控接入

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **A-1** 首次冷启动种植凭据 | 清除应用数据 → 启动 → Chucker 中能看到 `spi_v2` 与 `GenWebTicket` 两个请求，均成功 |
| ★ | **A-2** 凭据持久化 | 重启 App（不清数据）→ **不再重复请求** spi_v2 / GenWebTicket，直接放行 |
| ★ | **A-3** **gate 不阻塞 UI** | 断网启动 App → 界面正常渲染、输入框可输入可点击，**不白屏不 ANR** |
| ★ | **A-4** WBI 签名有效 | 触发一次带签名的请求 → 返回 `code: 0`，**不是 -412** |
| ☆ | **A-5** 凭据失效可恢复 | 用 debug 面板清空凭据 → 下次请求前自动重新种植 |

**A-3 详细验收**：这条容易被忽略但很重要。开飞行模式启动，界面必须完整可交互——请求可以失败，UI 不能等。若出现白屏或转圈卡住，说明 gate 被写成了阻塞式，违反架构文档 §3.1 的约束。

**A-4 失败诊断**：返回 `-412` 通常是签名参数集不对（漏参、多参、或编码方式不一致）；返回 `-352` 是风控拦截，检查 UA / Referer / bili_ticket 是否齐全。

### B. 取流与播放

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **B-1** playurl 解析成功 | 触发播放某 BV → 拿到 dash 数据，Chucker 中响应含 `dash.audio` 数组 |
| ★ | **B-2** **MPD 含双轨** | 打印组装出的 MPD → **同时含 audio 和 video 两个 `AdaptationSet`**，即使当前是听模式 |
| ★ | **B-3** 出声 | 触发播放 → **能听到声音**，进度条前进 |
| ★ | **B-4** 无缝切看（接真实流） | 重跑 M0 的 B-2 / B-3 判据，这次用 B 站真实流 |
| ★ | **B-5** URL 缓存生效 | 同一 BV 停止后再播 → Chucker 中**不再重复请求 playurl** |
| ☆ | **B-6** 降级链可用 | 构造 dash 缺失场景（或找一个老视频）→ 回退 durl 仍能播放 |

**B-2 详细验收**：这是无缝切看的地基，务必单独验。把组装好的 MPD 字符串打进日志，肉眼确认两个 `AdaptationSet` 都在。**若听模式下 MPD 只有 audio，无缝切看在 M2 必然失败**，且届时排查成本高得多。

**B-3 失败诊断**：有 dash 数据但没声音 → 优先检查请求头。B 站 CDN 校验 Referer，缺失直接 403。用 Chucker 看分片请求的响应码。

## 4. M2 —— 核心闭环

> **目标**：扫码登录 + Cookie 刷新 → 搜索 → 结果列表 → 播放 → 一键切看。  
> 这是「自己能日常用」的最小版本。

### A. 登录

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **A-1** 二维码生成与轮询 | 进登录页 → 出现二维码；手机 B 站扫码 → 状态变为「已扫描，待确认」 |
| ★ | **A-2** 登录成功取得凭据 | 确认登录 → 拿到 `SESSDATA` 与 `bili_jct` 并持久化 |
| ★ | **A-3** 二维码状态码处理 | 分别构造：未扫描 / 已扫未确认 / 二维码失效 → **三种状态 UI 提示各不相同**，失效时可刷新重出 |
| ★ | **A-4** **登录非强制** | 全新安装、不登录 → **仍可搜索、可播放** |
| ★ | **A-5** 登录态持久 | 重启 App → 仍是登录状态，无需重新扫码 |
| ☆ | **A-6** 登出干净 | 登出 → 凭据清除，回到未登录态，但 buvid 等风控凭据保留 |

**A-4 详细验收**：这是选型篇 §4.3 定的「登录非强制」。全新安装后直接搜索并播放，全程不应出现登录拦截。若被拦，说明某处把登录当成了前置条件。

### B. Cookie 刷新

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **B-1** 刷新流程跑通 | debug 面板触发强制刷新 → 五步全部成功，拿到新 Cookie |
| ★ | **B-2** 失效自动恢复 | debug 面板损坏本地 SESSDATA → 下次请求收到 `-101` → **自动刷新并重试一次成功**，用户无感 |
| ★ | **B-3** **`-352` 不重试** | 构造或等到一次 `-352` → **日志显示未发起重试**，进入退避 |

**B-3 详细验收**：这是架构文档 §3.2 特别标注的「做错会主动伤害用户账号」的点。检查日志，收到 `-352` 后不应有紧接着的同一请求重发。若难以自然构造，可在 debug 变体注入一个假的 `-352` 响应来验证代码路径。

### C. 搜索与播放闭环

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **C-1** 关键词搜索 | 输入关键词 → 出结果列表，含标题/封面/UP/时长 |
| ★ | **C-2** 分页加载 | 滑到底 → 自动加载下一页，无重复无跳跃 |
| ★ | **C-3** 点击即播 | 点任一结果 → 开始播放音频 |
| ★ | **C-4** **一键切看** | 播放中点「看」→ 出画面，**声音不断、进度不跳**（判据同 M0 B-3） |
| ★ | **C-5** 退回听 | 点「听」→ 画面消失，**EventLogger 确认视频轨禁用**，音频继续 |
| ★ | **C-6** 多 P 折叠 | 搜索到一个多 P 视频 → 结果列表中**只占一条**；点入后展开为列表 |
| ☆ | **C-7** 链接直达 | 粘贴 BV 号 / b23.tv 短链 → 直接解析跳转，不走关键词搜索 |

## 5. M3 —— 骨架成型

> **目标**：三入口导航 + MiniPlayer 持久容器 + 本地歌单 + 首页空状态 + design-system 移植。

### A. 导航与持久播放器（本里程碑的核心）

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **A-1** **跨页面播放不中断** | 播放中切换底部三个 tab → **声音不中断，MiniPlayer 始终可见** |
| ★ | **A-2** MiniPlayer 展开 | 上滑 MiniPlayer → 展开为播放页；下滑 → 收回 |
| ★ | **A-3** **展开不入导航栈** | 播放页展开状态下按系统返回键 → **收回 MiniPlayer，而不是退出当前页面** |
| ★ | **A-4** 原地展开看视频 | 播放页内点「看」→ **封面区原地变为视频**，页面不跳转 |
| ★ | **A-5** 上滑进全屏 | 视频区上滑 → 进全屏；返回/下滑 → 回到内联 |
| ★ | **A-6** **全屏退出无残留** | 全屏 → 退出 → **底部导航选中态、列表滚动位置均未改变** |

**A-1 详细验收**：这是「MiniPlayer 挂在 NavHost 之外」的直接检验。播放中反复切 tab 十次，声音必须连续无一次中断。若有中断，说明 MiniPlayer 被卷进了导航重组。

**A-6 详细验收**：进全屏前记下当前 tab 与列表滚动位置，退出后逐一核对。若被污染，说明走了「Scaffold 内部逐个隐元素」那条路，需改为顶层 overlay（架构文档 §7.2）。

### B. 首页与库

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **B-1** 首页不空屏 | 全新安装首次打开 → 有搜索框 + 引导内容，**不是纯空白** |
| ★ | **B-2** 搜索历史 | 搜索若干次 → 首页出现历史，**上限 10 条**，可单条删除与清空 |
| ★ | **B-3** 最近播放 | 播放若干条目后回首页 → 出现最近播放入口 |
| ★ | **B-4** 本地歌单增删改 | 新建歌单 → 加入条目 → 重排 → 删除 → 全部生效且重启后保留 |
| ★ | **B-5** 数据库迁移可用 | 构造一次 schema 变更并跑迁移 → 旧数据完整保留 |
| ☆ | **B-6** 播放热力图 | 有播放历史后 → 热力图正确反映日期分布 |

**B-5 详细验收**：不要等真正需要迁移时才验。M3 阶段主动写一个无意义的迁移（如加一个可空字段）跑通全流程，确认迁移机制可用。**这是一次性投入，能避免后期数据丢失事故。**

### C. 视觉体系

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **C-1** 莫奈动态取色 | 更换系统壁纸 → App 主色随之变化 |
| ★ | **C-2** 深浅色跟随 | 切换系统深浅色 → App 正确响应，无残留错色 |
| ★ | **C-3** **低端机降级生效** | 在低端机上运行 → **模糊与动效自动降级**，界面不卡顿 |
| ☆ | **C-4** 大字体/无障碍 | 系统字体放到最大 → 布局不破版、不截断关键信息 |

**C-3 详细验收**：这条必须在低端机上做。对比两台设备的同一界面，低端机上模糊强度应明显更低或直接关闭，动效更简。若两台表现一致，说明 `BlurBudgetPolicy` / `MotionTier` 没接上或判定阈值不起作用。

## 6. M4 —— MVP 收尾

> **目标**：后台/锁屏回落、PiP 判定、播放队列、续播。

### A. 模式自动回落（不变式的实地检验）

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **A-1** 进后台回落音频 | 看模式中按 Home → **EventLogger 确认视频轨禁用**，音频继续 |
| ★ | **A-2** 锁屏回落音频 | 看模式中锁屏 → 同上 |
| ★ | **A-3** **PiP 不回落** | 看模式中触发 PiP → **视频轨仍启用**，PiP 窗口有画面 |
| ★ | **A-4** 回前台恢复画面 | 从后台返回 → 画面恢复，**音频时间线连续、无重复片段** |
| ★ | **A-5** PiP 返回内联 | 从 PiP 点回 App → 回到内联看模式，画面连续 |
| ☆ | **A-6** 流量策略 | 开启「仅 Wi-Fi 看视频」→ 切到移动网络 → 自动回落音频并提示 |

**A-3 详细验收**：这是架构文档 §5.2 双维度状态机的关键检验。进 PiP 后 EventLogger 中视频轨必须**仍为选中**。若被禁用，说明「进后台」的判定没有正确区分 `PresentationMode == NONE` 与 `== PIP`，PiP 窗口会变黑。

**A-4 详细验收**：戴耳机验证。回前台时**不应听到约 2 秒的重复片段**——那是架构文档 §5.3 序列③ 记录的坑：回前台时若做了 seek，Media3 可能回退到前一个音频同步点。听到重复即说明代码里有多余的 seek。

### B. 队列与续播

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **B-1** 顺序播放 | 播放歌单 → 一条结束自动播下一条 |
| ★ | **B-2** 上一首/下一首 | 通知栏与锁屏的上/下一首均生效 |
| ★ | **B-3** 播放模式 | 单曲循环 / 列表循环 / 随机 → 行为符合预期 |
| ★ | **B-4** **进程被杀后续播** | `adb shell am kill` → 重开 App → **恢复到上次的条目与位置** |
| ☆ | **B-5** 队列可见可调 | 打开播放队列 → 可查看、可拖动重排、可移除 |

**B-4 详细验收**：用 `adb shell am kill com.biliseek` 而不是从最近任务划掉——后者在部分 ROM 上等同于正常退出，验不出真实的进程重建场景。

### C. 稳定性

| | 项 | 操作 → 预期 |
| --- | --- | --- |
| ★ | **C-1** 长时间播放 | 连续播放 1 小时 → 无崩溃、无内存持续增长、音频无中断 |
| ★ | **C-2** 弱网表现 | 限速或反复切换网络 → 能重连续播，不永久卡死 |
| ☆ | **C-3** 低端机内存 | 低端机上播放 30 分钟并频繁切页 → 不被系统杀掉 |

## 7. 回归验收集

> 每个里程碑完成时，除本里程碑清单外，**必须重跑以下项**。这些是最容易被后续改动打破的地方。

| | 来源 | 项 |
| --- | --- | --- |
| ★ | M0 B-2 | 视频轨确实被禁用（看日志，不看画面） |
| ★ | M0 B-3 | 切轨无缝：无 buffering、无 seek 不连续 |
| ★ | M0 C-1/C-2 | 后台播放 + 锁屏控制 |
| ★ | M1 A-3 | gate 不阻塞 UI（断网启动仍可交互） |
| ★ | M2 A-4 | 登录非强制（不登录仍可搜索播放） |
| ★ | M2 B-3 | `-352` 不重试 |
| ★ | M3 A-1 | 跨页面播放不中断 |

**为什么是这七条**：它们各自对应一个架构级承诺——省流量、无缝、后台可听、不阻塞、不强制登录、不伤账号、播放连续。任何一条被打破，都不是「一个 bug」，而是产品身份或架构假设出了问题。

## 8. 自动化覆盖范围（诚实边界）

**能自动化的：**

| 层 | 覆盖内容 | 速度 |
| --- | --- | --- |
| JVM 单测 | 所有 `*Policy` 纯函数：轨道选择、音质回退、状态迁移判定、重试策略 | 秒级 |
| 仪器化测试 | Room 迁移、DataStore 读写、**MediaController 能否连上 Service** | 分钟级 |

> **移植 BiliPai 代码时把测试一起搬。** 它几乎每个 `*Policy.kt` 旁边都有 `*PolicyTest.kt`，`design-system` 的 148 个文件里 59 个是测试。只拿实现不拿测试，等于把免费的回归网扔掉。

**无法自动化的（本清单存在的理由）：**

声音是否真的出来、切换是否听感无缝、画面是否及时、锁屏控制是否可用、低端机是否卡顿——**这些只能人工验收**。不要指望测试覆盖率能代表这个项目的质量，播放器类应用的质量主要由手工验收保证。

## 附录：常见失败诊断

| 现象 | 优先排查 |
| --- | --- |
| 有 dash 数据但没声音 | 请求头缺 Referer / UA（CDN 返回 403） |
| 接口返回 `-412` | WBI 签名参数集不对：漏参、多参、编码方式不一致 |
| 接口返回 `-352` | 风控：检查 UA / Referer / bili_ticket 是否齐全；**不要重试** |
| 切看时声音断一下 | 播放源被重建了。检查是否走了 seek 或 prepare，而非 `setTrackTypeDisabled` |
| 回前台听到约 2 秒重复 | 恢复画面时做了多余的 seek，去掉（架构文档 §5.3 序列③） |
| 关了画面但流量照跑 | 只 `clearVideoSurface()` 没禁用视频轨。看 EventLogger 确认轨道状态 |
| PiP 窗口黑屏 | 「进后台」判定误伤了 PiP。检查是否区分 `PresentationMode == NONE` 与 `== PIP` |
| Android 14+ 启动即崩 | 前台服务类型未声明 `mediaPlayback`，或通知构建超时未走 fallback |
| 低端机与旗舰表现一致 | `BlurBudgetPolicy` / `MotionTier` 未接上或阈值失效 |
| 切 tab 声音中断 | MiniPlayer 被卷进了 NavHost 重组，需挂到 NavHost 之外 |
