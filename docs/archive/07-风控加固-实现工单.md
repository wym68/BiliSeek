## 0. 现状与问题

当前 BiliSeek 的"设备身份"过于单薄、且全量共享：

| 问题 | 位置 | 后果 |
|------|------|------|
| **激活指纹静态硬编码**（分辨率 `1177x2094`、webgl/canvas 全固定） | `core/network/internal/BuvidActivation.kt:13` | 所有安装共享同一份指纹 → 易被聚类、整批标记，抬高 `-352`、降低 buvid 可信度 |
| **只种 3 个风控 cookie**（`buvid3/buvid4/bili_ticket`） | `Interceptors.kt:63` | 缺 `b_nut/_uuid/buvid_fp/b_lsid`——真实浏览器必带，缺了就"不像浏览器" |

## 3. 任务分解

### B1 — 激活指纹随机化 + per-install 稳定

**思路**：开机首次生成一份"看起来像一台真实 Windows Chrome 桌面机"的指纹档案，落库；此后每次激活/请求都复用同一份。随机性体现在**安装之间**不同（打散聚类），而非**每次请求**变（那反而异常）。

### B3 — 全局节流 + 风控冷却

**冷却**（撞墙后主动闭嘴，`-352` 绝不硬顶）：

`CooldownPolicy.kt`（新增，纯函数，把 `nextBackoffMs` 提升到全局）：

```kotlin
package com.biliseek.core.network.internal

/** 连续第 n 次(0基)风控后应冷却多久。指数退避 + 上限。 */
fun riskCooldownMs(consecutiveHits: Int, baseMs: Long = 60_000, maxMs: Long = 30 * 60_000): Long {
    if (consecutiveHits <= 0) return 0
    var d = baseMs
    repeat(consecutiveHits - 1) { d = (d * 2).coerceAtMost(maxMs) }
    return d.coerceAtMost(maxMs)
}
```

`RiskCooldown.kt`（新增，进程级单例状态）：

```kotlin
internal class RiskCooldown {
    private val _cooldownUntil = kotlinx.coroutines.flow.MutableStateFlow(0L)
    val cooldownUntil: kotlinx.coroutines.flow.StateFlow<Long> = _cooldownUntil
    private var consecutive = 0

    /** 收到 -352 调用：累加并延长冷却。 */
    @Synchronized fun onRiskControl(now: Long = System.currentTimeMillis()) {
        consecutive++
        _cooldownUntil.value = now + riskCooldownMs(consecutive)
    }
    /** 任意成功调用：清零。 */
    @Synchronized fun onSuccess() { consecutive = 0; _cooldownUntil.value = 0 }
    /** 请求前检查：处于冷却期返回剩余 ms（>0 表示应拒发）。 */
    fun remaining(now: Long = System.currentTimeMillis()): Long = (_cooldownUntil.value - now).coerceAtLeast(0)
}
```

**限速**（连发降噪）：

`RequestThrottle.kt`（新增）——按类别（`SEARCH`/`WRITE`/`FEED`）串行化 + 最小间隔 + jitter：

```kotlin
internal class RequestThrottle {
    private val mutexes = ConcurrentHashMap<String, Mutex>()
    private val lastAt = ConcurrentHashMap<String, Long>()
    suspend fun <T> gate(bucket: String, minIntervalMs: Long, jitterMs: Long, block: suspend () -> T): T =
        mutexes.getOrPut(bucket) { Mutex() }.withLock {
            val wait = (lastAt[bucket]?.plus(minIntervalMs) ?: 0) - System.currentTimeMillis()
            if (wait > 0) delay(wait + Random.nextLong(jitterMs))
            try { block() } finally { lastAt[bucket] = System.currentTimeMillis() }
        }
}
```

**接入**（`BiliRepository`）：`wbiRequest`（`:418`）与 `writeRequest`（Phase A）在发请求前：

```kotlin
riskCooldown.remaining().takeIf { it > 0 }?.let {
    throw /* SearchException(Blocked) 或 WriteException(WriteError.Blocked) */
}
return requestThrottle.gate(bucket, minInterval, jitter) { /* 原请求 */ }
```

并在响应分流处：`-352 → riskCooldown.onRiskControl()`；`code==0 → riskCooldown.onSuccess()`。`RiskCooldown`/`RequestThrottle` 由 `BiliNetwork` 单例持有并注入 `repository`/`authGate`。

- 验证：`CooldownPolicyTest`（退避序列、上限、清零）；`RiskCooldownTest`（连击延长、成功清零、`remaining` 计算，注入固定 now）；`RequestThrottleTest`（虚拟时钟下最小间隔生效、并发同 bucket 串行）。
- **注意**：冷却/限速一律用**注入的时钟/随机**，测试不得真 `delay` 挂钟表、不得联网。

### B4 — 真实登录 cookie 优先

**思路**：已登录用户，B 站登录响应的 `Set-Cookie` 里带了真实 `buvid3/buvid4/buvid_fp/b_nut`——可信度远高于自种。采信它们、并**跳过 `ExClimbWuzhi` 自激活**。

`CredentialSourcePolicy.kt`（新增，纯函数）：

```kotlin
enum class CredentialSource { REAL_LOGIN, SELF_SEEDED }

/** 有登录带回的完整 buvid 系 → 采信真登录；否则自种。 */
fun resolveCredentialSource(loginBuvid3: String?, loginBuvidFp: String?): CredentialSource =
    if (!loginBuvid3.isNullOrBlank() && !loginBuvidFp.isNullOrBlank())
        CredentialSource.REAL_LOGIN else CredentialSource.SELF_SEEDED
```

`LoginManager.kt`（改）：`parseSessionFromCookies`（`:136`）除 `SESSDATA/bili_jct/DedeUserID` 外，一并 `pick("buvid3"/"buvid4"/"buvid_fp"/"b_nut")`，回给 `AuthGate` 覆盖凭据并标 `source=REAL_LOGIN`。`BiliCredentials` 加 `source` 字段。登出时：真登录来源的 buvid 随账号一起清（因为它绑账号），自种的保留（设备身份，重种更像异常——保持现有《架构设计篇》§3.1 注释精神）。

- 验证：`CredentialSourcePolicyTest`；`LoginManagerTest` 扩充——mock `Set-Cookie` 含 buvid 系 → 会话与凭据都被填充。
- ⚠️ 端到端需真人扫码（登录完成态历史上未跑通，见《MVP 收尾总结》§5），标「未验证」。

## 5. 风险与未决

1. **指纹算法漂移**（B2 最大风险）：`_uuid`/`buvid_fp` 算法上游可能调整；集中在 `FingerprintCookies.kt`，改动面收敛。取不到证据就**宁缺毋错**。
2. **冷却误伤**（B3）：`riskCooldownMs` 基数/上限需真机调参；初值 1min→30min 上限是保守猜测，验收时校准。
3. **限速影响体感**（B3）：搜索联想的 `minInterval` 太大伤手感、太小没效果；`SEARCH` bucket 单独调。
4. **登录 cookie 可信度**（B4）：若登录响应未带全 buvid 系（不同登录方式差异），`resolveCredentialSource` 回落自种——需覆盖扫码/短信/cookie 导入三种。
5. **转发字段结构**（B6）：`create/dyn` 的 JSON body 结构复杂且易变，以当日抓包为准，先只做"纯文字转发"最小集。
