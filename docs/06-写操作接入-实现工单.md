## 0. 背景与根因

`-111 = csrf 校验失败`，**不是 `-352` 风控**（`ref/bilipai/.../ResultExtensions.kt:85` 定义 `CSRF_ERROR = -111`）。B 站对所有写操作（POST）校验：请求 **body 里的 `csrf` 字段**必须等于 `bili_jct` cookie，且与 `SESSDATA` 同属一个登录态。

当前 BiliSeek：

- `BiliCookieJar.loadForRequest()`（`core/network/internal/Interceptors.kt:49`）只把 `bili_jct` 当 **cookie** 注入；
- **没有任何地方把 `csrf` 写进 POST body**——所以只要按现有 GET 写法加写接口，必 `-111`；
- `resolveRetryAction`（`core/network/internal/RetryPolicy.kt:25`）只覆盖 `-101 / -352 / -412`，`-111` 落进泛化 `FAIL`，无自愈。

两个参考项目的做法印证了修法：

- **bbplayer** `postWithCsrf`（`ref/bbplayer/apps/mobile/src/lib/api/bilibili/client.ts:264`）：统一从 `bili_jct` cookie 取值塞进 body 的 `csrf`，所有写接口都走它；重复动作码（`65006` 已点赞）当成功（`api.ts:1094`）。
- **bilipai**：每个写接口显式 `@Field("csrf")`（`ref/bilipai/.../ApiClient.kt:339/999/1127`）；WBI 接口省略 Referer（`:2943`）；bvid 请求带视频页 Referer（`:2841`）。

**本工单核心保证**：`csrf` 只在 `writeRequest` 一处注入 + 写接口只收 `@FieldMap` ⇒ 调用点物理上无法遗漏 `csrf`（对齐 CLAUDE.md「enforced structurally so it can't be violated」）。

### T1 — `WritePolicy.kt`（纯函数，先做，可独立单测）

```kotlin
package com.biliseek.core.network.internal

/** 写操作（点赞/投币/收藏/评论/弹幕）的错误码处置。纯函数、无副作用、可单测。 */
sealed interface WriteOutcome {
    data object Success : WriteOutcome            // code == 0
    data object AlreadyDone : WriteOutcome        // 幂等：重复点赞/已收藏，业务等价成功
    data object CsrfInvalid : WriteOutcome        // -111
    data object NeedLogin : WriteOutcome          // -101
    data object Blocked : WriteOutcome            // -352，绝不重试
    data object ReseedCredentials : WriteOutcome  // -412
    data class  Failed(val code: Int) : WriteOutcome
}

/**
 * @param idempotentCodes 该操作视为成功的「重复动作」码。
 *        故意做成入参而非全局常量：65006 对点赞是成功，
 *        同一个码对另一接口未必——绝不能一刀切。
 */
fun resolveWriteOutcome(code: Int, idempotentCodes: Set<Int> = emptySet()): WriteOutcome = when {
    code == 0               -> WriteOutcome.Success
    code in idempotentCodes -> WriteOutcome.AlreadyDone
    code == -111            -> WriteOutcome.CsrfInvalid
    code == -101            -> WriteOutcome.NeedLogin
    code == -352            -> WriteOutcome.Blocked
    code == -412            -> WriteOutcome.ReseedCredentials
    else                    -> WriteOutcome.Failed(code)
}

/** 各操作的幂等成功码。TODO 标记项需真人验收实测补全（不得联网自测——AGENTS.md）。 */
object IdempotentCodes {
    val LIKE   = setOf(65006)     // 重复点赞（源自 bbplayer api.ts:1094，已确认）
    val COIN   = emptySet<Int>()  // TODO 验收补：如「已投币」码
    val FAV    = emptySet<Int>()  // deal 接口 add/del 同体，一般无需
    val FOLLOW = emptySet<Int>()  // TODO 验收补：如「已关注」码
}
```

- **不动** `RetryPolicy.kt:resolveRetryAction`——读路径已验收，写路径走独立函数避免回归。

helper（与读路径 `wbiRequest` 对称，`BiliRepository.kt:418`）：

```kotlin
/**
 * 写操作统一入口：注入 csrf(=bili_jct) 到 body、就绪风控三件套、统一错误分流。
 *
 * 与 [wbiRequest] 对称，两点不同：
 *  1. csrf 在此**唯一**注入——调用点无法遗漏，结构性杜绝 -111。
 *  2. 成功不要求 data 非空——写接口成功常返回空 data。
 */
private suspend fun <T> writeRequest(
    payload: Map<String, String>,
    idempotentCodes: Set<Int> = emptySet(),
    referer: String? = null,
    block: suspend (fields: Map<String, String>, referer: String?) -> BiliResponse<T>,
): Result<T?> = runCatching {
    val session = sessionStore.current
    if (!session.isLoggedIn || session.biliJct.isBlank()) {
        throw WriteException(WriteError.NeedLogin, "写操作需要登录")
    }
    // 保证 buvid/ticket/WBI 就绪，降低 -352（写操作同样吃风控三件套）
    try { authGate.awaitReady() } catch (e: Exception) {
        throw WriteException(WriteError.Network(e.message.orEmpty()), e.message ?: "风控凭据不可用")
    }

    suspend fun fire(csrf: String) = try {
        block(payload + ("csrf" to csrf), referer)
    } catch (e: java.io.IOException) {
        throw WriteException(WriteError.Network(e.message.orEmpty()), e.message ?: "网络不可达")
    }

    var response = fire(session.biliJct)

    // -111：登录态可能 jct 轮换 → 刷新一次后再打一次（仅一次，绝不循环）
    if (resolveWriteOutcome(response.code, idempotentCodes) is WriteOutcome.CsrfInvalid) {
        if (cookieRefresher.refreshIfNeeded() is RefreshOutcome.Refreshed) {
            response = fire(sessionStore.current.biliJct)
        }
    }

    when (val outcome = resolveWriteOutcome(response.code, idempotentCodes)) {
        WriteOutcome.Success, WriteOutcome.AlreadyDone -> response.data
        WriteOutcome.CsrfInvalid ->
            throw WriteException(WriteError.CsrfInvalid, "csrf 校验失败(-111)，请重新登录")
        WriteOutcome.NeedLogin ->
            throw WriteException(WriteError.NeedLogin, "未登录(-101)")
        WriteOutcome.Blocked ->
            throw WriteException(WriteError.Blocked, "触发风控(-352)，已进入退避")
        WriteOutcome.ReseedCredentials -> {
            authGate.invalidate()
            throw WriteException(WriteError.CredentialsInvalid, "请求被拦截(-412)，已重置设备凭据")
        }
        is WriteOutcome.Failed ->
            throw WriteException(
                WriteError.Unknown(outcome.code, response.message),
                "操作失败：code=${outcome.code} ${response.message}",
            )
    }
}
```

### T7 — `HeaderInterceptor` 尊重已设 Referer（`Interceptors.kt:22`）

现状无条件覆盖 Referer/Origin，会盖掉写请求的 `@Header("Referer")`。改成「缺则补」（对齐 bilipai `ApiClient.kt:2944` 的 `explicitReferer` 判断）：

```kotlin
override fun intercept(chain: Interceptor.Chain): Response {
    val req = chain.request()
    val b = req.newBuilder().header("User-Agent", BILI_USER_AGENT)
    if (req.header("Referer").isNullOrBlank()) b.header("Referer", "$BILI_ORIGIN/")
    if (req.header("Origin").isNullOrBlank())  b.header("Origin", BILI_ORIGIN)
    return chain.proceed(b.build())
}
```

- 对现有读请求**行为不变**（它们不带 Referer，仍补 www）。这是本工单唯一动到读路径共享代码处，需在回归里带上搜索/播放冒烟。

## 6. 风险与未决

1. **`-111` 刷新重试的有效性**：`CookieRefresher.refreshIfNeeded()` 仅在服务端 `refresh==true` 时真正换新 jct；纯 csrf 拼错的场景本工单已由「结构性注入」根治，刷新重试只兜底 jct 轮换这一少数情况。若真机发现 `-111` 仍偶发，需单独排查 SESSDATA/jct 一致性。
2. **Referer 覆盖改动**：T7 动到读路径共享的 `HeaderInterceptor`，回归必须带搜索 + 播放冒烟，确认 CDN 仍返 200（Referer 校验见《架构设计篇》§3.2）。
3. **转发（create/dyn）**：明确不在本工单；其 WBI+JSON 形态需 helper 扩展，Phase C 另开工单。
4. **幂等码不全**：`COIN/FOLLOW` 留空上线，首轮真机可能把「已投币/已关注」误报为失败——验收时优先补齐。
