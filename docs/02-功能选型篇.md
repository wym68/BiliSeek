## 1. 项目概述

**BiliSeek** —— 一个搜索驱动、默认只听、可按需看视频、没有推荐首页的第三方哔哩哔哩 Android 客户端。

**Slogan：** Seek and you shall find.（寻则得之）

### 背景

桌面端 biu 证明了一种干净的使用方式：打开即搜索、把 B 站当音频库来听，**没有视频信息流推荐**。但在 Android 上，这个定位存在一个空位：

- 纯音频播放器（BBPlayer、BiliSound、AzusaPlayer）体验干净、无推荐，但**只能听、不能看视频**；
- 完整第三方客户端（BiliPai、bilimiao、PiliPlus）能全站搜索、能看能听，但**都带推荐首页**、以视频浏览为中心。

BiliSeek 要填的正是二者之间的空位：**以「听」为默认、以「搜索」为入口、去掉推荐，同时保留「想看画面时一键切换」的能力，以及其他一些完整第三方客户端需要保留的功能或特性。**

> 措辞校订：biu 实际带有一个音乐推荐页（新歌 / 榜单 / 分区推荐，见 `src/pages/music-recommend/`），它没有的是**视频信息流**。这里需要区分两类东西——**算法个性化信息流**违背 BiliSeek 身份，坚决不做；**全站统一的非个性化榜单**不违背身份，但也不在当前规划内。

### 核心身份（四条差异点）

1. **全站关键词搜索** —— 打开就是搜索框，搜遍全 B 站视频，不限音乐区。
2. **默认只听** —— 默认只**解码/下载**音频流，锁屏/后台可听，省流量（视频轨被禁用，不消耗流量）。
3. **可切看视频** —— 单条内容上一个按钮即可切到看模式；看完可退回纯音频。
4. **没有推荐** —— 没有首页信息流，入口只有搜索 + 你自己的歌单/库 + 你自己的行为记录（搜索历史 / 最近播放）。

> 命名说明：`seek` 一语双关，既是「搜索」，也是播放器进度条的 `seek`，音频/视频通用。

## 2. 产品目标与非目标

### 目标（要做）

- 对标 biu 的核心：搜索即听、歌单/库、收藏夹同步、**音质择优**。
- 参考 BiliPai 和 BBPlayer 项目，补上 biu 没有的：默认听。
- 保持轻量、纯净、无广告、原生手感、**纯本地无后端**。

> 「无损优先」措辞校订：Hi-Res FLAC（音质 ID `30251`）与杜比（`30250`）在 playurl 里是独立字段（`dash.flac` / `dash.dolby`），且**需要大会员**。非会员实际天花板是 192K AAC。因此对外表述应为「**有则用、无则优雅回退到最高可用码率**」，不要把无损当成用户可感知的卖点。

> 「无后端」是一条**主动约束**：BBPlayer 有自建 Cloudflare Worker 后端（歌单分享 / 统计上报 / 更新检查），因此需要单独写隐私政策并承担成本与可用性。BiliSeek 不引入服务端，这是「轻量、纯净」定位的一部分。

### 非目标（明确不做，用来守住定位）

- **不做推荐 / 首页信息流。** 这是与完整客户端最根本的区别。
- **不做视频优先的浏览体验。** 视频是「按需切入」，不是浏览主线。
- **不做番剧 / 直播** 作为主线功能（至少 MVP~P2 阶段不做）。
- **视频下载：修订为「做」。**（原「不做」已定案，2026-08-28 修订）M9 起支持，作为「音频下载」的并列选项，下载时二选一、默认仍是听。定位不变：视频依旧是「按需切入」，不因此变成浏览主线。
- **不做收藏夹反向同步**（本地歌单写回 B 站）。（已定案）写操作会增加账号风控暴露面，与「防止账号被限制」的原则冲突。收藏夹只做单向拉取。
- **不做服务端。** 所有数据留在本地。

> 补充说明：**音频下载与视频下载的成本不对等，但视频下载无需转码。** DASH 音频流本身就是 M4A/AAC（或 FLAC），下载即完整文件；视频下载则是把音频轨 + 视频轨合成 MP4——用 Android 自带的 `MediaMuxer` 只做封装、不重编码，无需像 biu 那样打包 ffmpeg。所以「音频 / 视频」两种下载并存，成本上仍是可控切分，不破坏「轻量、无原生代码」的约束。

### 注意事项

- **采用尽可能安全的 b 站账号登录方式，防止账号被官方限制。** 已落实为：MVP **仅 Web 扫码**登录（不碰密码、不过极验、不冒用官方 appkey），并完整实现风控接入三件套（见 4.1）。

### 授权决策（重要）

- **本项目整体采用 `GPLv3` 开源。** 一旦复用 BiliPai 的代码（GPLv3 具传染性/copyleft），派生作品必须同为 GPLv3。
- **MIT 与 GPLv3 单向兼容**：可将 BBPlayer 的代码/资源并入，合并后整体按 GPLv3 发布，被并入的 MIT 部分保留其原始许可与版权声明即可。
- ⚠️ **PolyForm Noncommercial 不是开源许可证**，它限制商业用途，不满足开源定义（OSD），**与 GPLv3 不兼容**（GPLv3 禁止附加使用限制）。因此 biu 的源码、资源、图标一律不可复制，也不可「改写后并入」（衍生作品同样受限）。可以阅读学习其**思路与产品设计**——想法与架构模式不受版权保护。

## 4. 功能选型总表（核心）

**取用方式**分三类：

- **直接复用**：摘取现成 Kotlin 代码改造后使用。来源可为 BiliPai（GPLv3）或 BBPlayer 的 `orpheus` 模块（MIT），两者均合法。
- **参考重写**：读实现思路，在 Kotlin 中自行重写（主要针对 BBPlayer 的 TS 侧与 biu）。
- **自研**：三个项目都没有，BiliSeek 原创。

**优先级**：`MVP`（首个可用闭环）＞ `P1`（重要增强）＞ `P2`（锦上添花）＞ `待定`。

### 4.1 播放内核与网络接入（主要取自 BiliPai）

| 功能 | 取用方式 | 优先级 | 说明 |
| --- | --- | --- | --- |
| 风控接入三件套：buvid + bili_ticket + WBI 签名 | 直接复用 | MVP | **一切的前提**，缺失则搜索 -412、播放 -352。冷启动两步：① `spi_v2` 取 buvid3/4 ② `GenWebTicket` 取 bili_ticket（**顺带返回 WBI 密钥**，可省一次 nav 请求） |
| buvid3 获取策略 | 直接复用 + 改 | MVP | **优先调 `spi_v2` 由服务端下发**（biu 思路），失败才回退本地生成。BiliPai 的本地 `UUID+"infoc"` 生成法与真实 buvid 分布有差异，更易被风控识别 |
| DASH 音视频分离解析与取流 | 直接复用 | MVP | 听模式只**下载**音频轨，但**解析时保留完整音视频信息**（无缝切看的前提）。`fnval=4048`、`fnver=0`、`fourk=1`、`voice_balance=1` |
| 本地 DASH manifest（MPD）拼装 | 直接复用 | MVP | B 站返回 DASH JSON 而非标准 MPD，需自行拼装后喂给 Media3。**manifest 必须同时含音、视频两个 AdaptationSet**，否则无法无缝切看。注意 URL 内 `&` 必须转义 |
| 取流降级链 | 直接复用 | MVP | `dash` 缺失时回退 `durl`（单文件 MP4）；再不行走 `platform=html5 + high_quality=1`（不需登录也能到 1080p，但无高码率音频） |
| 听视频模式 / 纯音频播放 | 直接复用 | MVP | BiliSeek 的**默认**播放模式 |
| 音视频**无缝**切换（听 ⇄ 看） | 直接复用 | MVP | 「一键切看」的底层机制，**已定为无缝**：同一 player、同一 MediaSource，靠 `setTrackTypeDisabled(C.TRACK_TYPE_VIDEO, true) + setMaxVideoSize(0, 0)` 开关视频轨，不重建、不 seek、位置不丢。配套还需处理 surface 挂/摘与回前台的画面恢复 |
| 后台播放 / 系统媒体控制 | 直接复用 | MVP | `MediaSessionService` + `FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK`，含拿不到主通知时的 fallback 通知（防 Android 14+ 前台服务超时崩溃） |
| B 站登录 —— **仅 Web 扫码**（含风控处理） | 直接复用 | MVP | **已定为 Web 扫码**（`passport-login/web/qrcode/generate` + `/poll`），拿 Cookie（`SESSDATA` / `bili_jct` / `DedeUserID`），不碰密码、不过极验。**不用 TV 扫码**——理由见下方说明 |
| **登录态续期 / Cookie 刷新** | 直接复用 | MVP | **新增项**。不做则用户周期性掉登录，严重伤害「打开即用」。⚠️ **Web 端刷新流程比想象中繁琐**：查询是否需刷新 → **用 RSA-OAEP 算出 `correspondPath`** → 请求 `www.bilibili.com/correspond/1/{path}` 这个 HTML 页面**解析出 `refresh_csrf`** → 换新 Cookie → 作废旧凭证。工作量需在排期里单列，别按「一个接口」估 |
| 短信 / 密码登录 | 直接复用 | 待定 | 需过极验验证码，成本与风控风险都高；扫码已覆盖需求，暂不做 |
| 请求头策略（Referer / Origin / UA） | 直接复用 | MVP | **播放与下载请求同样要带**，B 站 CDN 校验 Referer，不带即 403 |
| 网络策略 / CDN 选线 | 直接复用 | MVP | 稳定取流的基础。注意 BiliPai 的 `network-core` 模块**只有 3 个策略类**，真正的网络层在 `app/core/network/` |
| 音质 / 音频流选择（Hi-Res FLAC、Dolby 判断） | 直接复用 | P1 | 三个独立来源：`dash.audio`（AAC 数组）、`dash.dolby.audio`、`dash.flac.audio`。含回退原因分类（不可用 / 倍速不兼容 / 无可播放音频） |
| Hi-Res FLAC 解码兼容 | 直接复用 | P1 | 部分设备给 `c2.android.flac.decoder` 只分配 32 KiB 输入缓冲，B 站 Hi-Res 单帧会超，触发 `InsufficientCapacityException`。需自定义 RenderersFactory 抬到 1 MiB |
| 倍速与高音质的互斥处理 | 直接复用 | P1 | 倍速 > 1.5x 时必须回退 Hi-Res/杜比到普通 AAC，并给出提示 |
| 播放记忆 / 续播 | 直接复用 | P1 | 本地续播优先，回退 B 站历史 |
| 画中画（PiP） | 直接复用 | P1 | 看模式下。与「自动降回纯音频」的冲突已有解，见 4.3 |
| 弹幕渲染 | 直接复用 | P2 | **仅看模式**加载，听模式不加载 |

#### 为什么选 Web 扫码而不是 TV 扫码

BiliPai 默认走的是 **TV 端扫码**（`passport-tv-login/qrcode/*`，用硬编码的「云视听小电视」appkey `4409e2ce8ffd12b8` 做 APP 签名，换取 `access_token`）。BiliSeek **不跟随**这个选择：

| 维度 | Web 扫码 | TV 扫码 |
| --- | --- | --- |
| 凭证 | Cookie（`SESSDATA` / `bili_jct`） | `access_token` + refresh_token（另附 cookie） |
| 请求签名 | WBI 签名 | APP 签名，且后续调用**必须全程用同一组 appkey** |
| 身份画像 | 一个用浏览器的普通用户 | 一台「云视听小电视」设备 |
| 画质权益 | 常规 | 更强（4K/HDR/高码率视频） |
| 凭证刷新 | 繁琐（RSA + HTML 解析） | 简单（一次带签名的 POST） |

决策理由，按重要性排序：

1. **TV 端的好处对 BiliSeek 几乎无价值。** TV 凭证换来的是高画质**视频**权益，而我们「默认只听」。音频侧的 Hi-Res / 杜比是**大会员**门槛而非端门槛，Web 端同样能通过 `fnval=4048` 拿到 `dash.flac`。等于付出冒用官方 appkey 的代价，换一堆用不上的东西。
2. **避免单点打击面。** TV 的 appkey/appsec 是公开流传的固定常量，所有第三方共享同一个设备身份。B 站若要收紧第三方，封禁或限流某个 appkey 是最省事的手段。Web 扫码不依赖任何冒用的官方凭据，没有这个共同故障点。
3. **行为画像一致。** Web 登录后，请求带浏览器 UA、`Referer: bilibili.com`、走 WBI 签名，与真人开网页完全一致。若用 TV 登录却继续发移动端特征的请求，会出现「TV 设备发出手机端流量」的矛盾画像，反而更易被标记；要做到一致就得连 UA、build 号、接口选择全套仿 TV，工作量和出错面都上去了。

> 诚实标注不确定性：**没有公开、确定的证据表明哪种登录方式会直接导致封号。** B 站风控主要盯**行为**（请求频率、IP 异常、批量操作、调用模式），登录方式影响的是「被识别为第三方客户端」的概率，不等同于封号风险。上述是风险面的相对比较，不是安全保证。
>
> 代价：Web 的 Cookie 刷新实现成本更高（见上表「登录态续期」行）。这是一次性成本，BiliPai 的 `TokenRefreshHelper.kt` 有现成实现可复用。

### 4.2 音频外壳与歌词（主要取自 BBPlayer）

## 6. 技术栈（已定方向）

- **原生 Kotlin + Jetpack Compose + Media3（ExoPlayer）。**
- 理由：招牌功能是「音视频同轴**无缝**切换」，Media3 原生支持 DASH、多轨、运行时禁用/启用视频轨、PiP；且 BiliPai 与 BBPlayer 的播放内核都是这套，最难的一块可以直接复用。
- **播放服务基类选 `MediaSessionService`**（跟随 BiliPai），不用 BBPlayer 的 `MediaLibraryService`——后者多一层「媒体库浏览」（Android Auto 可进来翻歌单），需实现 `onGetLibraryRoot` / `onGetChildren` 一套回调，对「搜索驱动、无推荐」的 BiliSeek 价值不大。确有需求再升级。

### 构建基线（**已在本机实测通过**，2026-08-23）

| 项 | 取值 |
| --- | --- |
| SDK | **minSdk 26、targetSdk 35、compileSdk 37** |
| AGP | **9.3.1** |
| Gradle | **9.7.1** |
| Kotlin | **2.4.10** |
| JDK | **Android Studio 捆绑的 JBR 25**（见下方说明） |
| Compose BOM | **2026.08.00** |
| Media3 | **1.11.0** |
| Navigation | Navigation Compose 2.9.8（稳定版，不用 Nav3 alpha） |

> minSdk 26 的理由：PiP 自 26 起可用；通知渠道、前台服务类型（Android 14 要求声明 `mediaPlayback`）也从 26 起才干净。

**两处与原计划的偏差（实测后修正）：**

1. **JDK 用 25，不是 21。** 当前 Android Studio（2026.1.3.8）捆绑的 JBR 就是 25，Gradle 9.7.1 在其上构建正常。刻意装 JDK 21 会导致 IDE 与命令行使用不同 JVM，产生两套 Gradle 守护进程与缓存失效。**统一用 Studio 的 JBR**，`JAVA_HOME` 指向 `~/android-studio/jbr`。字节码目标仍设为 JVM 21。

2. **AGP 9 内置 Kotlin 支持，不再需要 `org.jetbrains.kotlin.android` 插件。** 继续声明该插件会直接报错终止构建。Compose 编译器插件 `org.jetbrains.kotlin.plugin.compose` 仍需单独声明。

> KSP（2.3.11，已改用独立版本号）与 Hilt（2.60.1）在 M0 用不到，**骨架暂不引入**，等 M1 接网络、M3 接 Room 时再加。

### 从 BiliPai 摘码的正确姿势（已定）

> **不要 fork 后做减法。** 其「模块化」名不副实——`network-core` 只有 3 个策略类、`settings-core` 只有 1 个，真正的产品逻辑全在 `app` 模块（2544 个文件），且高度集中在几个巨型文件里：`VideoPlaybackViewModel.kt` **378 KB / 8663 行**、`ApiClient.kt` 133 KB、`MiniPlayerManager.kt` 105 KB。做减法的成本高于重写。
>
> **正确做法**：新建干净工程，**逐文件复制低耦合的纯逻辑**（WBI、MPD 拼装、轨道/音质策略、FLAC 渲染器、以及各 `*Policy.kt` 里的 `shouldXxx` / `resolveXxx` 纯函数——这些依赖极浅），播放器与 UI 层按 BiliSeek 自己的状态机重写。
>
> **值得沿用的约定**：BiliPai 把决策逻辑从 ViewModel 剥成无副作用纯函数放进 `*Policy.kt` 并配单测，这个模式让逻辑可测可复用，BiliSeek 应当照做。

> 具体的模块划分、播放器状态机、切轨时序、依赖解耦方案等**实现细节，留待《架构设计文档》**。

## 附录 A：一句话记住的三条原则

- **身份优先**：任何功能若引入「推荐流」或让浏览变成视频优先，就违背了 BiliSeek 的定位，宁可不做。
- **听为默认**：视频永远是「手动切入、自动退出」，不能反客为主。
- **授权守规**：用了 BiliPai 代码 = 整个项目 GPLv3，保留声明、公开源码；biu 的代码一行都不能碰。
