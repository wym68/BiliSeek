### B-2 证据：EventLogger 轨道选择对比

**听模式**（`[ ]` = 未选中）：

```

  group [ id=1
    [ ] Track:0, mimeType=video/avc, res=320x142   supported=YES
    [ ] Track:1, mimeType=video/avc, res=854x380   supported=YES
    [ ] Track:2, mimeType=video/avc, res=1280x570  supported=YES
    [ ] Track:3, mimeType=video/avc, res=1920x856  supported=YES
  ]
rendererReady [... rendererIndex=1, audio, true]     ← 只有音频渲染器
```

**切看后**（`[X]` = 已选中）：

```
    [X] Track:0 ... [X] Track:1 ... [X] Track:2 ... [X] Track:3
videoEnabled            [eventTime=105.21, mediaPos=44.66]
rendererReady           [... rendererIndex=0, video, true]
videoDecoderInitialized [... c2.goldfish.h264.decoder]
renderedFirstFrame      [... mediaPos=46.43, Surface(...)]
```

**退回听后**：

```
videoDisabled  [eventTime=142.39, mediaPos=79.75]
rendererReady  [... rendererIndex=0, video, false]     ← 视频渲染器已释放
仍被选中的视频轨数量: 0
```

> 关键点：这是**日志证明轨道状态**，不是「画面消失」的肉眼判断。`clearVideoSurface()` 同样会让画面消失，但视频轨可能仍在下载解码——那样省电省流量的目标一点没达成。

### B-3 证据：两次切换的实测诊断

| 方向 | buffering | seek 不连续 | 位置变化 | 判定 |
| --- | --- | --- | --- | --- |
| 听 → 看 | **0** | **0** | 44456ms → 44459ms | ✅ 无缝 |
| 看 → 听 | **0** | **0** | 201005ms → 201367ms | ✅ 无缝 |

位置单调递增且连续，全程无 `STATE_BUFFERING`、无 `DISCONTINUITY_REASON_SEEK`。

> 诊断逻辑已做进 App 本身（`SwitchDiagnostics`），每次切换直接在界面上给出「✓ 切换无缝」或「✗ 切换不无缝」，不需要人工翻日志判断。

### B-4 证据：流量对比

同为 50 秒窗口，`dumpsys netstats --poll` 后读取 uid=10209 的 rx 字节：

| 模式 | 50 秒下载量 |
| --- | --- |
| 听 | **846 KB** |
| 看 | **137,711 KB** |
| 比值 | **162.8×** |

> 注：模拟器的 netstats 默认是粗粒度轮询，直接读取会得到 0。必须先 `dumpsys netstats --poll` 强制刷新再读。这个坑值得记住。
>
> 看模式流量偏大是因为 M0 尚无画质策略，ExoPlayer 自动选了最高档（18 Mbps / 1920x856）。M1 接入 B 站后会有画质上限控制。

### C-2 补验（headless 模拟器，无需真机）

先前记录写「需真机复验」**不准确**——`screencap` 抓的是 framebuffer，锁屏照样渲染。

模拟器默认禁用了 keyguard，需先启用：

```bash
adb shell locksettings set-disabled false
adb shell input keyevent KEYCODE_SLEEP  && sleep 3
adb shell input keyevent KEYCODE_WAKEUP && sleep 4
adb exec-out screencap -p > lock.png
```

**结果：锁屏出现完整媒体控制卡片**——标题「M0 测试流」、暂停键、上一曲、进度条、输出设备切换（"This phone"）。

控制有效性实测：

| 操作 | MediaSession 状态 |
| --- | --- |
| 点锁屏暂停键 | `state=PAUSED(2), position=78236` |
| 发 `KEYCODE_MEDIA_PLAY` | `state=PLAYING(3), position=78296` |

### 附带发现：`POST_NOTIFICATIONS` 从未在运行时申请

| 权限状态 | 通知重要性 | 锁屏媒体卡片 |
| --- | --- | --- |
| 未授权（默认） | `importance=NONE` | ✅ 正常显示 |
| `pm grant` 后 | `importance=DEFAULT` | ✅ 正常显示 |

两点结论：

1. **锁屏媒体卡片由 MediaSession 驱动，不依赖通知权限。** 这与直觉相反——即使通知被系统完全屏蔽，锁屏控制照常工作。
2. **但通知栏控制依赖它。** Media3 确实发出了合规通知（`MediaStyle`、`category=transport`、`actions=2`、`flags=FOREGROUND_SERVICE`、标题「M0 测试流」），但未授权时 `importance=NONE`，不会在通知栏显示。

**App 目前从未在运行时请求 `POST_NOTIFICATIONS`**（manifest 声明了，但 API 33+ 需运行时授予）。这是一个真实缺口，**列入 M4 通知相关工作**。

## 结论与影响

**架构文档 §5.1 的核心假设成立：**

> 同进程下 `MediaController` 能正确转发 `setVideoSurfaceView()` 与 `setTrackSelectionParameters()`。

因此：

1. **「Service 持有 player + MediaController」的架构确认可行**，不需要退回 BiliPai 的单例方案。
2. **「无缝切看」确认可以做到零代价**——同一 player、同一 MediaSource，仅切换轨道选择参数，不重建、不 seek。选型篇把它从「允许缓冲」升级为「无缝」的决定得到实测支持。
3. **「听模式省流量」确认成立**，且是量级差异（162.8×）。

**双维度状态机（`PlaybackMode` × `PresentationMode`）在实现中验证有效**：播放态由呈现态推导，核心不变式在结构上无法违反，`resolvePlaybackMode` 是其唯一实现点。
