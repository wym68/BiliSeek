### B-1 证据：85 秒 → 13 毫秒

场景严格复现文档描述的原因：**清空凭据 + 飞行模式 + 后台预热正处于退避中**，
此时发起用户主动播放（外部链接直达）。

```
08-26 07:21:54.978  I/ActivityTaskManager  START ... act=android.intent.action.VIEW ... LAUNCH_SINGLE_TASK
08-26 07:21:54.991  W/BiliSeekAuth         凭据获取失败（第 1 次，FOREGROUND）：Unable to resolve host
```

**13 ms**。界面同时出现「重试」按钮。

两条关键观察：

1. 前台只打了 **1 次**（`第 1 次，FOREGROUND`）就收工，没有退避、没有重试——`maxAttempts = 1` 生效。
2. 同一时刻后台正独立跑到第 5 次：

```
07:21:05.117  凭据获取失败（第 1 次，FOREGROUND）
07:21:05.423  凭据获取失败（第 5 次，BACKGROUND）
```

两条链**并行推进**，说明前台请求没有排在后台预热的退避后面——这正是旧实现里
`mutex.withLock { repeat(5){ ... delay() } }` 造成 85 秒的根源。

后台退避序列实测为标准指数退避（间隔 1 / 2 / 4 / 8 秒）：

```
07:12:19.999 第 1 次     07:12:27.024 第 4 次
07:12:21.016 第 2 次     07:12:35.028 第 5 次
07:12:23.020 第 3 次
```

### B-3 说明：修的是分支，`Empty` 变体没能实拍

**白屏的成因已修**：旧代码里 `items.isEmpty()` 时无条件调用 `emptyContent()`，
而 `emptyContent` 内部要求 `keyword.isBlank()`，于是「有关键词但 0 结果」落进了一个
什么都不渲染的缝里。现在 `items.isEmpty() && error != null` 单独成支，渲染错误面板。

**这个分支已实测**（飞行模式下搜索，`items` 为空且 `error != null`）：

```
text="网络不可用"
text="重试"
```

不再是白屏。

**但 `SearchError.Empty`（「没有找到『xxx』」）这一具体变体没能实拍**：B 站搜索做模糊匹配，
连 `xqjzvwkhgfdpoiuytrewq09876zzz...` 这种 60 字乱码都会返回「约 1000 个结果」，
点不出真正的 0 结果。开发过程中倒是**自然撞见过一次**（风控软拒绝，`code=0` / `content-length: 101` / 0 条），
当时是旧构建，界面确实是白的——那是这条判据的原始复现，但新构建下无法按需重放。

判据降级为 🔸：渲染分支已验，文案分支由单测覆盖（`SearchError.Empty` 的 `retryable == false`），
`Empty` 变体的真机截图待日后自然遇到时补。

> 刻意把它逼出来的唯一办法是猛刷搜索直到被风控——那恰好是 B-4 明令禁止的行为，不做。

### B-4 说明：不实触发，靠单测与代码路径

`-352` 的处置是**绝不重试**，因此不会为了拍一张截图去故意触发风控。
证据取两处：

1. 单测锁定语义（`SearchErrorTest`）：

```kotlin
@Test fun `风控错误绝不给重试按钮`() {
    assertFalse(SearchError.Blocked.retryable)
}
```

2. UI 层唯一的按钮出口是 `if (error.retryable)`，`Blocked` 恒为 `false`，
   且文案明确写「请过几分钟再试，反复重试会让拦截时间变长」，不留可戳的控件。

## §4.3 Cookie 刷新：实现完整，但**未启用**

### 已完成

| 步骤 | 状态 |
| --- | --- |
| `correspondPath` = RSA-OAEP(SHA-256) 加密 `refresh_{ts}` → hex | ✅ 纯函数 + 单测 |
| `refresh_csrf` 的 HTML 提取（`id="1-name"`） | ✅ 纯函数 + 单测 |
| `BiliApi.correspond()` 返回原始 `ResponseBody` | ✅ 未引入 HTML 转换器 |
| 完整链路编排（info → path → csrf → refresh → 落库 → confirm） | ✅ |
| 复用 `parseSessionFromCookies` 解析响应头新 Cookie | ✅ |
| 遇 `-352` 绝不重试，保持现有登录态 | ✅ `RefreshOutcome.Blocked` |
| 触发时机：`AppViewModel.init` 中会话加载后，后台执行 | ✅ 实测日志 `启动时检查登录态续期：NotLoggedIn` |

### 未完成：`CORRESPOND_PUBLIC_KEY` 留空

`correspondPath` 所需的固定 RSA 公钥常量**没有填**，因此 `refreshIfNeeded()` 在到达该步时
返回 `RefreshOutcome.NotConfigured` 并跳过——功能处于未启用状态。

原因：本项目此前依赖的公开接口文档仓库（`SocialSisterYi/bilibili-API-collect`）已于
**2026 年 1 月 28 日因 B 站律师函全面下架并删除内容**，该常量无法从原出处取得。

**为什么留空而不是凭印象填一个值**：填错不会报错。OAEP 加密照样成功，只是服务端解不开，
表现为刷新永远静默失败、用户过一阵子莫名掉登录，且极难归因。
在一条负责账号凭据轮换的链路上，静默错值比功能缺失更糟。

填入常量后 `CookieRefresher` 无需改动即可生效。

### 关于「加密算得对不对」

公钥缺失不影响算法本身的可验证性。单测用**自生成的 2048 位密钥对**做往返验证：

```kotlin
@Test fun `加密结果可用私钥解回原文`() {
    assertEquals(plaintext, decrypt(rsaOaepHex(plaintext, pem())))
}
```

同时钉住了一个容易静默出错的点：JCA 里 `OAEPWithSHA-256AndMGF1Padding` 只约束 OAEP 摘要，
**MGF1 在多数 provider 上默认仍是 SHA-1**，而浏览器 WebCrypto 的 RSA-OAEP 两处同摘要。
不显式给 `OAEPParameterSpec(..., MGF1ParameterSpec.SHA256, ...)`，加密一样成功、服务端一样解不开。

### B-5 结论

如《功能优化篇》§4.3 警告所言，真实验证需先有真人扫码得到 `refresh_token`。
当前既无登录态、又缺公钥，**B-5 如实标注为未验证，不当作通过**。

> **补记（2026-08-26 真机）**：真人扫码登录后在 PJD110 / Android 16 上复采，链路推进了三步：
>
> ```
> D BiliSeekRefresh: 启动时检查登录态续期：NotConfigured
> ```
>
> `NotConfigured` 在 `CookieRefresher.kt:74` 才返回，走到那里必须先满足
> `isLoggedIn` → `cookie/info` 返回 `code=0` 且有 data → **`data.refresh == true`**。
> 也就是说带真实凭据打通了前三步，卡在唯一缺的那个常量上。
>
> 但**新 Cookie 的解析与落库仍未真实执行过，B-5 依旧不算通过**。
> 另注意：服务端此刻已判定该刷新（`refresh == true`），刷新未启用意味着这个登录态会掉。
> 见[真机验收记录](真机-2026-08-26.md) §B-10。
