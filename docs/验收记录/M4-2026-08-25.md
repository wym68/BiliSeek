## 发现并修复的缺陷

### 1. 续播 seek 被起播流程覆盖（功能完全失效）

**现象**：点最近播放条目，保存的位置 61s 不生效，从 0 开始播。

**根因**：早期写法是

```kotlin
c.setMediaItem(item)
c.prepare()
c.seekTo(saved)   // ← 经 MediaController 异步转发，时序不可靠
```

`MediaController` 把命令异步转发给 session，`prepare()` 之后紧跟的 `seekTo` 会被起播流程覆盖。

**修复**：改用 `setMediaItem(item, startPositionMs)` 原子设置起始位置。修复后实测 `position=62003`。

### 2. 接近结尾的续播等于「点了没反应」

**现象**：C-1 稳定性测试跑了 5 分钟进度纹丝不动，一度以为播放器卡死。查日志才发现 `state ENDED at mediaPos=62.00`——**续播的那首歌总长就是 62 秒，从 61s 续播 1 秒就播完了**。

这不是测试问题，是真实的产品缺陷：用户点一首听过大半的歌，会看到「点了没反应」。

**修复**：新增 `resolveStartPosition` 纯函数，两端都裁——开头 5 秒内不算进度，**距结尾不足 15 秒时从头开始**。配 5 个单测，其中一条直接锁定这个实测 case：

```kotlin
@Test fun `接近结尾时从头开始`() {
    assertEquals(0L, resolveStartPosition(61_000, 62_000))
}
```

### 3. 补上 M0 遗留的 `POST_NOTIFICATIONS` 运行时申请

M0 验收时确认：不授予不影响**锁屏**媒体控制（由 MediaSession 驱动），但通知栏控制会因 `importance=NONE` 不显示。现已在 `MainActivity` 启动时申请，拒绝也不阻断主流程。
