### C-1 证据：分享（`ACTION_SEND`）

模拟 B 站 App 的「分享到」，文本是**混着说明文字的短链**（真实分享文本就长这样）：

```
'【Bad Apple!!】 - 哔哩哔哩 https://b23.tv/BV17x411w7KC 快来看'
```

冷启动直接接住：

```
界面：正在播放 / BV17x411w7KC / 00:40 / 03:20
日志：b23.tv/BV17x411w7KC  →  playurl?bvid=BV17x411w7KC
```

`parseSearchInput` 从散文里挑出短链 → 展开 → 二次解析 → 起播，一步到位。

### C-2 证据：短链展开 + `onNewIntent`

**App 已在运行**时发 `ACTION_VIEW`，专门验「容易漏的第二处入口」：

界面：正在播放 / BV1Q541167Qg / 01:00 / 04:09

### C-3 证据：AV 号本地换算

```
输入：av170001
日志：pagelist?bvid=BV17x411w7KC  →  playurl?bvid=BV17x411w7KC
界面：正在播放 / BV17x411w7KC / 03:20
```

`av170001 → BV17x411w7KC` 完全本地算出，**没有为了拿 BV 号多打一次网络请求**。

  `parseDurationText` 的三段式解析与 `formatDuration` 的 `h:mm:ss` 分支

## 发现并修复的缺陷

### 起播请求在绑定完成前被静默丢弃（本里程碑引入）

**现象**：从外部链接进来有时完全没反应——不报错、不转圈、不起播。

**复现**：`pm clear` 后首次启动，再发 `ACTION_VIEW`。稳定复现。

**根因**：两层叠加。

1. `MainActivity` 是默认 `standard` 启动模式，`am start -a VIEW` 会**新建一个 Activity 实例**
   （日志里 `result code=3`），于是新建 `AppViewModel` → 新建 `PlayerConnection`。
2. `handleSharedIntent()` 在 `onCreate` 里就把链接喂了进去，而 `connection.connect()` 还在路上。
   `PlayerConnection.play()` 开头是 `val c = controller ?: return`——**请求就这么无声无息地丢了**。

之所以早期几次实测没暴露：短链要多一次网络往返（约 1 秒），刚好给绑定留出了时间。

**修复**（两处，缺一不可）：

- `play()` 不再默默返回：控制器没就绪就自己补一次 `connect()`；仍拿不到才落 `error = "播放器未就绪"`。
  `connect()` 同时加锁改为可重入，避免与启动时那次并发建出两个 controller。
- `MainActivity` 改 `launchMode="singleTask"`：外部链接复用已有实例走 `onNewIntent`，
  而不是每次分享都叠一个新 Activity + 新 ViewModel + 新播放器绑定。

**验证**：修复后三种时序全部通过——

| 场景 | 结果 |
| --- | --- |
| 已运行 + `ACTION_VIEW` | ✅ 起播，日志 `LAUNCH_SINGLE_TASK` |
| `pm clear` 后首启 + `ACTION_VIEW` | ✅ 起播（原复现场景） |
| 冷启动直接带 `ACTION_VIEW`（最激烈竞态） | ✅ 起播 |

这条也顺带兑现了 §4.2 的取向：**失败要能看见**。原来的 `?: return` 属于同一类问题——
「点了没反应」比报错更难排查。
