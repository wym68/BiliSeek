## B. 关键证据

### B-1 真实解码器与真实轨道表（只有真机能给）

切「看」时用的是**高通硬件解码器**，不是模拟器的 `c2.goldfish`：

```
videoEnabled            [eventTime=166.18, mediaPos=100.64]
videoDecoderInitialized [eventTime=166.53, mediaPos=100.92, c2.qti.hevc.decoder]
videoSize               [eventTime=166.69, mediaPos=101.18, w=1920, h=1072]
renderedFirstFrame      [eventTime=166.69, mediaPos=101.18, Surface(...)]
```

退回「听」时视频渲染器真的被释放，8 条视频轨全部落回未选中：

```
videoDisabled        [eventTime=141.16, mediaPos=75.62]
rendererReady        [... rendererIndex=0, video, false]
videoDecoderReleased [... c2.qti.hevc.decoder]
tracks
  group [ id=unset:0
    [ ] Track:0, mimeType=video/avc,  res=1920x1072
    [ ] Track:1, mimeType=video/hevc, res=1920x1072
    ...（8 条全是 [ ]）
  group [ id=unset:1
    [X] Track:0, mimeType=audio/mp4a-latm, bitrate=129664
```

「画面消失 ≠ 视频轨停下载」这条，在真机上也成立了。

### B-2 切看/切听无缝（两个方向）

同一份日志里数事件，**两个方向都是 0 / 0**：

| 方向 | buffering 次数 | positionDiscontinuity 次数 | mediaPos |
| --- | --- | --- | --- |
| 看 → 听 | 0 | 0 | 75.62 → 75.65 |
| 听 → 看 | 0 | 0 | 100.64 → 101.18（首帧 0.54 秒） |

### B-3 拖动不回弹 + 拖完被杀也不丢


### B-9 续播的尾部保护（步骤 19 的刻意行为）

专门做了一次对照实验：把「江南」（时长 04:27）拖到 **04:24** 后立即强杀，重启确认历史里存的是 `04:22 / 04:27`（距结尾 5 秒）。再点它播放，**从 `00:00` 开始**而不是从 04:22 续上：

```

```

`RESUME_TAIL_MARGIN_MS = 15_000` 生效。同一轮里另有正常续播的对照（WPS 从 01:40 续上）。

### B-10 登录态（步骤 20）与续期链路的真实进展

设置页：`已登录 · UID 3227*****`（UID 已打码），`force-stop` 重启后仍是登录态。

启动日志：

```
D BiliSeekAuth:    凭据从本地恢复，跳过网络请求
W BiliSeekRefresh: correspondPath 公钥未配置，跳过刷新
D BiliSeekRefresh: 启动时检查登录态续期：NotConfigured
```

**这条比看上去重要。** `NotConfigured` 在 `CookieRefresher.kt:74` 才返回，走到那里必须先满足：
`isLoggedIn` → `cookie/info` 返回 `code=0` 且有 data → **`data.refresh == true`**。
也就是说，带着真实凭据打通了续期链路的前三步，卡在**唯一缺的那个常量**上。

M6 的 B-5 因此从「完全无从验起」推进到「链路验到最后一步」——但**仍不算通过**：新 Cookie 的解析与落库没有真实执行过。

> ⚠️ 附带结论：服务端此刻就认为你的凭据**该刷新了**（`refresh == true`），而刷新未启用。
> 这个登录态大概率会在一段时间后掉。这不是新缺陷，是 `CORRESPOND_PUBLIC_KEY` 留空的既有代价。

## C. 真机暴露出来的问题

**都不是 M5–M7 的功能回归**，但都得记下来。

### C-1 画中画在本机进不去：系统侧权限为 deny

```
$ adb shell cmd appops get com.biliseek.debug PICTURE_IN_PICTURE
PICTURE_IN_PICTURE: deny
```

看模式下按 Home，**没有 PiP 小窗**，但音频继续播放（`state=PLAYING`）——回落逻辑本身是对的。

ColorOS 默认不给第三方应用画中画权限，且**不允许 adb 修改**（`cmd appops set` 报 `SecurityException: uid 2000 does not have MANAGE_APP_OPS_MODES`）。要验这条得手动开：
**设置 → 应用管理 → BiliSeek → 权限 → 画中画**。

### C-2 「播完后按播放无反应」在本机未复现

《手动测试指南》附录 3 把它列为已知缺口。实测：曲目播到 `04:09 / 04:09`（`state=STOPPED`）后点「播放」，**从头开始播**（`00:04`），不是点了没反应。

这条缺口应当改写或删除——但先别急着删，它当初是在模拟器上观察到的，两边行为可能真的不同。

### C-3 「切换无缝自检卡片」这个功能已经不存在了

《手动测试指南》步骤 8 与附录 1.6 要求在播放页看到：

```
✓ 切换无缝：听 → 看
buffering 次数      0
seek 不连续次数     0
```

**播放页上没有这个卡片。** 追代码：`SwitchDiagnostics` 与 `PlaybackState.lastSwitch` 仍在产出
（`PlaybackModels.kt:66`、`PlayerConnection.kt:424`），但**全项目没有任何 UI 消费它**。
`git log -S lastSwitch -- app/src` 显示它最后一次出现在 app 层是 **M3（c96f55b）**——那次播放器容器重构把卡片带走了，文档一直没跟上。

所以步骤 8 这轮是**靠日志判定的**（§B-2），不是靠卡片。文档需要修正。

### C-4 拖拽重排：`input draganddrop` 在真机上不触发长按

指南里给的 `adb shell input draganddrop x1 y1 x2 y2 2000` 在本机**不生效**，列表顺序纹丝不动。原因是它的按下时长不足以越过 Compose 的长按阈值。真机上要用分解事件：

```bash
adb shell "input motionevent DOWN 400 690; sleep 1; \
  for y in 720 780 850 920 990 1060 1130 1200 1260 1290; do input motionevent MOVE 400 \$y; done; \
  input motionevent UP 400 1290"
```

手指操作不受影响——你手动拖是通过的，这条只影响脚本化验证。

### C-5 时长展示口径不一致（观感问题）

同一个视频，三处显示不同：

| 位置 | 显示 | 来源 |
| --- | --- | --- |
| 搜索结果行 | `667:37` | B 站接口原样返回的 `mm:ss`，分钟数不进位 |
| 歌单条目 | `20:25:08` | `parseDurationText` + `formatDuration` 规整成 `h:mm:ss` |
| 播放页 | 当前分 P 的时长 | 播放器 duration |

后两者各自都对（歌单存的是**合集总时长**，播放页是**当前分 P**），但搜索结果里那个 `667:37` 没走规整，看着像 bug。建议搜索结果行也过一遍 `parseDurationText` + `formatDuration`。

### C-6 一次没能复现的观察

首次点开分 P「江南」（04:27）时，界面显示位置约 `04:17`，随即自动跳到下一 P。按 `resolveStartPosition` 的尾部保护，这不该发生。

随后做了 §B-9 的对照实验（存 04:22 → 从头播），**没能复现**，两次重放也都从 0 开始。可能是当时读到的是上一条目的残留状态。**记录在案，不当作缺陷**；若再遇到，重点看那次取流返回的 `durationMs` 是不是 0——`resolveStartPosition(saved, 0)` 只做开头裁剪，尾部保护会失效。

## F. 结论

- 《手动测试指南》Part B 步骤 1–20 **在 Android 16 真机上全部通过**，18 条有机器证据。
- 真机独有的收获有三个：**真实硬件解码器下切看仍然无缝**、**真实登录态把续期链路推进到只差一个常量**、以及**三处文档与实现不符**（C-2 / C-3 / C-4）。
- **发版前仍不能算完**：B6 的步骤 21–27（耳机、音频焦点、长时稳定性、Hi-Res）一条都没跑，那些才是真机路径存在的理由。
