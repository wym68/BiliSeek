### A-1 证据：拖动不被轮询拽回

从 `00:07` 处拖到约 60% 松手：

```
松手 1 秒后 ：01:43   media_session position=101122
松手 4 秒后 ：01:48   media_session position=107554
```

落点准确，且 4 秒后是**继续前进**而不是弹回 `00:07`——250ms 的 `pushState()` 轮询没有覆盖拖动值。
坑 2 的本地拖动态（`dragging` / `dragValue`）生效。

### A-2 证据：节流窗口内被杀也不丢位置

拖到 `01:06` 后 **2 秒内** `am force-stop`（远早于 5 秒回写节流），重启后首页「最近播放」：

```
[LOLA]Vortex void[VOCALOID原创]
01:04 / 02:52
```

若没有 `seekTo` 内的强制回写，这里会是拖动前的旧值。
（`01:04` 与界面上的 `01:06` 差约 1.6 秒，是回写用的是 seek 目标值、而界面显示的是随后继续播放的实时位置，两者一致。）

### A-5 证据：两种终止条件都实测

**播完当前**：先切到**单曲循环**，设「播完当前」，锁屏等待。

```
state=STOPPED(1), position=172003   （曲目总长 02:52 = 172000ms）
```

单曲循环本该原地重播，这里停在了曲末并保持 STOPPED——终止条件正确地**优先于播放模式**。

**15 分钟倒计时**：21:30 设定，界面显示 `睡眠定时 · 剩余 14:56`，锁屏后台运行。

```
21:42:02  state=PLAYING(3), position=140442, speed=1.5
21:45:28  state=PAUSED(2),  position=88138,  speed=0.0
```

到点暂停，且 `position=88138` 是**曲目中段**而非结尾——排除「自然播完」的干扰解释。
全程锁屏，验证了「计时器状态归 `PlayerConnection` 持有、不绑 UI 生命周期」。

## 顺带修掉的既有缺陷

### `recordPlay()` 会抹平续播位置

`recordPlay` 的 `positionMs` 参数默认 0，**每次起播都把已保存的进度清零**。
之前没暴露，是因为它在 `connection.play()` **之后**调用——续播位置已经读过了，
随后 5 秒节流的回写又把实时位置写了回去。但只要用户在起播后 5 秒内退出，进度就归零了。

M5 必须动它：时长回写走的是「更新已有行」的窄接口（坑 3），行不存在时会静默丢弃，
所以 `recordPlay` 得挪到 `connection.play()` **之前**。这一挪就会让上面的清零真正生效。

改法：`positionMs` 改为 `Long? = null`，传 `null` 表示**保留既有进度**。

## 与文档的偏差

| 项 | 文档 | 实际 | 原因 |
| --- | --- | --- | --- |
| `PlaybackState` 新增字段 | `sleepTimerRemainingMs` + `speed` | 另加 `sleepTimerEndOfTrack: Boolean` | 「播完当前」没有剩余时间可报，`remainingMs` 恒为 null，UI 无法区分「没设」与「设了播完当前」 |
| `formatDuration` 归属 | 未指定 | `:core:player` 的 `Formatting.kt` | 三个界面（Mini / Expanded / 首页）与后续通知栏都要用；放播放模块可被 `:app` 直接引用 |
