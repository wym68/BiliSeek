### D-1 证据：设置项落库

依次改三项：默认呈现态 → **记住上次**、音质 → **无损优先**、响度均衡 → **关**。
`am force-stop` 重启后重进设置页：

```
播放   ○ 默认只听   ● 记住上次
网络   移动网络下允许看视频   [关]
音质   自动 [无损优先] 省流量        响度均衡 [关]
```

三项全部保持。`SettingsStore` 的 DataStore 落库生效。

### D-2 证据：流量策略与一次性放行

把模拟器切到计量网络（`svc wifi disable`，落到 CELLULAR，能力位里没有 `NOT_METERED`），
在听模式下点「切「看」」：

```
当前是移动网络
设置里关闭了「移动网络下允许看视频」。视频流量大约是音频的一百倍以上。
[继续只听]  [这次就看]
```

点「这次就看」→ 进入看模式，画面正常。**随后回设置页确认开关仍是关的**——
一次例外没有被升级成永久开关，这正是 `MeteredVideoDialog` 那段注释要守住的东西。

### D-3 证据：记住上次

设为「记住上次」并在看模式停留过之后，从歌单点一首新曲目：
起播后播放页的主按钮直接是「**退回「听」**」而不是「切「看」」，即已自动进入看模式。

自动进看模式同样要过流量策略那一关（`MainActivity` 里 `shouldAutoEnterVideo()` 之后走的是
`requestPresentation` 而不是 `applyPresentation`），否则设置里关掉的移动网络看视频会从这条路溜进去。

### D-4 证据：死参数真的打通了

这是本里程碑的核心。改前 `PlayUrlResolver.toMedia()` 写死 `preferHiRes = false`，
UI 传什么都没用。改后设置成「无损优先」，取流日志：

```
D BiliSeekPlayUrl: MPD 组装完成：视频轨 3 条，音频轨 1 条（音质 LOSSLESS）
```

请求确实带着 LOSSLESS 出去了。该视频没有无损轨（且本轮未登录大会员），播放页如实写：

```
音质：自动（本视频无无损音轨，或账号无权限）
```

**显示的是生效值而非设置值。** 无损真正命中的正向用例需要大会员账号，本轮验不到——
但「请求带出去了」与「拿不到时如实说明」这两段都成立。

### D-5 证据：倍速与无损互斥

同一条内容，播放中点 2.0×：

```
日志：playurl 命中缓存 BV17x411w7KC:279786:AUTO      ← 缓存 key 后缀从 LOSSLESS 变成 AUTO
界面：音质：自动（倍速超过 1.5×，已回退）
位置：02:04 → 02:29（连续，没有回到 0）
```

**缓存 key 变了才是关键证据**：说明真的换了一份 manifest 重新取流，
而不是只把界面文案改成「已回退」却仍在放无损轨。位置连续则是 `startPositionOverride` 的作用点——
走数据库那条续播路会撞上 5 秒回写节流，赶不上。

### D-6 证据：响度均衡

同一条内容，开关各播一次：

```
开：响度均衡 开：measured=-10.2 target=-14.0 → gain=0.6456542
关：响度均衡 关：measured=-10.2 target=-14.0 → gain=1.0
```

响度数据是 B 站白送的（playurl 带 `voice_balance=1` 即返回 `measured_i` / `target_i`），
不必自己分析音频。关掉时**显式恢复 1.0**——不恢复的话上一首压下去的音量会一直带到下一首。

> 增益是听觉上的细微变化，界面上看不见。为此加了 `BiliSeekLoudness` 这个 tag：
> 没有日志这条判据就只能靠嘴说。

### D-7 证据：队列内非首条终于进历史

这是《手动测试指南》附录 3 里挂了一个里程碑的老缺口。

搜索接口本轮被限流（见下），因此用**数据库夹具**造了一个三首的歌单，
清空 `play_history` 后从头走一遍：

| 动作 | `play_history` 内容 |
| --- | --- |
| 点歌单第一首 | `队列第一首\|200\|UP甲` |
| 点「下一首」（手动切歌） | 追加 `队列第二首\|213\|UP乙` |
| 拖到曲末等自动推进 | 追加 `队列第三首\|249\|UP丙` |

**手动切歌与播完自动推进两条路径都写进了历史**，且 UP 主与时长都在——
`PlaybackRequest.Bili` 补的那两个字段让回调一处就能写全信息。

首页「最近播放」上也能直接看到这三条，格式为 `mm:ss / mm:ss`。

改法的落点是 `PlayerConnection.play()` 里的 `trackStartRecorder`：
`skipToIndex` / `skipToNext` / `onTrackEnded` 全都收敛到 `play()`，
挂在那里才不会漏；挂在 UI 的三个起播入口上就是之前漏掉的原因。

### D-9 证据：全屏

看模式下点「全屏」：

```
系统提示：Viewing full screen（系统栏已隐藏，沉浸生效）
画面：有内容，不是黑屏
播放：PLAYING，position 持续推进
日志：buffering 0 次、positionDiscontinuity 0 次
```

退出两条路都验了：「退出全屏」按钮一下即回；返回键**需要按两次**——
第一次被系统吃掉用于恢复系统栏（沉浸模式的平台行为），第二次才逐级收回到展开态。
退出后回到内联看模式，画面连续，没有 `already has a parent` 崩溃。

> SurfaceView 单宿主是这块最容易翻车的地方：全屏时展开态那份**不渲染** `PlayerSurface`
> （`PlayerContainer` 里 `FULLSCREEN -> Unit` 那个分支），保证同一时刻只有一个父容器。

## 环境限制：搜索接口本轮返回空结果

模拟器上任何关键词都搜不到东西，**且与 M8 的改动无关**：

```
--> GET .../wbi/search/type?search_type=video&keyword=acg&page=1&...
<-- 200 (245ms)
content-length: 101          ← 响应体只有 101 字节
bili-status-code: 0
```

`content-length: 101` 说明服务端**真的返回了空结果**，不是解析或渲染出了问题
（有结果的响应是几十 KB）。风控凭据本身是正常的：日志里 `buvid 激活: code=0` +
`风控凭据种植完成`，`pm clear` 重种一次也一样。同一网络下的真机今天早些时候搜索正常，
因此判断是这台模拟器的凭据/指纹被服务端静默降权。

**受影响的判据只有 D-8**：搜索结果行的时长口径改不到界面上验证。
该函数（`normalizeDurationText`）有 5 条单测覆盖，含「解析不出来时回退原文」这条关键分支。
**建议在真机上补看一眼**——那是这条唯一没被机器证据覆盖的地方。

## 未验证

**大会员相关的两项按《功能优化篇》§2.4 的口径处理：照常实现、只验逻辑、如实标注未验证。**
补记于 2026-08-28：这些路径已补上逻辑层覆盖（见下），但**仍不算通过**——
逻辑测试证明的是「按设计走对了」，不是「在真机上放出声了」。

| 项 | 为什么没验 | 逻辑层覆盖 |
| --- | --- | --- |
| D-10 Hi-Res FLAC 输入缓冲 | 需大会员 + 特定机型（部分设备只给 FLAC 解码器 32 KiB）。`HiResCompatibleRenderersFactory` 是**按已知解法预防**，不是实测修好 | `FlacBufferPolicyTest` 5 例：只动 FLAC、不缩小已够大的缓冲、系统缺省值不漏抬、MIME 大小写不敏感 |
| 无损音质的正向命中 | 需大会员账号。本轮只验到「请求带出去了 + 拿不到时如实说明」 | `LosslessManifestTest` 6 例：flac / 杜比轨**真的写进了 MPD**、无损档位下视频轨不被挤掉（否则切看要重建播放源）、URL 里的 `&` 正确转义 |
| 响度均衡的听感 | 模拟器无音频输出，只验到增益数值 | `LoudnessPolicyTest` 6 例 |
| D-8 搜索结果时长 | 接口本轮无结果，见上 | `DurationTextTest` 5 例 |

> 为了让 FLAC 缓冲那条可测，判定逻辑从 `MediaCodecAdapter.Factory` 里抽成了纯函数
> `resolveCodecMaxInputSize`。**抽它的理由就是验不到真机**——实测无门时，
> 至少让逻辑本身可被检验，而不是靠「看起来对」担保。

## 过程中发现的问题

### 「音质」这条链路原本从头到尾都是断的

不只是 `toMedia()` 里那个写死的 `false`：`resolve()` 把 `preferHiRes` 算进了缓存 key，
于是即便有人把参数传对，两个档位的 manifest 也会各存一份——**看起来像做了，实际上从来没生效过**。
这类「参数存在、链路不通」比功能缺失更难发现，因为搜代码能搜到它。

### 全屏的返回键要按两次

沉浸模式下第一次返回被系统用来恢复系统栏。用户视角是「按了一次没反应」。
当前用显式的「退出全屏」按钮兜底，可接受但不理想。
若要改，得在 overlay 里自己接管返回键的第一次按下。**记录在案，未处理。**

### 边缘到边缘下展开播放器压住了状态栏

展开态播放器是 Scaffold 之上的 overlay，没有吃到 `WindowInsets`，
顶部的「▾」与标题跟状态栏时钟挤在一起。**这是 M8 之前就有的老问题**，本轮只是看清楚了。
