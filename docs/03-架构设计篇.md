## 1. 设计原则

三条，用来在后续每个分歧点上做裁决：

1. **播放器生命周期绑 Service，不绑 UI。**  
   「默认只听」意味着用户绝大多数时间在别的 App 里、锁着屏。任何让播放器依附于页面的设计都是错的。
2. **决策逻辑做成纯函数。**  
   沿用 BiliPai 的 `*Policy.kt` 约定：把 `shouldXxx()` / `resolveXxx()` 从有状态组件里剥出来，无副作用、配单测。目前全仓约 50 个 `*Policy`（`core/*/internal/`、`app/data/`、`app/summary/`、`app/ui/` 等），这是遏制 God Object 的主要手段。
3. **能不落库就不落库。**  
   远程数据（收藏夹内容、合集、搜索结果、动态）只做内存缓存；只有用户主动保存进本地列表的东西才写数据库（例外见 §6.2）。

## 2. 模块划分

```
:app                    UI、导航、AppViewModel + feature Controller、Room、Repository、前台服务（下载 / AI 总结）
 ├── :core:network       风控凭据、WBI 签名、Cookie、节流与冷却、Retrofit 接口与 DTO、写请求编排
 ├── :core:player        取流、DASH/MPD 组装、ExoPlayer、PlaybackService、播放状态机、队列   → 依赖 :core:network
 ├── :core:ai            AI 总结：Provider（OpenAI 兼容）、分块 map-reduce Summarizer → Markdown   （不认识 B 站）
 ├── :core:asr           离线语音识别：sherpa-onnx + SenseVoice + Silero VAD，模型下载 / 导入 / 校验（不认识 B 站）
 └── :design-system      设计 token、主题、`Bs*` 通用组件、强调色策略
```

| 模块 | 职责 | 明确不承载 |
| --- | --- | --- |
| `:core:network` | `AuthGate`（buvid / bili_ticket / WBI）、`BiliCookieJar`、`HeaderInterceptor`、`RequestThrottle`、`RiskCooldown`、`CookieRefresher`、`LoginManager`、`BiliRepository`（读写 API 编排）、DTO | 任何 UI、播放 |
| `:core:player` | `PlayUrlResolver`（playurl + 缓存 + 离线拦截）、`LocalDashManifestBuilder`、`PlaybackService`、`PlayerConnection`（facade）、队列、续播、睡眠定时、响度 | Compose、导航 |
| `:core:ai` | Provider 预设（协议 × 预设）、`Summarizer`、`SummaryMarkdown`、`AiConnectionTester` | B 站任何东西、Cookie |
| `:core:asr` | `OfflineTranscriber`、`AsrModelManager`、`AsrModelCatalog`；带预编译 `.so`（`jniLibs/arm64-v8a`、`x86_64`） | B 站任何东西 |
| `:design-system` | `BsSpacing`/`BsSize`/`BsShapes` token、`Bs*` 组件、`AdaptiveAccentColorPolicy`/`ThemeContrastPolicy` | 网络、业务状态；封面取色（在 `app/ui/CoverAccent.kt`） |
| `:app` | 页面、导航、`AppViewModel` 与各 feature Controller、Room、`LibraryRepository`、`DownloadManager`/`DownloadService`、`SummaryManager`/`SummaryService`、弹幕 | — |

独立成模块的实际收益：(a) 可以脱离 Compose 跑纯 JVM 单测；(b) 外来源文件集中，便于按 GPLv3/MIT 标注来源；(c) `:core:ai`/`:core:asr` 与 B 站完全解耦，网络隔离（AI 与模型下载用自己的 `OkHttpClient`，不带 B 站 Cookie 与拦截器）在模块边界上就成立。

> 数据库与 Repository 仍在 `:app`，未拆 `:core:data`。

## 3. 网络与风控层

### 3.1 冷启动 gate（`AuthGate`）

所有业务请求必须在风控凭据就绪后才发出：

```
启动（AppViewModel：先加载 SessionStore，再 authGate.start()——GenWebTicket 需要 bili_jct 作 csrf）
 ├─ 从持久化恢复 buvid3/buvid4、bili_ticket、WBI keys、设备指纹
 ├─ 检查有效期 → 有效直接放行
 └─ 失效/缺失：
     ├─ GET  x/frontend/finger/spi_v2          → buvid3 / buvid4（立即注入 CookieJar）
     ├─ POST bapis/…/Ticket/GenWebTicket       → bili_ticket ＋ 顺带返回 WBI img/sub key
     │        （失败则跳过 ticket，改从 nav 取 WBI，照常放行）
     ├─ POST ExClimbWuzhi                       → buvid 激活（BuvidActivation，带 per-install 设备指纹）
     └─ 持久化 → 放行
```

**gate 不阻塞 UI。** 搜索框立刻可输入；业务请求 `authGate.awaitReady()` 排队等放行，UI 不感知。  
重试预算分两档（`SeedingProfile`，`internal/RetryPolicy.kt`）：后台预热 `BACKGROUND`（5 次指数退避，1s→30s）；用户主动请求 `FOREGROUND`（1 次、4s 超时，快失败让用户看到「重试」）。gate 失败不弹错误，只有用户发起的请求最终失败才在该处提示。

### 3.2 请求链与错误码分流

OkHttp 客户端（`BiliNetwork`）上只有两层：

```
Request
  ↓ HeaderInterceptor   注入 User-Agent / Referer / Origin（缺则补；写请求可自带视频页 Referer）
  ↓ BiliCookieJar       buvid3/4、b_nut、b_lsid、bili_ticket、SESSDATA、bili_jct
  ↓ (OkHttp 发出)
Response
```

**错误码不在拦截器里处理**，而是在 `BiliRepository` 的每个调用点经纯函数分流：读路径 `resolveRetryAction(code)`（`internal/RetryPolicy.kt`），写路径 `resolveWriteOutcome`（`internal/WritePolicy.kt`，由 `internal/WriteRequest.kt` 的 `runWriteRequest` / `jsonWriteRequest` 编排）。

| 错误码 | 含义 | 当前处理 |
| --- | --- | --- |
| `-352` | **风控拦截** | **绝不重试**：`RiskCooldown.onRiskControl()` 进入全局冷却（`riskCooldownMs`：60s 起、连续命中翻倍、上限 30min），冷却期内请求直接快速失败；任意成功清零 |
| `-412` | 请求被拦截（多为缺指纹） | 不重试，`authGate.invalidate()` 重新种植凭据 |
| `-111` | csrf 校验失败（仅写请求） | `CookieRefresher` 刷新一次后**重打一次**，仍失败则报错（绝不循环） |
| `-101` | 未登录 / 凭据失效 | 读请求：按普通失败返回；写请求：抛 `WriteError.NeedLogin`。⚠️ **「刷新 Cookie → 重试一次 → 登出」是设计目标但尚未接线**：`RetryAction.REFRESH_AND_RETRY` 目前没有调用方（待办见《功能优化篇》§10） |

`-352` 是风控信号而非凭据问题。碰到它就刷新凭据再打一次，会演变成「越被拦越猛打」，把临时限流推成长期封禁。这是本架构里少数几个**做错会主动伤害用户账号**的地方。

**主动降噪**（Phase B，见 [archive/07-风控加固-实现工单](archive/07-风控加固-实现工单.md)）：
- `RequestThrottle`：按 bucket 的全局最小间隔 + 抖动（搜索 800ms、动态 600ms、弹幕 1s、写 1s、消息 800ms、官方总结 800ms，抖动 300ms；常量在 `BiliRepository` companion）。
- `DeviceFingerprint`（per-install，持久化）+ `FingerprintCookies`（`b_nut`/`b_lsid`）。`_uuid`/`buvid_fp` 已实现但**有意不注入**（未做字节级取证）。
- 评论读取降级（`CommentReadPolicy`）、凭据来源选择（`CredentialSourcePolicy`）。

**WBI 签名不进拦截器。** 签名必须覆盖最终参数集，在调用点签好，返回 `Map` 用 `@QueryMap` 传入：

```kotlin
val params = WbiSigner.sign(
    params = mapOf("bvid" to bvid, "cid" to cid.toString(), ...),
    imgKey = credentials.wbiImgKey,
    subKey = credentials.wbiSubKey,
)
api.getPlayUrl(params)
```

### 3.3 Cookie 刷新（`CookieRefresher`）

```
1. GET  x/passport-login/web/cookie/info        → 是否需要刷新 + timestamp
2. 本地 RSA-OAEP 加密 timestamp                  → correspondPath（internal/CorrespondPath.kt）
3. GET  www.bilibili.com/correspond/1/{path}    → 解析 HTML 取 refresh_csrf
4. POST x/passport-login/web/cookie/refresh     → 新 Cookie + 新 refresh_token
5. POST x/passport-login/web/confirm/refresh    → 作废旧凭证
```

触发时机：**启动时检查一次**（`AppViewModel` 初始化，会话加载后、不阻塞 UI），以及写请求遇到 `-111` 时。`cookie/info` 撞 `-352` 时放弃刷新、保留现有登录态。公钥 `CORRESPOND_PUBLIC_KEY` 已配置，端到端刷新仍待真机长期验证。

## 4. 取流层

### 4.1 数据流

```
PlaybackRequest(bvid, cid, 音质偏好)
  ↓ ① 离线拦截（取流前、风控凭据前）——本地命中直接 file://，见 §4.5
  ↓ ② authGate.awaitReady()
  ↓ ③ 查 PlayUrlResolver 内存缓存（CACHE_TTL_MS = 100min；另按直链 deadline 与剩余时长判断能否复用，shouldReusePlayUrl）
  ↓ miss → playurl 接口（fnval=4048 fnver=0 fourk=1 voice_balance=1）
  ↓
PlayUrlResponse
  ├─ dash 存在       → 组装本地 MPD → MediaItem
  └─ dash 空、durl 有 → 单文件 MP4（音视频直链指向同一份）

下载（独立于播放路径，app/download/）：
  resolveForDownload → 音频轨直链 / 视频轨直链
  → DownloadService 前台服务流式写盘（Range 断点续传）→ 视频两条轨 MediaMuxer 合成 → 私有 / 公共 / SAF
```

**降级链**：`dash` → `durl`。`platform=html5` 第三级兜底**未实现**（代码注释：留到需要时再加）。  
播放中断后的重试与自动恢复会先 `invalidate` 缓存（失败多半是这份直链不能用了），恢复判定在 `PlaybackRecoveryPolicy` / `StreamLoadErrorPolicy`，CDN 健康度在 `CdnHostHealth`。

### 4.2 本地 MPD 组装 —— 无缝切看的地基

B 站返回的是 DASH 的 JSON 而非标准 MPD，由 `LocalDashManifestBuilder` 自行拼装喂给 Media3。

**硬性要求：manifest 必须同时包含音频和视频两个 `AdaptationSet`，无论当前是听还是看模式。** 这是无缝切轨的前提——两条轨在同一个 MediaSource 里，切换才不需要重建。

省流量靠的是禁用视频轨后 ExoPlayer 不请求视频分片，**不是**靠 manifest 里不放视频。额外开销仅为几百字节的元数据。

拼装要点：
- 每条流一个 `<Representation>`，内含 `<BaseURL>` 与 `<SegmentBase indexRange=…><Initialization range=…/></SegmentBase>`
- **URL 里的 `&` 必须转义**，否则 XML 解析直接崩
- 时长格式 `PT%.3fS`

### 4.3 音质 / 画质选择

策略在 `core/player/internal/QualityPolicy.kt`、`VideoQualityPolicy.kt`、`TrackSelectionPolicy.kt`（纯函数 + 单测），取流在 `PlayUrlResolver`，偏好经 `PlayerConnection.preferenceProvider` 注入。

三个独立音频来源，优先级由用户偏好决定：

```
dash.flac.audio    Hi-Res 无损（ID 30251，需大会员）— 单个对象，非数组
dash.dolby.audio   杜比全景声（ID 30250，需大会员）— 需 type>0 且 codecs 含 ec-3/eac3
dash.audio[]       普通 AAC 数组 — 按 bandwidth 排序
```

两个必须处理的边界：

1. **倍速 > 1.5x 时回退**：Hi-Res/杜比在高倍速下有兼容问题，自动降到 AAC 并给出提示（`QualityFallback`）。
2. **FLAC 解码器输入缓冲**：部分设备给 `c2.android.flac.decoder` 只分配 32 KiB，而 B 站 Hi-Res 单帧可能超过。`HiResCompatibleRenderersFactory` 把最小输入缓冲抬到 1 MiB（判定在 `FlacBufferPolicy`）。

⚠️ **验证口径**：开发者无大会员账号，无损 / 杜比的正向命中在真机上验不了；只验逻辑（`QualityPolicyTest` + `LosslessManifestTest`），验收记录里如实标注未验证。

响度均衡在 `LoudnessPolicy`（本地文件无响度数据 → 增益 1.0）。

### 4.4 离线取流拦截点

**不新增播放路径。** 在 `PlayUrlResolver.resolve()` 开头查本地下载库，命中就直接返回 `ResolvedMedia(uri = "file://…")`——续播、历史、队列、响度、音质显示全部不用动。

**拦截点必须在 `awaitReady()` 之前**：否则飞行模式下播放已下载的内容会卡在风控凭据上。

离线视频文件走同一条路：`file://` 的 MP4 音视频轨都在，「切看」照常工作；只下了音频的 m4a 看模式无画面——由 `PlaybackMode` 结构兜底，不特判。音质档位对本地文件无意义 → 播放页显示「本地文件」。文件被系统删除 → 播放前校验存在性，缺失则删表行并回落在线取流。

实现落点：`PlayerConnection.offlineLookup`（回调解耦）→ `PlayUrlResolver.offlineLookup` → app 层 `LibraryRepository.lookupOffline`（含 `resolveOfflineHit` 纯函数）。

## 5. 播放内核

### 5.1 播放器归属

**`PlaybackService`（`MediaSessionService` 子类）创建并持有唯一的 ExoPlayer 实例。UI 通过 `MediaController` 连接，外面包一层 `PlayerConnection` facade。**

```
┌─────────────── 同一进程 ───────────────┐
│  PlaybackService (MediaSessionService) │
│    └─ ExoPlayer  ← 唯一实例             │
│    └─ MediaSession                     │
│              ↑                         │
│         MediaController                │
│              ↑                         │
│   PlayerConnection (:core:player)      │  队列、续播、取流、会话持久化
│              ↑                         │
│   AppViewModel (:app)                  │  唯一 UI 侧状态持有者
│              ↑                         │
│   Compose 页面                          │
└────────────────────────────────────────┘
```

**硬性约束：Service 不声明 `android:process`，必须与 UI 同进程。** `MediaController` 同进程下会把 `setVideoSurfaceView()` 与 `setTrackSelectionParameters()` 转发到实际 player——这正是「原地切看 + 无缝切轨」的全部依赖。

**前台服务**：`FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK`，需准备 fallback 通知，否则 Android 14+ 会因前台服务启动超时崩溃。另有两个与播放无关的前台服务在 `:app`：`DownloadService`、`SummaryService`，彼此互不牵连。

选 `MediaSessionService` 而非 `MediaLibraryService`：后者要实现媒体库浏览回调（Android Auto），对「搜索驱动、无推荐」价值不大。

> **换内容时呈现态必须一并复位**（`resolvePresentationOnTrackChange`）：起播会禁掉视频轨，若呈现态还停在 `INLINE`，「视频轨启用 ⟺ 存在可见 surface」就被打破——表现为黑屏的 SurfaceView。PiP 例外。

### 5.2 播放模式状态机

**两个正交维度，而不是平铺的多状态**（类型在 `core/player/PlaybackModels.kt`，判定在 `PlaybackModePolicy`）：

```
播放态  PlaybackMode     { IDLE, AUDIO, VIDEO }
呈现态  PresentationMode { NONE, INLINE, FULLSCREEN, PIP }
```

**核心不变式：**

> **`PlaybackMode == VIDEO` ⟺ `PresentationMode ∈ {INLINE, FULLSCREEN, PIP}`**
>
> 等价表述：**视频轨启用 ⟺ 存在可见且已 attach 的 Surface**

`INLINE` 与 `FULLSCREEN` 从播放器角度完全相同，区别纯粹在 UI 布局。拆成两维后：不变式成为结构上的定义；全屏与 PiP 退化为纯 UI 变化；「PiP 不算进后台」的特例消失。

| 从 | 到 | 触发 | 副作用 |
| --- | --- | --- | --- |
| `IDLE` | `AUDIO` | 用户播放条目 | 取流、prepare |
| `AUDIO` | `VIDEO` | 呈现态从 `NONE` 变为非 `NONE`（用户点「看」） | 见 §5.3 序列① |
| `VIDEO` | `AUDIO` | 呈现态变回 `NONE`（点「听」／进后台无 PiP／锁屏／计量网络且未允许移动网络看视频（`VideoGatePolicy`）） | 见 §5.3 序列② |
| 任意 | `IDLE` | 停止 | 释放 |

呈现态之间的迁移不产生播放器副作用。音频焦点与两个维度都正交。

### 5.3 切轨时序

**① 进看模式**：attach SurfaceView → `setVideoSurfaceView` → 启用视频轨、清尺寸约束 → 等首帧 → UI 淡入。不 seek、不 prepare。  
**② 退听模式**：先禁用视频轨（`setMaxVideoSize(0,0)`）→ 再 `clearVideoSurface()` → UI 淡回封面。**顺序不能反**。  
**③ 回前台恢复画面**：attach 新 surface → 恢复轨道参数 → ⚠️ **不要 seek**（Media3 可能回退到前一个音频同步点，造成约 2 秒重复）。  
**④ 进 PiP**：保持视频轨启用，surface 交给系统 PiP，通知栏与 PiP 共用同一 MediaSession。

切换诊断：`PlayerConnection` 产出 `SwitchDiagnostics`（buffering / seek 计数），目前 UI 未展示（自检卡片为待办）。

### 5.4 队列、续播与后台

- **两层队列**：手动「加入队列 / 下一首播放」的条目固定（pinned），点击播放带入的条目是临时块、被下一次点击整体替换。规则全在 `QueuePolicy.kt`，详见 [10-播放队列工单](10-播放队列工单.md)。
- **续播**：`ResumePolicy`，位置本地持久化（`play_history`），会话在进后台时 `saveSession()`、启动时 `restoreSession()`（设置队列与位置，不自动播放）。不使用 B 站历史接口。
- **睡眠定时**：`SleepTimerPolicy`。
- **后台**：进后台且非 PiP 时关视频轨、清 surface。BiliPai 那套 `onTrimMemory` 内存压力分级**没有引入**。
- **弹幕**：已实现（`app/danmaku/`，读 `x/v2/dm/wbi/web/seg.so` protobuf，`DanmakuPolicy` / `DanmakuLayoutPolicy`），只在全屏播放器里渲染（`FullscreenPlayer`）。

## 6. 数据层

### 6.1 技术选型

**Room + KSP**，从第一版就建立迁移机制。当前 `BiliSeekDatabase` **version 7**，schema 导出到 `app/schemas/`（KSP 参数 `room.schemaLocation`），`MigrationTest`（instrumented）逐版本校验迁移。

### 6.2 落库边界

| 表（实体） | 版本 | 说明 |
| --- | --- | --- |
| `playlist` / `track` / `playlist_track` | v1 | 本地歌单及条目（用户资产） |
| `play_history` | v1 | 播放历史 / 进度：续播、热力图 |
| `search_history` | v1 | 搜索历史，上限 15（`SEARCH_HISTORY_LIMIT`），聚焦搜索框时弹出 |
| `download` | M9 | 下载记录与文件索引 |
| `favorite_folder` | v4（M11） | 收藏夹**目录**快照：音乐库秒开、断网目录可见；同步 = clear + 全量 upsert |
| `up_visit` | v5 | UP 访问记录，驱动动态页「常访 UP」行（`UpVisitPolicy`） |
| `ai_summary` | v6（v7 调整索引） | AI 总结索引与任务状态；正文 `summary.md` 按版本落盘在 `v{id}/` 目录 |

不落库：收藏夹**内容**、动态 feed、UP 投稿、关注列表、合集、稍后再看、消息、评论、搜索结果——全部内存缓存 + 分页。

设置不进 Room：`SettingsStore`（播放 / 下载 / 界面偏好）与 `AiSettingsStore`（API Key 经 `KeystoreCipher` 加密）。

**远程列表不落库的理由**：一旦落库就要处理增量同步、删除检测、冲突合并，复杂度翻几倍；收益只是离线能看到列表，但离线也播不了。收藏夹目录快照是唯一例外——它是元数据，量级与增删频率都低一个数量级。

### 6.3 「一切皆歌单」的落地

**统一抽象放在 UI 面向的状态层，而不是加载层。** 本地歌单走 Room 的 `Flow`；远程列表汇聚到 `app/data/RemoteListState.kt`：

- `TrackListId`：`Favorite(mediaId)`、`Uploader(mid)`、`WatchLater`、`Series(seriesId)`、`MessageReply`、`MessageLike`、`MessageFollower`、`PrivateSession`。
- `RemoteListState<T>`：分页 / 加载 / 错误的统一形状。动态 feed 同形状 + offset 游标。

加载机制不强求统一——**新增一种列表 = 新增一个数据源实现**，不改 UI。整张列表接着播（本地歌单 / 合集 / 稍后再看）走 `PagedQueueSource`（`app/remote/`），合集可自动续页。

**分 P**：搜索结果里一个 BV 折叠为一条；`videos > 1` 时展开各 P（分 P 面板 / `MultiPagePickerScreen`）。

## 7. UI 骨架与导航

### 7.1 结构

**单 Activity（`MainActivity`）+ Compose，导航用 Navigation Compose 稳定版**（不用 Navigation3 alpha）。

UI 侧状态由**单个 `AppViewModel`** 持有，内部按 feature 组合出若干 Controller（均为普通类，不是 ViewModel）：

| Controller | 包 | 职责 |
| --- | --- | --- |
| `SearchController` | `app/search/` | 搜索、分页、筛选、多 P 面板 |
| `DynamicFeedController` | `app/dynamic/` | 关注动态流、常访 UP |
| `RemoteLibraryController` | `app/remote/` | 收藏夹 / 合集 / 稍后再看 |
| `UpSpaceController` | `app/upspace/` | UP 空间、投稿 |
| `MessageCenterController` | `app/message/` | 消息中心、私信 |
| `CommentThreadController` | `app/comment/` | 评论 |
| `VideoInteractionController` | `app/interaction/` | 点赞 / 投币 / 收藏 / 三连 / 关注 |
| `EmoteController` | `app/emote/` | 表情包 |
| `SummaryController`、`AiSettingsController`、`AsrModelController` | `app/summary/` | AI 总结、AI 设置、识别模型 |

依赖注入为手写装配（无 Hilt），`AppViewModel` 在构造时串起 `BiliNetwork`、`PlayerConnection`、`LibraryRepository` 与各 Controller。

### 7.2 导航与持久播放器容器

```
Box
 ├─ Scaffold
 │   ├─ NavHost
 │   │   ├─ 底部 Tab：搜索 / 动态 / 列表 / 设置
 │   │   ├─ PLAYER（播放页，点视频 push、返回 pop）
 │   │   └─ UP 空间 / 关注列表 / 消息 / 回复与@ / 收到喜欢 / 新增粉丝 / 私信（push）
 │   ├─ MiniPlayer          ← 常驻底部，跨页面不销毁
 │   └─ NavigationBar       ← 四个 Tab
 └─ FullscreenPlayerOverlay ← 仅全屏时存在
```

（`Destination` 枚举在 `app/ui/AppShell.kt`。）

- MiniPlayer 挂在 NavHost 之外，页面切换不重建，播放不中断。
- **播放页自 M12-A 起是 NavHost 上的 destination**（此前是手写的展开状态机）；播放页内点「看」→ 封面区**原地**变为 SurfaceView，「退回听」始终是一步可逆的状态变更，不涉及返回栈。
- **全屏是 Scaffold 之上的 overlay**，入口是显式按钮；退出即销毁，无需恢复底部导航等状态。全屏与内联**不能同时渲染** `PlayerSurface`（同一 SurfaceView 只能有一个父容器）。全屏手势 / 面板策略在 `FullscreenPolicy`、`FullscreenGesturePolicy`。

### 7.3 各 Tab 内容

```
搜索（默认）  搜索框（聚焦时弹出搜索历史 15 条）+ 快捷入口 + 近一年（53 周）播放热力图；AV/BV/b23.tv 直达
动态          关注 UP 的动态流 + 常访 UP 行
列表          子 Tab：播放列表（本地）/ 收藏夹 / 合集；顶部入口：下载、AI 总结列表（Tab 内覆盖层）
设置          播放 / 网络 / 音质 / 画质 / 迷你播放器 / AI 总结（→ AI 设置页，含识别模型）/ 账号 / 关于
```

首页无算法推荐，但不空屏——全部是用户自己的行为数据。

## 9. AI 总结（0.4.1 起）

B 站相关的接线全在 `:app`（`app/summary/`），两个核心模块与 B 站无关：

- **`:core:ai`**：Provider 分「协议 × 预设」两层（v1 只有 OpenAI 兼容协议；MiniMax 国内 / 国际、自定义为预设），`Summarizer` 负责分块总结与合并（章节优先分块、每块断点落盘、换模型沿用已完成分块；`ChunkPolicy`、`ReasoningStripPolicy`、`PromptPolicy` 等）。
- **`:core:asr`**：只认「本地音频文件 → 带时间戳的句子」（解码 → 重采样 → Silero VAD → SenseVoice），带模型下载（断点续传 + 逐文件 SHA-256）/ 导入 / 校验。
- **`:app`**：`SummaryManager`（进程内单例、串行队列）+ `SummaryService`（前台服务）；原文来源按序：B 站官方总结 → 字幕（`BiliSubtitleSource`）→ 本机识别（`LocalAsrSource`，`LocalAsrPolicy`）；失败出路 `FailureActionPolicy`（在 `SummaryPolicies.kt`）；阅读页 `SummaryReaderScreen`、列表 `SummaryListScreen`。
- **网络隔离**：AI 与模型下载用自己的 `OkHttpClient`（不带 B 站 Cookie 与拦截器）；B 站侧请求仍走风控链路。
- **数据流**：入口 → 查一次官方总结与字幕 → 原文（落盘复用）→ 分块总结 → `summary.md`（每个版本一份）；Room 只存索引与任务状态。

设计取舍与实现记录见 [archive/10-AI总结-实现工单](archive/10-AI总结-实现工单.md) §8。
