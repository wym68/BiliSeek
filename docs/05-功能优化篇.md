## 2. 边界与约束

### 2.1 首启空状态保持现状

新用户无搜索历史、无最近播放，首页空状态只有一句 slogan。**不加引导页、不加内置示例搜索词。**

理由：「没有推荐」是产品身份（见《功能选型篇》§1）。写死的关键词 chip 也是一种编辑推荐——它和算法推荐的区别只是谁来选，不是有没有人选。新用户的上手路径由 M7 的**外部分享入口**承担，那是真实需求驱动的入口，不是我们替他挑内容。

### 2.2 数据库不动

M5–M7 所需字段（`TrackEntity.durationSec` / `coverUrl` / `PlaylistTrackEntity.sortKey`）在 v2 schema 里全都有。`BiliSeekDatabase` 保持 `version = 2`，**不新增迁移**。

### 2.3 每个里程碑都要留扩展位

后续功能（歌词、响度均衡、音质选择、下载导出）不在本阶段实现，但要在门面与 UI 结构上留好接入点，避免届时返工。具体见 §3.5。

### 2.4 大会员相关功能：先实现，只验逻辑

**开发者手上没有大会员账号。** 无损（Hi-Res / FLAC）、杜比全景声这类需要会员权限的能力，
在真机上永远只能走到「回退 AAC」那一支，正向路径实测无门。

口径定死为三条：

1. **照常实现，不因为验不了就搁置。** 缺的是账号，不是设计——B 站的接口、轨道结构、
   降级规则都是公开的，实现完整了，将来拿到账号就是「开一次看看」的事。
2. **验证降级为逻辑层**：纯函数单测 + 从轨道挑选到 MPD 组装的端到端断言。
   凡是能在没有账号的情况下判定对错的，都必须有测试钉住——**这是这类代码唯一的担保**。
3. **验收记录里如实标注为「未验证」，不写成通过。** 逻辑测试证明的是「按设计走对了」，
   不是「在真机上放出声了」。两者混为一谈，等于把没测的当测过的。

具体到 M8：

| 能力 | 逻辑验证 | 真机待验 |
| --- | --- | --- |
| 无损 / 杜比轨挑选 | `QualityPolicyTest`（含 type/codecs 校验、拿不到时回退 AAC） | 正向命中后声音确实是无损 |
| 无损进 MPD | `LosslessManifestTest`（挑对了**且真写进了 manifest**，视频轨不被挤掉） | 同上 |
| 倍速 > 1.5× 回退 | `QualityPolicyTest` + 模拟器实测缓存 key 变化 | — |
| FLAC 输入缓冲 | `FlacBufferPolicyTest`（只动 FLAC、不缩小、缺省值不漏抬） | 特定机型上不再 `Insufficient capacity` |

> FLAC 缓冲那条尤其典型：判定逻辑本可以埋在 `MediaCodecAdapter.Factory` 里没人看得见，
> 抽成纯函数**正是因为验不到真机**——实测无门时，至少让逻辑本身可被检验。

## 3. M5 — 播放器基本功

> 收口目标：进度条能拖、封面能看见、时长不再是 0、能定时睡觉、能调倍速。

### 3.1 seek

`PlayerConnection.kt` 新增门面方法：

```kotlin
fun seekTo(positionMs: Long)      // controller.seekTo，clamp 到 [0, duration]
fun seekBy(deltaMs: Long)         // 相对快进/快退，供后续通知栏按钮复用
```

**坑 1 —— 位置回写的节流。** `recordPositionIfNeeded()`（`PlayerConnection.kt:323`）有 5 秒节流且要求 `isPlaying`。用户拖完进度条立刻切后台被杀，位置会丢。`seekTo` 内部要把 `lastRecordedAt` 归零并强制回写一次。

**坑 2 —— 拖动被轮询覆盖。** `connect()` 里有个 250ms 的 `pushState()` 轮询循环。Compose 侧的 `Slider` 若直接绑定 `state.positionMs`，拖动过程中会被轮询值拽回去。UI 必须用本地拖动态：

```kotlin
var dragging by remember { mutableStateOf(false) }
var dragValue by remember { mutableFloatStateOf(0f) }
value = if (dragging) dragValue else state.positionMs.toFloat()
onValueChange = { dragging = true; dragValue = it }              // 只改本地
onValueChangeFinished = { seekTo(dragValue.toLong()); dragging = false }
```

**UI 落点**：`ExpandedPlayer` 加 `Slider` + 两端 `mm:ss` 文本；`MiniPlayer` 的 `LinearProgressIndicator` 保留为不可拖的细进度条。新增纯函数 `formatDuration(ms): String`（`mm:ss`，超一小时 `h:mm:ss`），配单测。

### 3.2 时长回写

`ResolvedMedia.durationMs` 目前只喂给了 MPD 组装，没有出口。

- `PlayerConnection` 新增回调 `var durationRecorder: (suspend (String, Long, Long) -> Unit)?`，与既有的 `resumePositionProvider` / `positionRecorder`（`PlayerConnection.kt:57-60`）并列——播放内核不认识数据库，这是现有的解耦惯例，照做。
- `play()` 中取流成功后调用它。

**坑 3 —— 不能复用 `recordPlay()`。** 它的 `positionMs` 参数默认 0，调一次就把续播位置抹平了。新增窄接口，照抄 `recordPlayPosition()`（`LibraryRepository.kt:89`）的写法：

```kotlin
suspend fun recordDuration(bvid: String, cid: Long, durationSec: Long) {
    val existing = history.find(bvid, cid) ?: return
    if (durationSec <= 0) return
    history.upsert(existing.copy(durationSec = durationSec))   // 不动 positionMs / playedAt
}
```

`TrackEntity.durationSec` 同样恒为 0（`AppViewModel.kt:122` 硬编码）。搜索结果里有现成的 `SearchVideo.duration` 字符串（形如 `"4:32"`），新增纯函数 `parseDurationText(text): Long` 到 `SearchInput.kt`（该文件已是解析类纯函数的归处），配单测覆盖 `"4:32"` / `"1:02:03"` / 空串 / 脏数据。

### 3.3 封面图

- 版本目录引入 **Coil 3**（`coil-compose` + `coil-network-okhttp`）。
- **坑 4 —— Referer。** B 站图片 CDN（`i0.hdslb.com`）对热链有校验风险。装配自定义 `ImageLoader`，其 OkHttp 复用 `BiliNetwork.mediaRequestHeaders`（`BiliNetwork.kt:63`，已含 UA / Referer / Origin）。这与 `PlaybackService.kt:37` 给 DataSource 注入请求头是同一个道理，不要重新发明。
- **`PlaybackRequest.Bili` 与 `PlaybackState` 目前都没有 `coverUrl` 字段**，需各加一个，否则展开播放器拿不到封面。`AppViewModel` 的三处构造点（`play` / `playPage` / `playPlaylist`）一并带上。
- 渲染落点：搜索结果行左侧 16:9 缩略图（`ResultRow`）、首页「最近播放」、歌单条目、以及 `ExpandedPlayer` 里那个黑框——现在纯音频模式下写着「纯音频模式」四个字，改成显示封面。

### 3.4 睡眠定时器与倍速

- 新增 `core/player/internal/SleepTimerPolicy.kt`：纯函数 + 数据类，描述「剩余毫秒」与「播完当前曲目再停」两种终止条件。与 `ResumePolicy` / `QueuePolicy` 的现有模式一致，配单测。
- 计时器状态**归 `PlayerConnection` 持有**，不放 ViewModel。理由与「播放器归 Service 持有」相同：用户设了定时器就会锁屏走开，状态不能绑 UI 生命周期。
- `PlaybackState` 增加 `sleepTimerRemainingMs: Long?` 与 `speed: Float`。倍速走 `controller.setPlaybackSpeed()`。
- UI：定时 15 / 30 / 60 分钟 + 播完当前；倍速 0.75× / 1.0× / 1.25× / 1.5× / 2.0×。

### 3.5 扩展位

`ExpandedPlayer` 的控制区目前是两个写死的 `Row`（`PlayerControls` / `QueueControls`）。改成由动作列表驱动渲染，后续「歌词」「音质」「下载」直接往列表里加项，不再改布局代码。

同时在门面上留好接口而**不实现**：

| 后续功能 | 已就位的东西 | 缺什么 |
| --- | --- | --- |
| 响度均衡 | `ResolvedMedia.measuredLoudness` 已在拿数据 | 应用侧的增益处理 |
| 音质选择 | `PlayUrlResolver.resolve(preferHiRes)` 参数已存在 | 从未被外部传过 `true`，且无 UI |

## 4. M6 — 等待与错误体感 + Cookie 刷新

> 收口目标：断网时秒级报错而不是 85 秒；错误能重试；不再周期性掉登录。

### 4.1 拆两类重试策略（最高性价比的一项）

**现状**（`AuthGate.kt:96-128`）：`ensureReady()` 整个函数体在 `mutex.withLock` 里，内含 `repeat(MAX_ATTEMPTS = 5)` 的指数退避（1s→2s→4s→8s→16s = 31s 纯等待，叠加 `connectTimeout 15s` / `readTimeout 20s` 后接近 85 秒）。用户主动点播放时排在后台预热之后，全程只能干等。

改法：

1. **两条路径分开预算。** `start()`（后台预热）走慢退避、次数多；`awaitReady()`（用户主动请求）走**快失败**——最多 1 次尝试、短超时，失败立刻抛异常。
2. **锁不覆盖退避。** `mutex` 只保护「检查状态 → 写入凭据」的临界区，`delay()` 必须在锁外，否则后台退避期间所有用户请求全被堵死。
3. **保留 `awaitReady()` 现有的核心语义**（`AuthGate.kt:77` 的注释说得很清楚）：失败要抛异常而不是继续挂起，且每次调用会重新触发一轮，网络恢复后用户再点一次即可自愈。这条别改坏了。
4. 退避判定抽成纯函数放 `internal/RetryPolicy.kt`（该文件已是这类策略的归处），配单测。

### 4.2 错误可重试 + 区分错误类型

- `BiliRepository.search()`（`BiliRepository.kt:25`）当前把所有失败都塞进 `Result.failure` 的 message 字符串里。引入 `sealed interface SearchError`：`Blocked`（-352 风控）/ `CredentialsInvalid`（-412）/ `NotActivated`（data 为 null）/ `Network` / `Empty`（code=0 但 0 结果）。
- `SearchUiState.error` 从 `String?` 改为该类型，UI 据此给出不同文案与**不同的可用操作**。

  > ⚠️ **`Blocked` 不给重试按钮。** `resolveRetryAction` 的 `BACKOFF_NO_RETRY` 语义就是绝不重试（见《架构设计篇》§3.2），UI 不能诱导用户猛戳，那会把临时限流推成长期封禁。

- **修白屏**：`showEmptyState` 条件补上「有关键词且 0 结果」的分支，渲染「没有找到『xxx』」而不是空白。
- `ExpandedPlayer` 的取流失败（`PlayerContainer.kt:207` 那行红字）补一个「重试」按钮。

### 4.3 Cookie 刷新（P0 遗留）

接口层已就绪（`BiliApi.kt:93-117`：`cookieInfo` / `cookieRefresh` / `confirmRefresh`，DTO `CookieInfoData` / `RefreshData` 也在）。新建 `core/network/CookieRefresher.kt`，补齐缺失的两步：

1. **`correspondPath`**：用固定 RSA-OAEP 公钥（SHA-256）加密 `refresh_${timestamp}`，输出 hex。纯函数，可单测。
2. **抓 `refresh_csrf`**：GET `https://www.bilibili.com/correspond/1/{correspondPath}`，从返回 HTML 里取 `id="1-name"` 元素的文本。`BiliApi` 需新增一个返回 `okhttp3.ResponseBody` 的方法——Retrofit 原生支持，不必为此加 HTML 转换器。解析用正则，抽成纯函数配单测（喂真实 HTML 片段）。
3. **完整链路**：`cookieInfo`（判断 `refresh == true`）→ 算 `correspondPath` → 取 `refresh_csrf` → `cookieRefresh` → 从响应头解析新 Cookie（**复用** `LoginManager.kt:112` 的 `parseSessionFromCookies`）→ `sessionStore.save()` → `confirmRefresh`（带**旧** refresh_token）。
4. **触发时机**：`AppViewModel.init` 中 `sessionStore.load()` 之后，若已登录则检查一次。不阻塞 UI，与 `authGate.start()` 同为后台任务。
5. **安全红线**：整条链路遇到 `-352` **绝不重试**，直接放弃并保持现有登录态。

> ⚠️ **验证需要真人先扫一次码。** MVP 收尾时登录完成态从未跑通（见《MVP 收尾总结》§5）。Cookie 刷新的真实验证只能在拿到真实 `refresh_token` 之后进行；在此之前只能验到纯函数单测 + `cookieInfo` 的响应。这一点会在验收记录里如实标注为「未验证」，**不当成通过**。

## 5. M7 — 搜索入口 + 歌单与队列

> 收口目标：从 B 站 App 分享过来能接住；加歌单能选；队列看得见、拖得动。

### 5.1 AV 号 / b23 短链直达

补齐 `AppViewModel.submitSearch()`（`AppViewModel.kt:168-183`）的 `else ->` 分支丢掉的两个 case：

- **`SearchIntent.VideoAid`**：新增纯函数 `avToBv(aid: Long): String`（B 站公开的 XOR + Base58 换表算法），放 `SearchInput.kt`，配单测（用几组已知 av↔BV 对照）。**本地换算，不多打一次网络请求**——与项目「不给服务端多余的行为特征」的取向一致。
- **`SearchIntent.ShortLink`**：需要展开重定向。`BiliApi` 加 `@GET suspend fun resolveShortLink(@Url url: String): Response<Unit>`，OkHttp 默认跟随重定向，从 `response.raw().request.url` 取最终地址，再喂回 `parseSearchInput()` 二次解析。**加防护**：只接受重定向落点在 `bilibili.com` 域内，否则退回关键词搜索。

### 5.2 接住外部分享（首次上手的关键路径）

`AndroidManifest.xml` 目前只有 LAUNCHER。给 `MainActivity` 加两个 intent-filter：

- `ACTION_SEND` + `text/plain`：接 B 站 App 的「分享到」。
- `ACTION_VIEW` + `https://b23.tv` / `https://www.bilibili.com/video/*`：接浏览器里的链接。

`MainActivity` 需处理 `onCreate` 与 `onNewIntent` **两处**入口（后者容易漏），把文本喂给已有的解析路径。

> 这是新用户第一次接触本 App 最可能的路径——从 B 站刷到一首歌，分享过来只听音频。§2.1 决定不做内置示例词，上手体验就由这个入口承担。

### 5.3 选择歌单对话框

`AppViewModel.addToPlaylist()`（`AppViewModel.kt:112`）现在是 `playlists.value.firstOrNull()` 硬选第一个。改为：VM 暴露「待加入的条目」状态，UI 弹 `AlertDialog` 列出全部歌单 + 「新建歌单」项，选定后再落库。`LibraryScreen.kt:157` 已有 `NameDialog`，新建分支直接复用。

### 5.4 长按操作菜单

搜索结果长按现在直接加歌单（`MainActivity.kt:102`）。改为弹 `ModalBottomSheet`：加入歌单 / 下一首播放 / 复制链接 / 查看分 P。

「下一首播放」需要 `PlayerConnection` 新增 `enqueueNext(request)`——队列是本类私有的 `List<PlaybackRequest>`（`PlayerConnection.kt:52`），插入后要同步修正 `queueIndex`，这段逻辑抽进 `QueuePolicy.kt` 配单测。

> 后续：点击播放不再整队替换，改为两层队列（固定 / 临时），见 `docs/10-播放队列工单.md`。

### 5.5 队列列表 + 拖拽重排

- `PlaybackState.queue` 已经带着完整队列了，UI 只显示了「队列 N / M」。加一个可展开的队列面板：列出全部、高亮当前、点击跳转（`PlayerConnection` 加 `skipToIndex(i)`）。

## 9. M9 — 下载（音频/视频）与离线播放，外加四项打磨

> 版本：规划稿（2026-08-28）  
> 收口目标：没网也能听/看自己下过的东西；下载时可选「只音频」或「视频」，保存位置可选；顺手清掉四个挂了很久的小项。

### 9.1 为什么是这件事

到 M8 为止，BiliSeek **对网络是全依赖的**：缓冲耗尽就只能卡住。真机 Part C 验过「出电梯自动续上」，
但那验的是「网络回来之后」——地铁、飞机、信号盲区里，这个 App 现在等于不能用。
而它的定位恰恰是「装进口袋里听」。

另外两条理由：

1. **这是选型篇 P1 待办里唯一还没动的大件。** 收藏夹同步、莫奈取色都可以再等，
   离线不能——它决定的是「能不能在通勤路上用」。
2. **音频下载成本很低，视频下载也不用 ffmpeg。** DASH 音频轨本身就是完整的 M4A/AAC 文件，
   **下载即完整文件，无需转码**。视频下载则要额外把「音频轨 + 视频轨」合成一个 MP4——
   但这一步**只做封装（mux）、不做重编码**，用 Android 自带的 `MediaMuxer` 即可，
   不必像 biu 那样打包四平台 ffmpeg。所以「音频 / 视频」两种下载并存，
   成本上仍是可控的切分，不破坏「轻量、无原生代码」的约束。

### 9.2 边界与约束

**下载内容二选一、保存位置三选一，两者正交。** 原来的「下载 vs 导出」两分法被「位置」
一个维度取代——不再有独立的「导出」动作，下载时直接选位置。

**下载内容：**

| 内容 | 产物 | 说明 |
| --- | --- | --- |
| 只音频 | `.m4a` | DASH 音频轨即完整文件，无需转码，直接落盘 |
| 视频 | `.mp4` | 音频轨 + 视频轨分开下载，`MediaMuxer` 合成（只封装、不重编码） |

**保存位置：**

| 位置 | 去向 | 语义 | 权限 |
| --- | --- | --- | --- |
| 应用私有目录（默认） | `files/downloads/` | 给**离线播放**用，卸载即清，不污染用户媒体库 | 不需要 |
| 公共媒体库 | 音频 `MediaStore.Audio`（`Music/BiliSeek/`）、视频 `MediaStore.Video`（`Movies/BiliSeek/`） | 给**用户**用，能被别的播放器看到，卸载后仍在 | API 29+ 不需要；API 26–28 需 `WRITE_EXTERNAL_STORAGE` |
| 自定义目录 | SAF `ACTION_OPEN_DOCUMENT_TREE` 选任意文件夹 | 用户指定位置 | SAF 授权（`takePersistableUriPermission`）即可，无需运行时权限 |

其余约束：

- **视频下载是「封装」不是「转码」。** 只用 `MediaMuxer` 把两条已下好的轨合成 MP4，
  不重编码、不引 ffmpeg、不加原生代码。与 biu 打包 ffmpeg 的做法有本质区别。
- **不做自动预下载 / 批量爬取。** 只下用户明确点的那条或那个歌单。自动预取既是「替用户决定」，
  也平白增加请求特征，与「不给服务端多余的行为特征」的一贯取向冲突。
- **下载请求必须带与播放同一套请求头**（`BiliNetwork.mediaRequestHeaders`）。B 站 CDN 校验 Referer，
  不带就是 403——这个坑在封面图（M5）和播放（M0）上各踩过一次，别踩第三次。
- **数据库升到 v3**，必须写迁移与迁移测试。表行要记录**保存位置**（私有 / 公共 / SAF 的 uri），
  离线库据此知道去哪找文件、删表行时是否要连文件一起删。框架 M3 就建好了
  （`app/schemas` + 仪器化迁移测试），照用。

### 9.3 下载：从取流到落盘

**取直链。** `ResolvedMedia`（`PlayUrlResolver.kt:10`）现在只对外给一个 MPD 的 data URI，
下载需要的是真实轨道 URL。轨道其实早就挑好了——`collectTracks` 返回的 `audios` / `videos`
第一条就是目标（M8 已按音质档位排好序），只差把它们带出来：给 `ResolvedMedia` 加
`audioUrl` 与 `videoUrl` 两个字段（视频轨还带 codec / 宽高，供 mux 时写容器元数据）。

**下载档位复用 M8 的 `AudioQuality`**：`SAVER` 下小文件，`AUTO` 下最高码率 AAC。
视频清晰度 M9 先取 DASH 里**最高可用视频轨**，不单独做清晰度档位——那是 P2 的事。
不必为下载再发明一套音质选择。

**下载器**：OkHttp 流式写盘 + `Range` 断点续传。

- 只音频：单条流，落点 `files/downloads/{bvid}_{cid}.m4a`——文件本身就是完整 fMP4，
  **改个扩展名就能播，不转码**。
- 视频：音频轨 + 视频轨**两条并行下载**（各自断点续传），下完用 `MediaMuxer` 合成
  `{bvid}_{cid}.mp4`。mux 是纯封装、不重编码，AAC + H.264/HEVC/AV1 都能进 MP4。
  mux 失败（轨不完整 / codec 不支持）时**保底**：删除半成品并报「下载失败，可重试」，
  不留一个只有声音或只有画面的文件。

**保存位置决定写入路径**：

- 私有目录：直接写 `files/downloads/`。
- 公共媒体库：`MediaStore.Audio`（`RELATIVE_PATH = Music/BiliSeek/`）或
  `MediaStore.Video`（`RELATIVE_PATH = Movies/BiliSeek/`）。
- 自定义目录：SAF `DocumentFile` 写用户选的树；`takePersistableUriPermission` 拿持久授权，
  下次重进 App 不必重选目录。

**前台服务** `DownloadService`：与 `PlaybackService` **分开**。播放服务不该被下载任务拖住生命周期，
两者的存活条件也不同（播放跟着用户听，下载跟着任务队列）。
需要新权限 `FOREGROUND_SERVICE_DATA_SYNC`（Android 14+ 强制声明类型）。

封面与元数据内嵌（BBPlayer 的 `ExportDownloadsHelper.kt` 有现成实现，MIT 可直接搬）**放到 P2**，
M9 只保证「文件可播 + 文件名可读」。

### 9.4 离线播放：只加一个拦截点

**关键设计：不新增播放路径。** 在 `PlayUrlResolver.resolve()` 开头查本地，命中就直接返回
`ResolvedMedia(uri = "file://…")`。这样续播、播放历史、队列、响度均衡、音质显示**全部不用动**——
它们看到的仍是一个普通的 `ResolvedMedia`。

> ⚠️ **拦截点必须在 `awaitReady()` 之前。** `resolve()` 现在第一行就是
> `network.authGate.awaitReady()`（`PlayUrlResolver.kt:43`）。写在它后面的话，
> 飞行模式下播放已下载的歌会卡在风控凭据上——**离线功能被自己的风控 gate 挡住**，
> 这是这块最容易写反的一处。

离线视频文件走同一条路：`file://` 的 MP4 里音视频轨都在，「切看」照常工作；只下了音频的 m4a
则只有音轨、看模式无画面——由 `PlaybackMode` 结构兜底，不用特判。

四个边界要显式处理：

| 边界 | 处理 |
| --- | --- |
| 本地文件没有响度数据 | `loudnessGain(null, null)` 已经返回 `1.0f`，现有策略天然覆盖，不必特判 |
| 音质档位对本地文件无意义 | 播放页音质行显示「本地文件」，而不是谎报「自动」 |
| 只下了音频的 m4a 没有视频轨 | 看模式自然无画面，播放页维持「纯音频」呈现，不崩、不特判 |
| 文件被用户在系统里删了 | 播放前校验存在性，缺失则回落在线取流并把表行标为失效——不能只报「播放失败」 |

`PlaybackService` 的 `DefaultDataSource.Factory`（`PlaybackService.kt:40`）本来就同时支持
`file://` 与 http，播放侧一行都不用改。

### 11.2 核心设计决策

1. **收藏夹目录落库、内容不落库**（《架构设计篇》§6.2 落库边界）——目录很小（秒开、断网可见、显示同步时间），内容量大且易变（增量/删除/冲突收益近零）。
2. **一切皆歌单**：收藏夹内容、UP 投稿收敛到同一个 `RemoteListState<T>` 状态形状，UI 只依赖来源无关的状态，新增列表 = 新增数据源，不改 UI。
3. **登录非强制**：未登录时收藏夹 / 动态分区内嵌 `LoginPanel` 引导，搜索与播放完全不受影响。

### 12.3 M12-B Compose UI 测试（36 例全绿）

3. 封面取色用 `androidx.palette:palette-ktx`（官方小库，BBPlayer `image-theme-colors` 的等价实现）。

### 13.2 用 B 站 App 一键登录

**需求**：Web 扫码登录生成二维码的同时，加一个按钮自动唤起手机中已安装的哔哩哔哩 App 完成扫码确认。

**实现**（`app/.../LoginScreen.kt` + `AndroidManifest.xml`）：

- `QrReady` 状态加「用 B 站 App 一键登录」按钮，点击后 `Intent(ACTION_VIEW, qrUrl).setPackage("tv.danmaku.bili")` 唤起官方 App
- 官方 App 的 `IntentHandlerActivity` 处理 `account.bilibili.com` 域（`.bilibili.com` 通配 intent-filter），在 App 内 WebView 弹出扫码确认页
- 用户在 B 站 App 点确认 → 服务端标记成功 → 我们既有的 2s 轮询自动收到 `code=0` 完成登录
- Manifest 加 `<queries><package android:name="tv.danmaku.bili" /></queries>`（Android 11+ 包可见性）
- 失败兜底：`ActivityNotFoundException`（未安装）→ Toast「未找到哔哩哔哩 App」；`SecurityException` → Toast 提示手动扫码

**设计要点**：`setPackage` 避免浏览器抢选择框；不改轮询逻辑（登录成功自动收敛）；不引入 `QUERY_ALL_PACKAGES`。

**验证**：真机 ColorOS 首次唤起会弹「应用启动确认」（系统级，选 30 天内允许后免打扰）；B 站 App 打开 `MWebActivity` 显示含 BiliSeek logo 的扫码确认页；轮询日志确认后台持续 `qrcode/poll`。

### 13.5 锁屏 / 通知栏封面（MediaSession artwork）

**需求**：手机锁定时播放，锁屏媒体卡片只有默认音符图标、没有封面。

**实现**（`core/player/.../PlayerConnection.kt` + `app/.../AppViewModel.kt`）：

### 13.12 真机验证说明（风控 -111 环境问题）

**现象**：2026-08-30 晚，真机所有网络请求失败——`GenWebTicket 失败: code=-111`（搜索、稍后再看都不可用）。

**分析**：
- B 站官方错误码表无 -111 公开定义；社区经验指向「csrf 校验失败」，但在本项目场景（csrf 可空、几小时前同代码正常）不成立
- 更合理：B 站服务端对该请求环境（IP / UA / 设备指纹组合）的**临时风控拒绝**，与 -412 同类

**影响**：风控凭据是所有网络请求的前置（搜索/动态/稍后再看/收藏夹都依赖），-111 期间全部不可用。**不是代码 bug**——请求路径、错误捕获、重试按钮都符合预期。

**排查建议**：等 30 分钟~几小时（临时风控过期）；切 WiFi ↔ 移动数据（换 IP）；冷启动一次（`AuthGate.invalidate()` 清旧凭据重种）；换设备排除设备指纹标记。

**需求**：搜索页播放热力图横纵没有标月份和星期几。参考 BBPlayer（com.roitium.bbplayer）主页热力图设置。

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 格子 | 14dp / 间距 3dp / 圆角 3dp | **18dp / 间距 4dp / 圆角 4dp**（BBPlayer 主页参数） |
| 星期侧边栏 | 中文「日/一/二/三/四/五/六」 | **英文「Sun/Mon/Tue/Wed/Thu/Fri/Sat」**（labelSmall 英文 ddd 简写，无句点） |
| 月份表头 | 中文「6月/7月」 | **英文「Jun/Jul/Aug/Sep」**（`DateTimeFormatter.ofPattern("MMM", Locale.ENGLISH)`，无句点） |
| 初始滚动 | 左侧 | **滚到右端**（`rememberLazyListState` + `LaunchedEffect { scrollToItem(weeks-1) }`，同步无动画） |
| 窗口 | 13 周（近 3 个月） | **53 周（近一年）**，可横向滚动看更早历史 |

**设计要点**：

- **月份 formatter 用 `Locale.ENGLISH`**：dayjs 的 `MMM` 在不同 locale 下输出不同（zh-cn 输出「1月/2月」），Compose 的 `DateTimeFormatter` 同样。锁定 `Locale.ENGLISH` 才能保证输出「Jan/Feb/.../Dec」英文简写。`remember` 缓存避免 recomposition 重建。
- **月份无句点**：与 BBPlayer `MMM` 输出一致（「Aug」而非「Aug.」）。早期加过句点，用户反馈偏离 BBPlayer 标准简写，已去。
- **星期/月份文字不设宽度约束**（真机反馈修复）：侧边栏 `Column` 原 `width(10.dp)` 把「Sun」裁成「S」；月份表头原 `width(18.dp)` 同理可能裁「Aug」。改为只约束 `height(18.dp)`（与格子行高对齐），宽度自适应文字——「Sun」约 68px、「Wed」约 84px@4x，文字 100% 完整显示。月份「Aug」窄于格子 18dp，不会掉宽列；文字向左对齐后向右溢出到后续空表头列（BBPlayer SVG 表头同款跨列效果）。
- **窗口一年**：`HEATMAP_DAYS = 91 → 365`，`weeks` 默认 13 → 53。数据源 `observeHistorySince(cutoffMs)` 拉一年 play_history 按 `LocalDate` 本地日期聚合（数据量 ~2000 行，无压力）。

**验证**：真机像素扫描确认格子 68px@4x≈17dp（圆角切 1dp），列节距 88px=22dp，行节距 88px。星期侧边栏 7 个标签宽度 46-84px（多字母完整），「Sun」S-u-n 三字母像素清晰可辨。月份 Jun/Jul/Aug/Sep（无句点）uiautomator 确认。点击今天格子（8/30）→ 日历史页 22 条记录。`./gradlew :app:testDebugUnitTest` 全过，编译装机成功。

**过程中的反复（记录为准）**：先按用户「窗口保持近 3 个月」实现 13 周；随后用户反馈「不能向右滚动查看更久历史」→ 扩到 53 周一年；简写格式经历「中文单字 → 英文+句点(Aug.) → 英文无句点(Aug)」三次迭代，最终与 BBPlayer `MMM`/`ddd` 完全一致。

### 13.16 播放队列：两层队列、列表来源播放、右滑删除与撤销

**需求**：点击播放一个视频会清空队列，只有「加入队列」「下一首播放」是往队列里加，很容易误把攒好的队列冲掉。

- **两层队列**：「加入队列」「下一首播放」加的是**固定**条目，点击播放永远不删；点击带进来的是**临时**条目，

  列表里的视频进队列只占一项，**轮到播放时**才取分 P 原地展开，一次只为真正要播的那条发请求。
- **队列面板**：70% 屏高、无拖动条、打开定位到当前项；清空按钮常驻标题行（早先在列表下方，长队列时被挤出屏幕）；

### 13.29 首页「热门播客」入口（2026-10-02）

设计稿：[home-podcast](superpowers/specs/2026-10-02-home-podcast-design.md)。补做 §13.28 里搁置的热门播客。

- **它是什么**：官方 App 热门页的「热门播客」入口，分享出来是运营搭建的 H5 活动页 `blackboard/era/fuwAmTrtqFLexuSx.html`（App 端走 gRPC，不走）。用户用 App 同款 UA 存下真实页面核实：HTML 里内嵌 `window.__BILIACT_EVAPAGEDATA__`，其中一个 `EvaTabs` 下有 63 个标签面板（「第63期」…「第1期」，最新在前），每期一个编辑推荐卡，10–21 个 `{"bvid": …}`；**只有 BV 号，没有标题封面**。
- **入口与页面**：首页第四张卡片「热门播客」，进入榜单页；顶栏下多一排期数选择条（`FilterChip`，默认最新一期），点哪期看哪期；列表行与其他榜单一致，点条目整期作临时队列起播，副标题「N 个视频」。
- **取数**：打开 = 取页面 HTML 1 次 + 当期卡片 1 次；切到没看过的期只多 1 次卡片请求；看过的期缓存在内存，关闭或下拉刷新时清掉。卡片用 `GET x/article/cards?ids=BV…,BV…`（社区文档：可传 BV，只要 `Referer`，不要 WBI，一次一期），按卡片里的 `bvid` 对应。页面请求限定 `bilibili.com` 域、套 `FEED` 桶、冷却期快速失败，HTTP 412 当被拦（记冷却、不重试），其他非 2xx 报「页面加载失败」。
- **解析**：`core/network/internal/EraPagePolicy.kt`，不写死层级路径——找所有 `EvaTabs.Panel`，标签取 `props.tabItem.tabItemProps.textContent.content`，BV 取面板内所有合法 `bvid`；没有标签面板时退化成一组「全部」；JSON 用认字符串与转义的括号配对取出，不靠 `;` 定界。解析不出时显示「热门播客页面结构变了，没能解析」，不白屏。解析器与 `videoCards` 都是通用的，之后「b23 短链展开成活动页时列视频」可复用，本次不接。
- **结构**：`:core:network` 新增 `EraGroup`、`resolveCardItems`、仓库方法 `podcastIssues()` / `videoCards()`、接口 `eraPage` / `articleCards`；`:app` 的 `ChartKind` 加 `PODCAST`，`ChartState` 加 `issues` / `selectedIssue`，`ChartController` 加 `selectIssue`，`ChartScreen` 加期数选择条。
- **风险**：只绑定这一个活动页，运营换页（网址变）或改版（组件结构变）就失效；`x/article/cards` 只来自社区文档。
- **验证**：`EraPagePolicyTest`（10 例，样例取自用户存下的真实页面，裁剪成 3 期 × 3 个 BV，保留真实嵌套结构）、`ChartPolicyTest` 新增 3 例、`ChartDtoTest` 新增 1 例（卡片响应按文档手写，**没对照过真实响应**）；`./gradlew test assembleDebug` 通过（`:core:network` 326 例、`:app` 288 例全绿）。**未验证**：真机上热门播客页能否取到并解析、`x/article/cards` 的真实返回与限制、期数选择条与切换、标题封面显示、点条目起播、断网重试。

### 13.30 搜索框：活动页列视频 + 收紧 av 号（2026-10-02）

设计稿：[search-era-and-av](superpowers/specs/2026-10-02-search-era-and-av-design.md)。接上 §13.29 留的口子（解析器通用）。

- **一次额外请求**：展开短链时 App 本来就把落点页面下载了一遍但没保留，榜单页再走自己的取页面（限速、冷却、HTTP 412 处理）取一次。只发生在「短链落到活动页」这条少见的路径上。
- **收紧 av 号**：只认整段输入就是 `av170001`（不分大小写）、或文本里带 `/video/av170001`（后面可跟 `/`、`?`、`.html`），数字须大于 0。不再认：纯数字（搜「2024」不再去播 av2024）、`av` 后带空格或字母、链接里别的 `/数字/`（UP 收藏夹 `…/12345/favlist` 不再被当成 av12345）、`aid=`。
- **验证**：`SearchInputTest` 新增 9 例（av 大小写、视频页网址、纯数字、`favlist` / `cv` 链接、`avatar2024` 等；活动页网址规整、`m.` 站与 `http`、分享文本里挑出、`activity-xxx` / 别的域名 / `bilibili.com.evil.com` 仿冒域名不算），`EraPagePolicyTest` 新增 2 例（`<title>`）；`./gradlew test assembleDebug` 通过（`:core:network` 337 例、`:app` 288 例全绿）。**未验证**：真机上搜活动页短链与直接粘贴网址的完整流程、榜单页标题与期数条、清空搜索框后的返回行为；其他 era 页面如果结构不同，会走「没能解析」的错误提示。

### 13.31 搜索框：「这个链接不是视频」提示（2026-10-02）

- **起因**：§13.30 之后，b23 短链展开后既不是视频也不是活动页（如指向 UP 空间、专栏），仍退回「拿链接原文当关键词去搜」，用户看到的是毫不相干的搜索结果或「没有找到」。用户选了「明确提示」。（§13.30 里「行为不变」那一条由本节取代。）

### 13.35 动态页按 UP 筛选：选中 / 取消时的下方提示（2026-10-02）

设计稿：[dynamic-up-filter-notice](superpowers/specs/2026-10-02-dynamic-up-filter-notice-design.md)。

- **起因**：动态页「最常访问」里点 UP 头像可以只看这个 UP 的动态，再点取消筛选，但只有头像上一圈主题色环，没有文字提示。用户要求选中和取消的时候，在下方用浮框提示。
- **提示**（用户选定）：选中某个 UP（含从 A 直接切到 B）→「只看「X」的动态」；取消筛选 →「已取消筛选」；筛选没变化不提示。
  **UP 主名字太长时截断、用省略号代替放不下的部分**（用户要求）：系统 Toast 自己不会给省略号，所以拼文字时就截——按显示宽度算（码点 ≥ U+2E80 的全角字符算 2、其余算 1），
  名字宽度超过 20（约 10 个汉字）就保留宽度 ≤ 19 的前缀再接「…」，按码点切，不会切坏 emoji；首尾空白去掉，名字为空时「只看这位 UP 主的动态」。
- **通道**：不走全局消息管道（它逐条排队，连点头像时提示会滞后）。`DynamicFeedController` 暴露 `filterNotice`（缓冲 1、满了丢最旧的），
  `MainActivity` 收集后用「先取消上一条再弹」的系统 Toast，连点只留最新一条。这个写法抽成 `showReplacingToast(text)`，与未登录点头像的提示（§13.27，原来的 `showLoginHint` 里那段）共用一个「上一条」引用。
  系统 Toast 在下方，Android 12 起是白底胶囊 + App 图标；不带按钮的普通提示按项目约定就用它。
- **纯函数**（`dynamic/DynamicFilterPolicy.kt`）：`resolveUpFilterChange(selectedMid, up)` 给出点头像后筛选怎么变（`Select` / `Clear` / `null` = 没变化），
  规则就是 `selectDynamicUp` 里原来的写法原样搬出（行为不变）；`upFilterNotice(change)` 给出提示文字（含截断）。
- **验证**：先写测试并确认编译失败（RED）再实现；新增 `DynamicFilterPolicyTest`（11 例：选中 / 再点取消 / A 切 B / null 有无筛选；提示文字的正常名、空白名、恰好在上限、超长中文、超长英文、中英混排、emoji 不被切坏）；
  `./gradlew test assembleDebug` 通过（`:core:network` 341 例、`:app` 307 例全绿），并确认新代码已编进 debug APK。
  **未验证**：真机上提示的位置、一行放不放得下（宽度上限 20 是估的，不合适调 `MAX_NOTICE_NAME_WIDTH`）、连点时是否确实只显示最新一条。

> 后续（2026-10-07 按代码核对）：提示在 §13.60 改为前台走 App 内提示（`AppToast`，在迷你条上方），只有后台 / 小窗 / 别的弹层盖着主界面时才用系统 Toast；`showReplacingToast` 现在也发到这条管道，连点仍只留最新一条。

  - 两类撤销提示共用一个位置，新提示出来先收起旧的。队列那边的收集也加了同样一行，免得排队把撤销时间耗掉。
  - aid 用 `resolveAid`：有 aid 用 aid，否则用 bvid 本地换算，都不行按失败处理。**绝不把 null 交给 `delToView`**，那是「清空所有已看过的」。
- **收藏夹翻页（这次顺带修）**：
  - 问题：删过条目后，服务器上的序号前移，按「页码 + 1」翻页会漏条。
  - 改为：按「列表里的条数 + 正等着提交的条数」算该取哪一页（`favoriteFetchPage`），新一页按 bvid 去掉已有的和正等着移除的（`appendUnseen`）。
  - 自动加载的触发键从页码改成条数：重取同一页时页码不变，按页码不会再触发。
  - 一页取回来没有新条目时停止自动加载，免得一直转圈。
- **顺带修的原有问题**：收藏夹内容页、合集内容页的「滚到底自动加载」在加载失败后会立刻再次触发，等于对 B 站不停自动重试（CLAUDE.md 禁止）。现在失败后不再自动加载，只等用户点「重试」。
  合集**列表**页底部的自动加载有同样的问题（失败后 `LaunchedEffect(Unit)` 重新进入组合就再打一次），当时没动；用户确认后在 §13.41 修了。

### 13.40 当日听歌时长改为真实收听时长；热力图只显示到今天（2026-10-04）

- **起因**（用户原话）：
  - 热力图点进某一天，播放记录上方的当日听歌时长只是把条目时长加起来，不是真实的收听时长。
  - 热力图显示完整的横竖方格，还没到的日期不该显示，只显示到今天。
- **根因**：
  - **听歌时长**：`DayHistoryScreen` 用 `entries.sumOf { it.durationSec }`，把当天播过的视频的**完整时长**相加。`play_history` 对 (bvid, cid) 唯一，每个视频只有一行、只记最后一次播放的时间和进度，根本没有「实际播了多久」的数据。
  - **热力图**：最后一列用 `today.with(DayOfWeek.SUNDAY)` 定。java.time 的周是周一到周日，这个调用拿到的是本周**结束**那天的周日，于是：
    - 每列其实是「周一 → 周日」，却按「周日、周一……周六」从上往下画。顶上那格周日比底下的周六还晚一天，按时间读是错位的。
    - 最后一列把今天之后的几天也画了出来（为了列高对齐，渲染成底色、还能点）。
    - 只藏掉未来格子不够：周一时最后一列顶上会空一格，前一天的周日跑到前一列最上面，所以排法要一起改。
- **真实收听时长**：
  - 新表 `listen_day(epochDay 主键, listenedMs)`，DB 升到 **v8**（`MIGRATION_7_8`，schema `8.json`，`MigrationTest` 补了 7→8）。
  - 计时：`ListenTimeTracker`（AppViewModel 持有）看 `PlayerConnection.state` 的 `isPlaying`。开始播放就计时，停下（暂停 / 缓冲 / 停止）就结算，播放中每 30 秒结算一次落库（进程被杀最多丢 30 秒）。
  - 判断都在纯状态机 `ListenClock` 和 `splitByLocalDay`（`data/ListenTimePolicy.kt`）里：
    - 时长用单调时钟（开机时长）量，不受改系统时间影响；归到哪天用墙钟。
    - 跨零点的一段按毫秒分到两天。
    - 倍速按实际过去的时间算，也就是「你花了多久听」。
  - 累加分两步（`INSERT OR IGNORE` 再 `UPDATE … + ms`），包在一个事务里：minSdk 26 的 SQLite（3.18）不支持 `ON CONFLICT DO UPDATE`。
  - 日播放记录页显示这个数。那天没有记录（更新之前的日子）显示「未统计」，不再拿完整时长相加充数。
- **热力图**：
  - `ui/HeatmapPolicy.kt`：`heatmapLastWeekStart` 取今天或之前最近的周日，`heatmapCellDate(today, weeks, column, row)` 给出每格日期（列 = 周日 → 周六，连续），`heatmapCellShown` 表示今天之后不画。
  - `WeeklyHeatGrid` 改用它们，未来格子换成同样大小的空位（列高不变、不能点）。
- **验证**：
  - 先写测试并确认编译失败（RED）再实现：`HeatmapPolicyTest` 6 例（各星期几的最后一列、未来不画、列内与跨列连续、第一列），`ListenTimePolicyTest` 9 例（同日、跨零点、零时长；计时 65 秒、定时结算不多不少、暂停不算、没在播不记、重复开始不重置、跨零点）。
  - `./gradlew test assembleDebug :app:compileDebugAndroidTestKotlin` 通过（`:app` 343 例全绿）。核对过生成的 `8.json` 建表语句与迁移一致；`MigrationTest` 只做编译核对，没在设备上跑。按用户要求没有装机。
- **没改、要知道的**：
  - 日播放记录页的**列表**和热力图的**颜色深浅**仍来自 `play_history`，含义是「最后一次播放在这天的视频」：一个视频今天又播了，它就从之前那天的列表和格子里挪到今天。
  - 当日听歌时长不受这个影响，按天如实累计。所以「列表里的视频」和「这天听了多久」可能对不上。要不要改由用户决定。
- **未验证（要真机看）**：热力图最后一列的样子（今天是周几就显示到第几行）；听几分钟后进当日记录看时长是否大致对得上；跨零点播放；更新前的日子显示「未统计」。

### 13.41 列表滚到底的自动加载：失败后不再自动重试（2026-10-04）

- **起因**：§13.39 实现时发现，用户确认要修。
- **根因**：「列表」页合集分区底部的 `series-load-more` 只看是否在加载（`isLoadingMore` 转圈，否则 `LaunchedEffect(Unit)` 加载下一页）。
  - 加载失败后 `isLoadingMore` 变回 false、`hasMore` 仍为 true，自动加载重新进入组合，立刻又打一次 `x/v3/fav/folder/collected/list`，一直到成功为止。

- **修法**：
  - 新增纯函数 `shouldAutoLoadMore(hasMore, isLoadingMore, errorMessage)`（`ui/LoadMorePolicy.kt`）：还有更多、没在加载、上次没失败才自动加载。
  - 合集列表页底部改为三种状态：加载中转圈、可以自动加载就加载、失败就显示错误文字和「重试」（与收藏夹 / 合集内容页的底部一致）。
  - §13.39 修过的收藏夹内容页、合集内容页也改用这个函数，条件写在一处。
- **同类问题（用户确认一起修）**：下面 4 处底部是同样的写法（`if (hasMore && !isLoadingMore) LaunchedEffect(…) { onLoadMore() }`），对应控制器失败后同样保留 `hasMore`、只写 `errorMessage`，所以也会失败后自动重试：
  - UP 空间的投稿（`UpSpaceScreen`）
  - UP 空间的动态（`UpSpaceScreen`）
  - 动态页（`DynamicScreen`）
  - 动态评论弹窗（`DynamicCommentDialog`）
  
  四处都改用 `shouldAutoLoadMore`，底部换成设计系统现成的 `BsLoadMoreFooter`（在加载就转圈，失败就显示原因和「重试」，没出错时照旧显示「加载中…」）。
  原来 UP 空间两处失败后什么都不显示，动态页只显示原因、没有「重试」。
  动态评论弹窗原来给 `BsLoadMoreFooter` 传的是写死的「一直在加载、没有错误」，失败时只会一直转圈，现在传真实状态。
  搜索页的自动加载按 `(shouldLoadMore, itemCount)` 触发，失败不会重新触发，没有这个问题。
- **验证**：先写 `LoadMorePolicyTest`（4 例：正常加载、失败后不再来、加载中不重复、没有更多不加载）并确认编译失败再实现；`./gradlew test assembleDebug :app:compileDebugAndroidTestKotlin` 通过（`:app` 347 例全绿）。按用户要求没有装机。
- **未验证（要真机看）**：断网后在合集列表、UP 空间（投稿 / 动态）、动态页、动态评论弹窗滚到底，应显示错误和「重试」，不会自己一直重试；恢复网络点「重试」能接着加载。

### 13.42 离开播放页回到迷你播放条：收起播放页、看自动切成听（2026-10-04）

设计稿：[leave-player-to-listen](superpowers/specs/2026-10-04-leave-player-to-listen-design.md)。

- **起因**（用户原话）：进入播放页后，从底部四个主页面切换时播放页不会返回为迷你播放条，希望切换时收回播放页；回到迷你播放条时如果在看，自动切到听。
- **原因**：离开播放页的几条路以前各走各的。
  - 只有左上「收起」箭头会先切成听再退。
  - 系统返回手势直接退出这一页，画面没了、视频轨还开着，违反「视频轨启用 ⟺ 存在可见 surface」。
  - 点底部页面时，播放页跟着它所在页面的返回栈一起存起来，不收起，切回来又被恢复出来，还在看。
  - 从播放页跳去 UP 空间时，迷你播放条出现了，却仍在看。
  - 「起播模式：记住上次」在起播时就进看，但起播早已不再自动打开播放页，画面没有地方显示、视频却在解码。

  - 收起箭头、系统返回（播放页上新增 `BackHandler`）、点底部页面、程序化切 tab、跳去 UP 空间，都走 `AppShell.leavePlayerThen`：在看先切成听，等呈现态变成 `NONE` 再跳。
  - 点底部页面时先 `popBackStack()` 退掉播放页再切，播放页不会再被存进页面的返回栈。
  - 兜底：迷你播放条在显示却还在内嵌看，自动切成听（`shouldForceListen`）。
  - 自动切成听用 `AppViewModel.leaveToListen()`，只撤画面、不写「上次在看」。用户在播放页上亲手点「听 / 看」才写。
  - 「记住上次」改在播放页进入组合时判断（`onPlayerPageShown` → `shouldAutoWatchOnPlayerPage`）。删掉 `MainActivity` 起播时的自动进看和 `shouldAutoEnterVideo`。
  - 设置页说明改为「上次离开播放页时在看，下次打开播放页直接进看模式」。
  - 规则在 `ui/PlayerPagePolicy.kt`（`mustLeaveToListen` / `shouldForceListen` / `shouldAutoWatchOnPlayerPage`）。
- **验证**：先写 `PlayerPagePolicyTest`（6 例）并确认编译失败再实现；`./gradlew test assembleDebug :app:compileDebugAndroidTestKotlin` 通过（`:app` 353 例全绿）。导航接线没有 UI 测试。按用户要求没有装机。
- **顺带发现（用户确认后一并处理）**：
  - `MainPlaybackChainTest`（androidTest）早已过期：它找已不存在的按钮文字「切「看」」「退回「听」」，还假设起播会自动展开播放页。
    已按现在的界面改写：
    - 主链路：起播停在迷你播放条、是听 → 点迷你条打开播放页 → 点「看」 → 下一首回到听。
    - 暂停与继续：改在迷你条上按无障碍描述找。
    - 新增两例：看模式下点底部「列表」收起播放页并切回听，切回「搜索」播放页不再冒出来；看模式下按返回收起并切回听。
    
    只做了编译核对，没有在设备上跑。
  - `AppViewModel.playbackStarted` 这条起播信号去掉起播进看之后已经没有人用，已删除：6 处发信号、`AppShell` 的同名参数和 `MainActivity` 的传参。
- **未验证（要真机看）**：在看时点底部各页面、返回手势、收起箭头、「查看UP主」都收起并切成听，声音不断、进度不跳、没有黑框或残影；切回原页面播放页不再冒出来；全屏返回、画中画仍在看；「记住上次」打开播放页时切回看。手动测试指南步骤 8 末尾已补检查点。

### 13.46 长图文动态展开：全文、图片按原位置、长按选字（2026-10-04）

设计稿：[dynamic-opus-inline-images](superpowers/specs/2026-10-04-dynamic-opus-inline-images-design.md)。

- **起因**（用户原话，附截图）：「这个动态内容比较多，同时在文字中间穿插了图片。在展开时，图片没有正常的渲染，而且文字没有加载全。」截图里展开后正文中间是一行行「[图片]」，末尾是「…」，卡片上一张图都没有。选方案时补充：「现在单点展开的动态文字会自动折叠。我还想长按时进行文字选择。」
- **原因**：
  - 展开时拉两份详情：web 详情（截断摘要，图片位置写成「[图片]」）和 opus 详情（完整段落）。`detailContentScore` 只算 `opus.pics 张数 + summary 长度`，opus 详情的全文归一化进了 `desc`、`summary` 为空，得分只有图片张数，永远输给截断摘要，全文被丢掉。
  - 解析 opus 详情时文字拼成一整段、图片另收一组，位置信息丢了；展开态只换文字，图片区还是动态流的预览图——这条动态在动态流里没有预览图。
  - 修好第一条后会冒出来：opus 详情的 `type` 可能是数字，`parseDynamicItem` 认不出，展开会「加载失败」。
  - 展开后整段正文挂着点击收起，长按松手也算一次点击，没法选字。
- **用户选定**：图片按原文顺序穿插（和 B 站一样）。
- **网络层**：
  - 新增 `dto.DynamicBlock`（`Text` / `Images`）、`dto.DynamicPic`（url + 宽高）；`DynamicOpus.blocks`（`@Transient`，只在 opus 详情段落归一化时填）；`DynamicEntry.body`。
  - `DynamicModulesCompatSerializer` 按原文顺序收段落：相邻文字段用换行合成一段，图片段带宽高；分割线图不进段落（仍在平铺 `pics` 里）。
  - `detailContentScore`：带段落的候选得 `100_000 + 文字长度 + 图片张数`，总是优先（对齐 bilipai）。
  - `mergeDetailItem`：详情带段落时正文以详情为准；`type` 认不出时按 feed 卡片的类型解析，没有 seed 按 OPUS。
- **界面**（`DynamicScreen` 的 `DynamicBody`，动态页和 UP 空间页的动态共用）：
  - 展开且拉到段落时按顺序画：文字照旧（表情、话题）；一段一张图铺满宽度、按原图比例，缺宽高按 4:3，特别长的图最高到宽的 2 倍、多出的裁掉；一段多张图用九宫格。点图进预览，左右能翻到正文所有图。
  - 正文里有图时卡片下方不再重复画预览图；没拉到段落时退回整段文字。
  - 单击正文不再收起；「收起」改成正文下方右侧单独一行，复制时不会带上。
  - 动态正文长按可选中复制（`SelectionContainer`），折叠、加载中、失败、展开后都可以。
  - 判断放在 `ui/DynamicBodyPolicy.kt`：`expandedBody`、`bodyImageUrls`、`bodyImageOffsets`、`inlineImageAspect`。
  - `RichText` 的 `suffix` 参数只有动态「收起」在用，已删除。
- **验证**：
  - 先写测试并确认失败再实现：`DynamicDetailParseTest` 加 5 例（段落顺序、feed 没有段落、评分优先、合并取详情全文、数字 type），`DynamicBodyPolicyTest` 6 例。去掉评分修正时「带段落的详情优先于更长的截断摘要」失败，确认它能复现原问题。
  - `DynamicCardClickRegionsUiTest` 加「展开后单击正文不收起」「长图文按段落显示、点收起回调」，只做了编译核对。

- **未验证（要真机看）**：opus 详情真实返回的形状（自动化不能请求 B 站）；截图里那条长图文展开后的全文与图片位置；普通图文（较长文字 + 九宫格）展开后九宫格的位置；超长图的裁切；长按选字与复制；单击正文不收起。

设计稿：[download-improvements](superpowers/specs/2026-10-04-download-improvements-design.md)。

- **起因**（用户原话，五条）：
  - 「已下载中的已完成条目，需要添加三点功能按钮和右滑删除功能」；

  - `DownloadListPolicy.doneEntries` 把同一视频的 2 个及以上分 P 合成一组，按 P 几排序（`splitPartTitle`）。
  - 组行显示「N 个分 P · 位置 · 总大小」，点开是分 P 页：点一行用 `playFromContext` 从这一 P 播起；三点和右滑删除。
  - `DownloadNoticePolicy`：一个视频还有分 P 在排队 / 下载 / 暂停时不提醒，最后一个完成时「下载完成：视频标题（共 N 个分 P）」。

### 13.70 通知栏 / 锁屏的「下一首」可用，「上一首」真的换歌（2026-10-21）

- **起因**（用户原话）：「播放时，手机系统下拉栏和锁屏界面的控制台中，只能播放上一首和暂停开始，播放下一首的按钮没有或是灰色不可用」。
- **原因**：队列在 `PlayerConnection` 里，ExoPlayer 里永远只有当前一首（切歌是 `setMediaItem()` 整体替换）。系统控件按播放器自己的列表判断，认为没有下一首；「上一首」是 Media3 的默认行为——回到本首开头，并没有换歌。
- **做法**：`PlaybackService` 交给 MediaSession 的改成 `internal/QueueSkipPlayer.kt`（`ForwardingPlayer`）：始终声明 `COMMAND_SEEK_TO_NEXT / PREVIOUS`（含 `_MEDIA_ITEM`），按下后经 `QueueSkipBridge`（同进程）转给 `PlayerConnection`，规则与 App 内按钮相同（`resolveManualNextIndex` / `resolvePreviousIndex`）；队列到头或界面侧没连上时退回播放器原本的行为。耳机 / 蓝牙的切歌键走同一条路。
  - session 收到「可用命令变了」时直接用事件里的那份，所以 listener 也要包一层把事件补齐；Kotlin `by` 委托不转发 Java 默认方法，改用动态代理，按参数类型认方法（release 包 R8 会给 Media3 改名）。
- **已知局限**：界面进程被系统回收、只剩播放服务时，这两个键退回原行为（与播完自动下一首同一前提）。
- **验证**：`QueueSkipPlayerTest` 5 例（转给队列、到头退回、没登记退回、其余事件照转、移除交回同一个代理）；命令表的补齐依赖 `SparseBooleanArray`，JVM 单测测不了；`./gradlew test` 通过。2026-10-21 debug 包真机测试通过；release 包待验证。

### 13.71 消息中心未读角标修正；「回复与@」点条目改为看详情（2026-10-21）

- **起因**（用户原话）：「消息中心……特别是点赞，显示的未读信息数量角标不对」；「在回复与@中……我点击后直接开始播放，我希望点击的时候不碰播放，而是打开一个消息详情和回复框」。
- **核查到的问题**（对照 `ref/bilipai`，两边未读接口与字段相同，点赞都取 `x/msgfeed/unread` 的 `like`，都没有点赞已读接口、靠「拉列表即已读」）：
  1. 信封总数含私信未读，但消息中心里私信会话行不显示未读数，总数与页面里能看到的角标对不上；
  2. 进消息中心不刷新未读（设计稿要求刷新，实现漏了），角标停在上次回前台时的值；
  3. 两路未读任一路失败或返回错误码就按 0 算、整体失败全清零，角标忽然变小 / 消失又冒出来；
  4. 回前台、进页面、列表加载完各发一次刷新，互不取消，慢的旧结果晚回来会把刚清掉的角标盖回去；
  5. 超过 99 显示「99」；App 内登录后要等切后台再回来才有角标。
- **做法**：新增 `core/network/internal/UnreadPolicy.kt`（`resolveUnreadSummary`：两路都 code=0 才出结果，否则 null），`messageUnread()` 改返回可空，调用方 null 时保留旧角标；`MessageCenterController.refreshUnreadCount()` 新一次取消上一次；进消息中心 / 下拉刷新同时刷角标；私信会话行显示 `unread_count`，看完一个会话本地清零；角标文字 `unreadBadgeText`（>99 显示「99+」）；登录状态变化时刷新一次。
  - 「回复与@」：点条目不再播放，弹出消息详情（`ReplyAtScreen`，完整展开的底部弹层）：全文、被回复的我的评论、视频标题 +「播放视频」、回复框；原来的长按回复去掉（点一下就是同一个弹层）。动态 / 专栏下的评论没有「播放视频」，也不能站内回复，显示灰字说明。
- **未做**：总数未计入系统通知 / 被拦截私信 / 客服消息（BiliPai 计入），因为消息中心没有系统通知入口，计入后用户清不掉。看完点赞后服务端若有延迟，本次刷新可能仍是旧数，要到下次回前台才更新——需真机确认是否存在。
- **验证**：`UnreadPolicyTest` 4 例、`UnreadBadgeTextTest` 2 例；`./gradlew :core:network:test :app:testDebugUnitTest` 通过，`:app:compileDebugKotlin` 通过。未装机，真机检查项见手动测试指南步骤 29 末尾。
